## 1. Varnish CVE-2026-50052 — HTTP/2 request-smuggling/desync, distinct from the CVE-2026-34475 already tracked (HIGH PRIORITY — feeds `tech-varnish.md` + `class-request-smuggling.md`)
New Varnish CVE beyond the auth-bypass one surfaced 2026-07-25. A deficiency in HTTP/2→HTTP/1.1 frame translation lets a crafted HTTP/2 request be seen as one request by Varnish but two by the backend — the smuggled second request gets attributed to the *next* legit user's connection (cache poisoning / auth-bypass / response hijack). **Only exposed when Varnish is built/run with `+http2` explicitly enabled** (off by default, so real-world exposure is narrower than it sounds — check for HTTP/2 support before treating a Varnish host as in-range). Fixed: Varnish Cache 9.0.3/8.0.2/6.0.18, Vinyl Cache 9.0.1 (2026-05-18). Detect: version-fingerprint + confirm HTTP/2 is actually spoken (`h2` in ALPN/`Upgrade`) before flagging.
Sources: [sentinelone.com/vulnerability-database/cve-2026-50052](https://www.sentinelone.com/vulnerability-database/cve-2026-50052/), [docs.varnish-software.com/security/VSV00019](https://docs.varnish-software.com/security/VSV00019/), [blog.calif.io/p/mad-bugs-my-cousin-vinyl-cve-2026](https://blog.calif.io/p/mad-bugs-my-cousin-vinyl-cve-2026)

## 2. GraphQL introspection-block bypass: newline-in-`__schema` regex evasion + CVE-2026-30854 inline-fragment bypass (feeds `class-graphql.md`)
Two new bypasses for our "introspection OFF → Clairvoyance field-suggestion" fallback, useful as a **cheaper pre-step to try before falling back to the slow suggestion-mining path**:
- Most introspection blockers regex-match the literal string `__schema`/`__type` in the request body. GraphQL itself ignores whitespace/newlines/commas between tokens, but many blocking regexes don't — inserting a newline inside `__schema` (`__sch\nema`) slips past the filter while the parser still executes it as valid introspection.
- **CVE-2026-30854** (Parse Server, GraphQL adapter): nesting a `__type` query inside an inline fragment (`... on Query { __type(name:"X"){name fields{name}} }`) bypasses the `disableIntrospection` control even when it's correctly configured, letting an unauth client still walk type names one at a time.
Both are read-only reconnaissance (introspection-equivalent), fit our existing safe-probe gate — worth trying as step 0 before the Clairvoyance near-miss suggestion harvest in `recon_graphql.sh`.
Sources: [x.com/0xacb/status/2022643073855951103](https://x.com/0xacb/status/2022643073855951103), [sentinelone.com/vulnerability-database/cve-2026-35413](https://www.sentinelone.com/vulnerability-database/cve-2026-35413/), [advisories.gitlab.com/pkg/npm/parse-server/CVE-2026-30854](https://advisories.gitlab.com/pkg/npm/parse-server/CVE-2026-30854)

## 3. AWS Amplify dangling IAM trust-policy → unauth Cognito role takeover (feeds `class-cognito-unauth.md` — directly matches our lane's exact pattern)
Datadog/Mallory-documented pattern that's a closer match to `recon_cognito.sh`'s exact chain than a generic Cognito misconfig: when Amplify's Authentication category is **removed** from a project, the generated IAM role's trust-policy `Condition` (which scoped `sts:AssumeRoleWithWebIdentity` to the specific identity pool) is stripped but `"Effect":"Allow"` is left standing — so the role becomes assumable with **no condition at all** by anyone who can supply a web-identity token from *any* provider, not just the original pool. This is a second, independent way to land "unauthenticated → issued AWS credentials" beyond the legacy-MobileHub pattern already in our KB (the Logitech #3800848 reference case) — worth adding as a second detection signal: a Cognito-fronted host whose linked IAM role trust policy has `Allow` + `AssumeRoleWithWebIdentity` but no matching `Condition`/`aud` restriction.
Sources: [mallory.ai/stories/019e59ea-36a4-79e9-9431-fa3fc572a19d](https://www.mallory.ai/stories/019e59ea-36a4-79e9-9431-fa3fc572a19d), [securitylabs.datadoghq.com/articles/amplified-exposure](https://securitylabs.datadoghq.com/articles/amplified-exposure-how-aws-flaws-made-amplify-iam-roles-vulnerable-to-takeover/)

## 4. Favicon-hash pivot to find true origin IP behind CDN/WAF (feeds `class-cdn-origin-bypass.md`)
Standard technique but directly actionable against our top-tech list (Cloudflare/CloudFront/Google Cloud CDN dominate our in-scope surface, and CDN-fronting is exactly what makes our `recon_port_proto.py` chain skip a host — "a CDN ACKs every port"). Hash the target's favicon (MurmurHash3, the Shodan-native format) from a confirmed in-scope host, then dork `http.favicon.hash:<hash>` on Shodan/Censys — same infra reused on a non-CDN IP (dev/staging/build box) shows up directly, turning a "skipped, CDN-fronted" host into one where the port/protocol chain is actually meaningful. Fits inside our existing Shodan budget discipline (`recon_uncover.sh`, 60/100 monthly cap) as one more query type, not a new credit sink.
Sources: [hivesecurity.gitlab.io/blog/favicon-hash-shodan-infrastructure-fingerprinting](https://hivesecurity.gitlab.io/blog/favicon-hash-shodan-infrastructure-fingerprinting/), [payatu.com/blog/favicon-hash](https://payatu.com/blog/favicon-hash/)
