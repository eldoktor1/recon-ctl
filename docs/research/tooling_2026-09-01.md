# Research digest — tooling — 2026-09-01 (pass 2)

## Bottom line
One genuine category gap found: our cache lane (`recon_wcd.sh` + WCVS) covers poisoning/deception but not **CPDoS** (cache-poisoning-triggered *denial of service*) or cache-key-normalization DoS — a distinct, unauth-safe, non-destructive-to-detect primitive we don't currently probe for. JWT-tooling, gitleaks-vs-trufflehog, subdomain-takeover, and shadow-API/openapi-diff sweeps turned up nothing that beats what we already run or evaluated — noted below as checked/rejected so future passes don't re-spend budget there.

## 1. EVALUATE — `c0dejump/HExHTTP`
- **What it is:** Python CLI, 762★, license unspecified, **actively pushed 2026-08-26** (5 days ago). Broader-than-poisoning "HTTP header exploitation" tool: web cache poisoning, **CPDoS** (Cache Poisoning Denial-of-Service — forcing an error response to get cached and DoS all subsequent visitors), cache-key normalization DoS, plus vhost/method/CDN-proxy behavior analysis. `-u/-f` single/bulk URL, `-H`/`-A` custom header/UA, `--proxy`/`--burp` integration, `--humans` (rate-limit-friendly pacing), `-o` HTML report.
- **Why it matters:** our `class-cache-deception.md` KB and `recon_wcd.sh` doctrine center on WCD (path-confusion) and WCP (unkeyed-header reflection into cache) — both *confidentiality/integrity* framings. CPDoS is a third, distinct primitive: an attacker-crafted request (oversized header, malformed Accept, HTTP/2 pseudo-header abuse, etc.) causes an origin error that then gets **cached and served to everyone** — i.e. an unauth, non-destructive-to-*detect* DoS-capability primitive, same shape as our graphql-cop batch/alias-DoS-detection pattern (adopted 2026-08-18): confirm the primitive exists without launching the actual DoS.
- **Doctrine fit:** unauth-safe ✅ (detection probes, not a sustained flood), dup-resistant ✅ (CPDoS is far less commonly scanned than reflected WCP), non-destructive **if** used in detect-only mode — but a positive CPDoS hit necessarily means the tool *did* cache one bad response, so it must run with the SAME "test under our own cache-buster key, never poison the shared cache real users hit" discipline `recon_wcd.sh` already enforces, and any confirmed CPDoS hit needs an explicit purge/cooldown, not repeated firing.
- **Caveats:** no explicit OSS license in the repo metadata (check before any redistribution/CI baking-in, doesn't block internal use); broader "header exploitation" scope than we need (vhost/method probing overlaps other lanes) — cherry-pick the CPDoS/cache-key-normalization checks rather than adopting the whole tool wholesale; last digest (2026-08-29) concluded "nothing beats WCVS" for cache tooling — that was correct for WCD/WCP but missed the CPDoS angle, which is genuinely additive, not a WCVS replacement.
- **Verdict: EVALUATE** — trial CPDoS/cache-key-normalization checks against 1-2 in-scope CDN-fronted hosts already in the `recon-wcd` worklist, own-cache-buster only; if it fires cleanly with low FP, wire the CPDoS check into `recon_wcd.sh` as a new LEAD subtype (`wcd:cpdos-lead`) alongside the existing WCD/WCP leads — do not let it auto-flood, respect the same throttle.
