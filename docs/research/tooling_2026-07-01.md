### Lane gaps — no current coverage in our pipeline

#### 1. Race Conditions (HTTP/2 single-packet) — EVALUATE

**Gap:** We have no automated race-condition lane. Single-packet HTTP/2 race attacks (Kettle 2023, now mainstream in 2025-2026 bug bounties) collapse network jitter to zero, making TOCTOU/double-spend/limit-bypass reliably exploitable. Reward class: payment flows, coupon/promo code replay, credit balance overconsumption. High-payout, dup-resistant because it requires timing + state understanding that commodity scanners miss.

**Best current tooling:**
- [Turbo Intruder](https://github.com/PortSwigger/turbo-intruder) (Burp extension, HTTP/2 support built-in) — operator-driven
- `curl --http2` + a parallel launch shell wrapper — lightweight CLI approach for our pipeline

**Doctrine fit:** Unauth-safe (test on registration/promo/rate-limited endpoints); non-destructive (fire N identical requests, observe response divergence); dup-resistant (crowd doesn't automate this). CONFIRMED would need operator to verify actual state change.

**Action:** Add a `recon_race.sh` lane: discover endpoints with rate-limit signals (429s in our ES data) or financial/promo/counter semantics from jsintel → flag as race candidates → operator tests with Turbo Intruder. No existing script to retire; new KB doc needed.



## CONFIRMED primitive
Two or more successful responses where only ONE should succeed (e.g., coupon applied twice, balance debited twice for one action). Operator observes actual state change using two owned accounts.

## Hard lines
- Never trigger real money movement against third-party accounts
- Test only on own accounts (register two, test cross-account or self-double-spend)
- IDOR race (two users racing for same resource) = human-in-the-loop only

## Sources
- James Kettle, "Smashing the State Machine: The True Potential of Web Race Conditions" (PortSwigger Research, 2023): https://portswigger.net/research/smashing-the-state-machine
- Turbo Intruder: https://github.com/PortSwigger/turbo-intruder

#### 2. JWT Algorithm Confusion / alg:none — EVALUATE

**Gap:** No JWT-specific testing lane. JWT vulns (alg:none, RS→HS key confusion, weak-secret brute) are reliably paid and unauth-testable — you need only a valid token (often in jsintel or the app's own login flow). CVE-2026-29000 (pac4j JWE-wrapped PlainJWT bypass, 2026) confirms the class is live.

**Best current tooling:**
- [jwt_tool](https://github.com/ticarpi/jwt_tool) — CLI, established, covers alg:none + confusion + crack; last commit active 2025
- No new tool beats it

**Doctrine fit:** Unauth-safe (the attack IS the bypass attempt, requires only a token you already have); non-destructive (forge a token, attempt one request, observe 200 vs 401); dup-resistant (requires per-app reasoning about key type + algorithm). Not a commodity scan.

**Action:** Add JWT signal to jsintel lane: when sourcemapper/jsluice surfaces a JWT decode call or `Authorization: Bearer` header pattern, flag the host as `jwt_candidate`. Operator tests with jwt_tool. Add to briefing output.



### 2. alg:none bypass
Some libraries skip signature verification when `alg: none`. Change header alg, strip signature.

```bash
python3 jwt_tool.py <token> -X a
```

### 3. Weak secret brute
HS256/HS384/HS512 with a guessable secret.

```bash
python3 jwt_tool.py <token> -C -d /usr/share/wordlists/rockyou.txt
```

### 4. JWK injection
If server trusts a `jwk` header embedded in the token itself.

```bash
python3 jwt_tool.py <token> -X i
```

## Signals to target (jsintel / ES)
- `/.well-known/jwks.json` in endpoint surface (public key exposed)
- JS containing `jwt_decode`, `verify(`, `Bearer` in fetch/axios headers
- `/api/auth`, `/oauth/token`, `/login` returning JWT in response body
- CVE-specific: pac4j < 4.0 (CVE-2026-29000), node-jsonwebtoken < 9.0, python-jose < 3.4

## Unauth-safe confirm primitive
1. Capture a valid JWT (login with own account, or from JS/sourcemap)
2. Attempt alg:none or confusion variant
3. CONFIRMED = server accepts forged token (200/data returned instead of 401)

## Hard lines
- Use ONLY your own account's JWT as base
- Never forge tokens targeting other users' IDs
- NEVER use RCE-capable payloads even if JWT drives a deserialization sink

## Tools
- jwt_tool: https://github.com/ticarpi/jwt_tool (Python CLI, covers all attack classes)
- CyberChef JWT decoder (manual inspection)

## Sources
- CVE-2026-29000: https://nvd.nist.gov/vuln/detail/CVE-2026-29000
- PortSwigger JWT attacks: https://portswigger.net/web-security/jwt

#### 3. Prototype Pollution — LOW PRIORITY / SKIP for pipeline

**Server-side PP** (Node.js `__proto__` injection → RCE/auth bypass) is high-payout but hard to test safely unauth in an automated lane — the confirm primitive is inherently destructive (pollution persists in the server process). No pipeline-safe tool surfaced; no tooling is better than manual testing.

**Client-side PP** → DOM XSS sink is already covered by our dalfox `--deep-domxss` lane and DOMDig.

**Verdict: SKIP for autonomous pipeline.** Add to operator manual checklist when hitting Node.js APIs.
