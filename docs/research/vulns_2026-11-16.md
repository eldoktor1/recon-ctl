# Research digest — vulns — 2026-11-16

## Research Digest — Vuln/CVE + Writeup Watch (2026-11-16, trailing ~14d)

### 1. Apache HTTP Server CVE-2026-119618 — unauth RCE in mod_http2 (HIGHEST PRIORITY, matches our top tech)
- **What:** Race condition / heap corruption in `mod_http2`; unauthenticated, network-reachable RCE (Red Hat confirms unauth RCE classification). Reported independently by Anthropic's OSS Scanner (Oct 26) and Google Cloud VRP (Nov 3).
- **Affected:** Apache httpd **2.4.55 – 2.4.70** (standalone `mod_h2` 2.0.8–2.0.42). Fixed in **2.4.71** (released Nov 11, 2026). Also bundles CVE-2026-106023 (DoS crash) and CVE-2026-109163 (low-sev stack overflow).
- **Precondition:** **HTTP/2 must be enabled** (`Protocols` directive / ALPN `h2`) — HTTP/1.1-only servers are not vulnerable. This is the detection-critical fact: version-in-range alone is not enough, per our n-day doctrine.
- **Detect (in-range-verifiable, unauth-safe):** (a) `Server:` header version string if not suppressed; (b) TLS ALPN negotiation offering `h2` confirms the precondition even when the header is hidden. Both are safe/passive checks — feed into `recon_nday.sh`.
- **PoC status:** Public PoC reproduces crash/memory-corruption only, **not** demonstrated RCE yet — treat as LEAD (confirmed-in-range version + HTTP/2 flag), never P0, until a working RCE PoC surfaces.
- Sources: [SecurityWeek](https://www.securityweek.com/apache-patches-critical-http-server-rce-found-by-anthropic-google/), [Rescana](https://www.rescana.com/post/apache-httpd-mod-http2-cve-2026-119618-patch-now), [TheHackerNews](https://thehackernews.com/2026/11/critical-apache-http2-flaw-could-let.html)

### 2. WordPress Core CVE-2026-119977 — KEV, unauth RCE via update-process TOCTOU
- **What:** CWE-367 TOCTOU in WordPress's full-package core-update flow. Installer files stage briefly in a **predictable path under `wp-content/upgrade/`** before replacing the live install; an attacker racing that window can execute arbitrary PHP. CVSS 8.1, added to CISA KEV **Nov 3, 2026**.
- **Affected:** WordPress Core **4.7 – 7.1.3**.
- **Actionability for us:** narrow timing window (only exploitable *during* a live core auto-update), so it's not a standing scan target — but it's a strong fit for our **n-day racing doctrine**: watch for in-scope WP hosts about to auto-update after a new core release drops, and probe `wp-content/upgrade/` paths during that window. Low value as a passive/background check.
- Sources: [BleepingComputer](https://www.bleepingcomputer.com/news/security/cisa-flags-wordpress-rce-flaw-as-actively-exploited-in-attacks/), [Beazley Labs advisory](https://labs.beazley.security/advisories/BSL-A1241)

### 3. New XSS primitive: Cloudflare `/cdn-cgi/image/` — SVG-sanitizer bypass + Chromium Cache-Control-strips-CSP trick (reusable technique, Cloudflare is our #1 CDN)
- **What ("Cache Me If You Can", Searchlight Cyber, Oct 28 2026):** chained (a) a bypass of Cloudflare's `svg-hush` SVG sanitizer, with (b) a Chromium quirk where a specific `Cache-Control` header on the **origin** image response causes Chromium to **exclude the CSP header from its cached representation** on replay — defeating a `default-src 'none'` CSP that would otherwise block the injected SVG script.
- **Already fixed** on Cloudflare's own `/cdn-cgi/image/` zone — not directly exploitable against Cloudflare infra anymore. But the researchers note the **same cache/CSP-strip primitive extends to Netlify Image CDN and public S3 objects under specific conditions** — i.e., it's a generic technique against *any* image-proxy/CDN that (1) accepts SVG uploads reflected back, (2) relies on CSP rather than content-type/sandboxing to neutralize them, and (3) passes through origin `Cache-Control`.
- **Actionable for us:** on in-scope hosts using Cloudflare image resizing, a self-hosted image proxy, or any CDN serving user-uploaded SVGs — check whether CSP survives a crafted origin `Cache-Control` on repeat/cached fetch.
- Sources: [slcyber.io writeup](https://www.slcyber.io/research/cache-me-if-you-can-xss-in-cloudflares-cdn-cgi-image), [cybersecuritynews.com](https://cybersecuritynews.com/cloudflare-xss-vulnerability/)

### 4. CloudFront/WAF bypass technique: HTTP/2 body fragmentation defeats WAF body inspection (CVE-2026-13762, already remediated server-side)
- AWS's own CloudFront+WAF pairing had inconsistent HTTP/2 request-body reassembly between the WAF inspection layer and the forwarding logic, letting fragmented HTTP/2 bodies carry payloads past AWS Managed Rules undetected. **Remediated server-side by AWS already — no longer exploitable against CloudFront itself.** Worth keeping only as a generic WAF-bypass *idea* to test against other origin WAFs we encounter (body-fragmentation across HTTP/2 DATA frames), not a standing lead.
- Source: [GitHub Advisory](https://github.com/advisories/ghsa-9jjc-h3c2-fw2v)
