## Tooling Watch — 2026-07-18

### ADOPT — Autoswagger (intruder-io/autoswagger)
Free OSS BOLA/broken-authz scanner for Swagger/OpenAPI-documented APIs. Discovers specs (direct
`.json/.yaml`, Swagger-UI paths, common `/swagger.json`/`/openapi.json` brute-force), then hits every
documented endpoint **unauthenticated, GET-only by default** — flags any 200 that shouldn't need auth,
then screens the response for PII (via Presidio), secrets (regex), or oversized/"interesting" payloads.
This is exactly our safe-probe doctrine already codified (unauth, non-mutating, no creds) — the `-risk`
flag adds mutating methods but we'd **never enable that** autonomously. It's a direct complement to
kiterunner (finds routes on bare API gateways) and native GraphQL schema reasoning: same "read the spec,
reason over what shouldn't be reachable unauth" idea, but for REST/Swagger, and it ships the PII/secret
response-screening we currently do by hand. Young project (Intruder's initial release, still adding spec
format coverage) but the mechanics are sound and match our IDOR/BAC pillar's LEAD tier exactly (a 200 +
PII/secrets without auth = provenance-confirmed candidate, same rigor as `recon_idor_candidates.py`).
**Verdict: ADOPT** — wire as an on-demand lane next to `recon-kr`: run against any host where jsintel/kr
surfaces a Swagger/OpenAPI spec, GET-only, feed hits into the IDOR/BAC candidate ranker as LEADs (never
auto-mint CONFIRMED — still Claude-verify + human 2-account swap for anything requiring more than "this
endpoint answers unauth").
Sources: [autoswagger GitHub](https://github.com/intruder-io/autoswagger), [Intruder research post](https://www.intruder.io/research/broken-authorization-apis-autoswagger), [Help Net Security coverage](https://www.helpnetsecurity.com/2025/07/24/autoswagger-open-source-tool-expose-hidden-api-authorization-flaws/)

### EVALUATE — Hadrian (praetorian-inc/hadrian)
OSS API security framework (Go, Apache-2.0, v1.0.0 Mar 2026, 67 stars — small but active, 144 commits)
automating **role-based BOLA/BFLA testing** across REST (OpenAPI), GraphQL (introspection/SDL), and gRPC
(proto), via YAML-defined roles + `auth.yaml` credentials, doing setup→attack→verify (create a probe
resource as role A, try to access/modify it as role B). This is NOT unauth-safe — it needs multiple
authenticated role credentials and explicitly creates/mutates/deletes resources, so it's a hard fit for
our **human-in-the-loop, 2-owned-account** authed-IDOR SOP, never the autonomous pipeline. Could replace
some of the manual Claude-in-Chrome "map ops, swap owned IDs" grind once we've provisioned 2 accounts on
a target with a published spec — but small community, worth a supervised trial on one real target
(staging-first per its own docs) before trusting it inside the SOP.
**Verdict: EVALUATE** — try manually on the next target where we have 2 owned accounts + an OpenAPI/GraphQL
spec; do not wire into any autonomous lane (mutating by design).
Sources: [Hadrian GitHub](https://github.com/praetorian-inc/hadrian)

### SKIP — Noseyparker (praetorian-inc/noseyparker)
Rust-based git-history secret scanner, faster than TruffleHog on huge histories but weaker ruleset and no
live-credential verification. **Archived by Praetorian on 2026-04-24 — read-only, no further updates.**
TruffleHog remains the right call for us specifically because verified-live-credential confirmation is
what lets us mint CONFIRMED without a human staring at a token-shaped string (matches our own documented
`js_secret_hit`-noise lesson). No action needed — flagging only so nobody resurrects noseyparker later.
Sources: [appsecsanta secret-scanning comparison](https://appsecsanta.com/secret-scanning-tools/best-open-source-secret-scanning-tools)

### SKIP — graphql-scanner (davidfortytwo/graphql-scanner)
Checks introspection exposure + schema misconfig + basic resource-pressure signals. Functionally a subset
of what `recon_graphql.sh` already does (native introspection harvest → Claude reasoning over the schema
for sensitive mutations/object-ref args/injectable args), with none of our doctrine's dup-resistance (it
stops at "introspection enabled," which our own KB already flags as an Info-FP, not a finding).
**Verdict: SKIP** — no capability we lack.

### Noted, not adopted — cvemap (projectdiscovery/cvemap)
ProjectDiscovery's own CLI: navigates CVEs with nuclei-template status + public-PoC links attached, same
team/quality bar as subfinder/httpx/nuclei/katana we already run. Marginal but real time-save for the
n-day lane's version-reasoning step (quick "does this CVE have a nuclei template / a public PoC" lookup
before treating a KEV tech-match as anything more than a LEAD). Not a new capability, just a faster lookup.
**Verdict: light-EVALUATE** — worth a one-off manual trial (`cvemap -cve <id>`) next time `recon-mood
CVE-xxxx` needs a quick template/PoC check; not worth wiring in yet.
Sources: [cvemap overview](https://docs.projectdiscovery.io/opensource/cvemap/overview)
