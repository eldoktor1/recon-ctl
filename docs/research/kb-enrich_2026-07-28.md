## 1. SSRF — redirect-chain as confirm-primitive bypass + impact-escalation reasoning (class-ssrf.md)

Two gaps in the current doc: it correctly refuses to be a payload list (bypass-the-*class*, not memorize payloads), but is missing (a) a technique for when the sink strict-validates our canary URL itself, and (b) a severity/impact note for post-confirm reasoning.

- **Redirect-chain bypass for OOB confirm** — if a sink allowlists/validates the *input* URL but the underlying HTTP client follows redirects, point it at an **allowed-looking URL that 302s to the interactsh canary** instead of the canary directly. This can turn a "sink appears protected" negative into a confirmed OOB hit without touching internal data — still zero-exploitation, same interactsh-callback confirm primitive, just routed around allowlist validation that only checks the initial hostname. Worth trying as a second pass on any sink that 400s/refuses the direct canary URL before writing it off.
- **Protocol-smuggling impact note (operator-only, post-confirm severity, never autonomous):** gopher/dict schemes send raw bytes including CRLF to the target port — since Redis/Memcached/SMTP/FastCGI are text/line-based protocols, a confirmed SSRF against an internal service on those ports can escalate past "OOB ping" into real internal-service command injection (e.g. Redis `CONFIG SET`/key write via gopher). This is squarely in "confirm the exposure, don't exploit past it" territory — the note is for *severity write-up reasoning* (an SSRF that can reach an internal Redis/Memcached is materially worse than one that can only reach an HTTP metadata endpoint), not something the pipeline fires.



## 2. Bucket exposure — Azure anonymous listing correction + SAS-token mining sub-lane (class-bucket-exposure.md)

The doc currently states flatly "Azure can't enumerate containers anonymously" (line 104). Microsoft's own docs (learn.microsoft.com/azure/storage/blobs/anonymous-read-access-configure) say this is only true at the **Blob** public-access level; at the **Container** level, anonymous clients CAN list all blobs via a plain HTTP GET. This is a real gap — a live check we're not running — and also missing entirely is **SAS-token exposure**, a distinct and arguably higher-EV Azure lane that overlaps directly with our existing JS-intel/trufflehog secret-mining pillar.


curl -s "https://<account>.blob.core.windows.net/<container>?restype=container&comp=list"
```
A 200 with an XML `<Blobs>` enumeration = Container-level anon access = LEAD (same content-sensitivity
gate as S3 public-read). A 403/`AuthenticationFailed` = Private or Blob-level (secure or needs a known
blob name — not a listing win). Source: learn.microsoft.com/en-us/azure/storage/blobs/anonymous-read-access-configure.

## Azure SAS-token exposure — new sub-lane via existing JS-intel/secrets pillar (added 2026-07-28)

Distinct from bucket ACL misconfiguration: a **SAS (Shared Access Signature) token** leaked in
client-side JS, a source-map, or a config file grants direct read/write/delete on a container or blob
regardless of the container's own public-access setting — functionally equivalent to a leaked cloud
credential (our [[project_cognito_unauth_lane]] class). Detection is provenance-confirmed for free
through the same jsintel/jsluice-secrets + trufflehog pipeline already mining each host's JS:
- **Pattern:** `sv=\d{4}-\d{2}-\d{2}&...&sig=[A-Za-z0-9%]+` (SAS query-string signature) or a full
  `?<container-url>?<SAS>` URL embedded in JS/config.
- **Verify (read-only, LEAD not auto-confirm):** `curl -s "https://<account>.blob.core.windows.net/<container>?restype=container&comp=list&<SAS>"` — 200 + listing = live token; check the `se=` (expiry) param
  for a far-future date and the `sp=` (permissions) param for `w`/`d`/`a` (write/delete/add) — those are
  the severity-driving bits, not mere read access.
- Add `sv=` / `sig=` SAS pattern to whatever list feeds jsluice-secrets candidate LEADs; keep it
  review-only same as every other jsluice secret candidate (token-shaped ≠ confirmed-live — must verify
  the listing call succeeds before minting).

## 3. Race conditions — multi-endpoint/partial-construction technique (class-race-conditions.md, currently thin at 32 lines)

The doc covers single-packet HTTP/2 + limit-overrun (coupon/withdraw) races well but is missing the other major class from PortSwigger's "Smashing the State Machine" research: **multi-endpoint** races, where the vulnerable window spans *different* endpoints (not N copies of the same request) — genuinely higher-EV for us since it's far less commonly tested manually (most hunters fire the same request N times; almost nobody fires different requests at each other) and lines up directly with the MOTTO (dup-resistance = crowd doesn't do this).


Requires target support HTTP/2 (`engine=Engine.BURP2` is incompatible with HTTP/1 targets — check ALPN
before assuming this technique applies). Recent Burp builds improved single-packet accuracy for very
small race windows — a target that "didn't race" on an older test may be worth a re-test.
