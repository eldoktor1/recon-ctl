## 1. Web Cache Deception — concrete normalization-discrepancy payload patterns (class-cache-deception)
PortSwigger's 2026 WCD lab set formalizes two exact discrepancy patterns beyond the basic "static-suffix" confusion our lane currently probes — both give a precise payload template `recon_wcd.sh` can add as additional variants (still under our own cache-buster key, never poisoning the real cache).

- **Origin-normalizes, cache-doesn't (dot-segment traversal into a cacheable prefix):** origin resolves `..%2f`, cache treats path by raw prefix match. Payload: `/<cacheable-prefix>/..%2f<sensitive-endpoint>?<cachebuster>` (e.g. `/resources/..%2fmy-account?wcd`) — origin normalizes to `/my-account` and serves the sensitive page, but the cache stores it keyed on `/resources`.
- **Cache-normalizes, origin-doesn't (fragment-delimiter trick):** cache decodes `%23%2f%2e%2e%2f` as `#/../`, resolving into a cacheable directory; origin treats `%23`(`#`)/`%3f`(`?`) as a hard delimiter and stops parsing there, serving only the sensitive base path. Payload: `/<sensitive-endpoint>%23%2f%2e%2e%2f<cacheable-prefix>?<cachebuster>` (e.g. `/my-account%23%2f%2e%2e%2fresources?wcd`). The `%23` matters because browsers never send URL fragments to the server — it's purely a cache-key confusion primitive.

Both are testable unauth (probe under our own cachebuster key, check `X-Cache: HIT` / no-store headers before/after) and fit the existing detect-only doctrine.

Sources: [Exploiting origin server normalization for WCD](https://portswigger.net/web-security/web-cache-deception/lab-wcd-exploiting-origin-server-normalization), [Exploiting cache server normalization for WCD](https://portswigger.net/web-security/web-cache-deception/lab-wcd-exploiting-cache-server-normalization)



## 2. AWS Cognito — self-service privilege-attribute writeback + JWT-signature-skip patterns (class-cognito-unauth)
Two July-2026 AWS Ops Wheel CVEs (CVE-2026-6911, CVE-2026-6912) generalize into fingerprints worth adding to our Cognito lane beyond the identity-pool/unauth-role primitive we already document.

- **CVE-2026-6912 (CVSS 8.8):** the app's Cognito User Pool schema marked a privilege-bearing custom attribute (`custom:deployment_admin`) as user-writable. Any authenticated user calls Cognito's `UpdateUserAttributes` directly (own token, no app-server involvement) and sets the attribute themselves → instant privesc, since the app trusted the Cognito-issued attribute rather than a server-side authorization check. **Generalizes to any app storing role/tier/admin flags as Cognito custom attributes** (`custom:role`, `custom:is_admin`, `custom:tier`, `custom:subscription`) — check the User Pool schema (visible via `aws cognito-idp describe-user-pool` if creds are ever obtained, or infer from JWT claims/JS SDK config) for which custom attributes are `Mutable: true` and callable by the end user, then attempt self-`UpdateUserAttributes` with a privileged value.
- **CVE-2026-6911 (unauth):** a v2 API Gateway custom authorizer for Cognito was not enforcing JWT signature verification, so any unauthenticated caller could forge a token (fill in arbitrary claims, unsigned or garbage signature) and reach admin-gated routes. **Generalizes to any Lambda/API-Gateway custom authorizer** — when jsintel surfaces a Cognito JWT being sent to an API, worth an unauth safe probe: strip/mangle the JWT signature (`alg:none` or a bit-flipped sig) and hit the endpoint with OPTIONS/GET to see if it still 200s (safe, non-destructive discovery of the same authorizer bug class as `class-jwt-attacks.md`'s `alg:none`/key-confusion — this is the Cognito-specific instance of it, worth cross-referencing).

Both need a real target with Cognito wired up as we already fingerprint (pool ID / client ID in JS); worth checking any Cognito-pool host we've already flagged for whether custom attributes are writable and whether the authorizer actually validates signatures (safe/unauth: bad-signature probe only, never state-changing UpdateUserAttributes against a target we don't own).

Sources: [AWS Security Bulletin 2026-018](https://aws.amazon.com/security/security-bulletins/2026-018-aws/), [CVE-2026-6912 — AWS Ops Wheel privesc](https://www.thehackerwire.com/aws-ops-wheel-privilege-escalation-via-cognito-attribute-modification-cve-2026-6912/), [Tenable CVE-2026-6912](https://www.tenable.com/cve/CVE-2026-6912)



## 3. GraphQL mutations as a mass-assignment / over-posting vector (class-graphql)
2026 API-bug-bounty writeups converge on GraphQL mutations as the primary mass-assignment surface — a class our GraphQL lane currently ranks for IDOR/injection but doesn't yet explicitly test for over-posting. Real payout precedent: Shopify H1 report #2207248, $5,000, IDOR via GraphQL `BillingDocumentDownload`/`BillDetails` queries returning cross-tenant billing docs.

Methodology: from the harvested introspection schema (or Clairvoyance field-suggestion recovery when introspection is off), enumerate every mutation's input type fields — not just the fields the app's own frontend actually populates. Fields visible in the schema but absent from the UI's request (e.g. `role`, `isAdmin`, `balance`, `isPremium`, `subscriptionStatus`, `internalNotes`) are candidate over-posting targets: submit the same mutation with those extra fields set to a privileged value and see if the backend silently accepts them because it deserializes the whole input object into the DB model rather than allow-listing fields. This is a **schema-diff** technique (compare schema-declared input fields vs. observed real traffic fields) layered on top of what `recon_graphql.sh` already harvests — no new tooling, just a new ranking signal: input-type fields present in schema but never observed in captured traffic = LEAD for human 2-account mass-assignment test.
