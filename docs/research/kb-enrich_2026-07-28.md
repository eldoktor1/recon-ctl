## 1. GraphQL WebSocket (subscriptions) as an untested injection surface — NEW for us
`recon_graphql.sh` currently only does introspection/`__typename` over HTTP — it never touches the WS transport. A April 2026 writeup ($2,000 bounty, critical) chained IDOR→error-based SQLi over a `/graphql-ws` subscription endpoint: 25-digit numeric doc IDs looked unenumerable, but fuzzing the ID param with junk characters triggered verbose Postgres errors leaking column names (`email`) back in the WS error frame; the researcher then injected the discovered column name into the ID param to force type-conversion errors that reflected real row values, and used `||` string concatenation to pull multiple fields/rows through the same error channel. Confirms our doctrine (injection = human/authed-confirm only) but flags a **new discovery angle**: any host running GraphQL subscriptions is worth a WS-handshake probe even when the HTTP endpoint looks clean, since WS resolvers often skip the same input validation the HTTP layer has.
Source: [IDOR to SQLi in GraphQL WebSocket — DarkyOS](https://medium.com/@DarkyOS/sql-injection-in-graphql-websocket-escalated-to-pii-document-leak-09ba7ad2800a)

## 2. Cognito account-takeover via unverified `email` attribute rewrite — extends our Cognito lane
Distinct from our existing unauth-creds-harvest angle (Amplify config → pool ID → unauth identity). Here, an attacker with ANY valid Cognito access token (own low-priv account) ran:
```
aws cognito-idp update-user-attributes --region <r> --access-token <token> \
  --user-attributes Name=email,Value=<victim-org-domain-email>
```
Because the app used `email` (not `sub`) as the authoritative identity claim and Cognito accepted the attribute write without re-verification gating downstream authz, changing your own email to a target org's domain granted that org's portal access — full account/org compromise from one API call, no phishing. Actionable for our authed-testing flow: when a program uses Cognito, an owned-account authed check should include `update-user-attributes` on `email`/`custom:userId` and check whether the app trusts the new value pre-verification.
Source: [AWS Cognito misconfiguration → full org compromise](https://medium.com/@a-shams/how-an-aws-cognito-misconfiguration-led-to-full-organization-account-compromise-5c9f6983e1a4)

## 3. IDOR: "UUID illusion" + mass-assignment chaining — sharpens our ranker's blind spot
Confirms a gap in `recon_idor_candidates.py`'s scoring model: it currently treats UUID-keyed params as lower-priority ("harvestable" but not "enumerable"), but 2026 writeups show the real technique isn't guessing UUIDs — it's **harvesting leaked UUIDs from referer headers, logs, or sibling API responses**, then testing them for a missing ownership check (UUID complexity ≠ authz). Second pattern: chain a confirmed IDOR with mass-assignment on the same mutation/PATCH body (e.g. `updateProfile(input:{name,email,role})` not filtering `role`/`password`) to escalate a read-IDOR into a write/privesc. Both are still human/2-account-confirm per our hard line, but worth encoding into the ranker's rationale text so operators know to (a) grep crawled responses/JS for UUIDs referencing OTHER objects before dismissing a UUID param, and (b) always retest a confirmed IDOR's mutation body for extra unfiltered fields.
Sources: [BOLA/IDOR 2026 guide — XHack](https://xhack.io/blog/bola-vulnerability-idor-api-guide), [Mass Assignment for bug bounty hunters](https://medium.com/@merida-/mass-assignment-vulnerabilities-in-apis-explained-for-bug-bounty-hunters-1c84c9b06204)
