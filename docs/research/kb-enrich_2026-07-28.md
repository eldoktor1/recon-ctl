## 1. Cognito — authenticated-role privesc via self-signup abuse (new attack path, not in our doc)

Our KB currently only tests the **unauth guest role** (`get-id`/`get-credentials-for-identity` with `--no-sign-request`). NotSoSecure's writeup documents a second, deeper path when the User Pool allows **open self-signup**: register your own account → get an *authenticated* identity-pool role (often more permissive than the guest role) → enumerate/abuse Lambda functions reachable by that role for further privesc.

```
aws cognito-idp sign-up --client-id <app-client-id> --username <you> --password <pw>
aws cognito-idp confirm-sign-up --client-id <app-client-id> --username <you> --confirmation-code <code>
aws cognito-idp initiate-auth --client-id <app-client-id> --auth-flow USER_PASSWORD_AUTH --auth-parameters USERNAME=<you>,PASSWORD=<pw>
aws cognito-identity get-credentials-for-identity --identity-id <id> --logins "cognito-idp.<region>.amazonaws.com/<user-pool-id>=<id-token>"
# then, with the returned ASIA... creds:
aws lambda list-functions
aws lambda get-function --function-name <name>   # env vars often carry more creds
```
This is an **own-account, active-PoC** path (self-signup is authorized own-account setup per our active-PoC doctrine) — distinct from and complementary to the unauth-guest test, and should run as a second stage whenever a pool is found with self-signup enabled and the guest role turns out locked-down (our #1 current FP pattern).

Source: [NotSoSecure — Hacking AWS Cognito Misconfigurations](https://notsosecure.com/hacking-aws-cognito-misconfigurations)

## 2. Amplify legacy `authRole`/`unauthRole` — IAM trust-policy takeover fingerprint (CVE-2024-28056)

Not in our doc: a distinct Cognito-adjacent bug class — IAM role **trust policies** generated by old Amplify CLI (July 2018–Aug 2019) or left behind when auth was later removed (Aug 2019–Jan 2024) lacked the Cognito identity-pool **audience restriction**. Any caller who obtains a valid Cognito identity token (even from an *unrelated* Cognito setup, pre-Apr-2024 patch) could `sts:AssumeRoleWithWebIdentity` into these roles with no extra authz. AWS patched role *creation* in 2024, but pre-existing legacy roles can still be vulnerable same-account. Researchers found **8,000+ public role ARNs** matching the naming pattern.

**Enumerable fingerprint:** role ARNs/names containing `authRole` / `unauthRole` (Amplify's default naming) surfaced via jsintel/`aws-exports.js`/CloudTrail-adjacent leaks — worth a quick `sts assume-role-with-web-identity` probe (own/test identity token) against any such ARN found on an in-scope legacy Amplify app, since it's a config-drift bug that outlives the 2024 platform patch.

Source: [Mallory.ai — AWS Amplify IAM Role Takeover Flaw](https://www.mallory.ai/stories/019e59ea-36a4-79e9-9431-fa3fc572a19d)

---


aws cognito-idp sign-up --client-id <app-client-id> --username <you> --password <pw>
aws cognito-idp confirm-sign-up --client-id <app-client-id> --username <you> --confirmation-code <code>
aws cognito-idp initiate-auth --client-id <app-client-id> --auth-flow USER_PASSWORD_AUTH \
  --auth-parameters USERNAME=<you>,PASSWORD=<pw>
aws cognito-identity get-credentials-for-identity --identity-id <id> \
  --logins "cognito-idp.<region>.amazonaws.com/<user-pool-id>=<id-token>"
# with the returned ASIA... creds, SAFE enumeration only (list_/describe_, no data reads/writes):
aws lambda list-functions
aws lambda get-function --function-name <name>   # env vars sometimes carry further creds
```
Run this as a **second stage** when: (a) self-signup is open on the pool, and (b) the unauth guest role came back locked-down (the #1 current FP). The authenticated role is frequently scoped far more broadly than the guest role, since developers assume "signed in" implies "trusted." Same blast-radius discipline as the unauth path: list/describe only, no object data, note the assumed-role ARN + what it reaches, honest severity.

Source: notsosecure.com/hacking-aws-cognito-misconfigurations

## Amplify legacy authRole/unauthRole trust-policy takeover (CVE-2024-28056, added 2026-07-28)

A distinct, Cognito-adjacent bug: IAM role trust policies generated by **legacy Amplify CLI (Jul 2018–Aug 2019)**, or left over when auth was later removed from a project (Aug 2019–Jan 2024), can be missing the Cognito identity-pool **audience (`aud`) restriction** in their trust policy. Any caller holding a *valid Cognito identity token* — not necessarily from the same pool — could `sts:AssumeRoleWithWebIdentity` into the role with no further authorization, prior to AWS's Apr-2024 STS-level fix for cross-account exploitation. Same-account exploitation risk can persist on unremediated legacy roles.

**Fingerprint:** IAM role ARNs/names following Amplify's default pattern — `*authRole*` / `*unauthRole*` — found via jsintel (`aws-exports.js`, `amplifyconfiguration.json`) on an in-scope host whose Amplify project predates 2024. Worth checking whether the app is still on a legacy-generated role before assuming the 2024 platform patch covers it (patch fixed role *creation*, not existing malformed trust policies).

**Test:** `aws sts assume-role-with-web-identity --role-arn <arn> --role-session-name test --web-identity-token <own-cognito-id-token>` — success with no audience check = confirmed misconfigured trust policy (same list/describe-only blast-radius discipline as the standard Cognito test).
```
