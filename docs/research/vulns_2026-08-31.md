# Research digest — vulns — 2026-08-31

## 1. NEW — Varnish Cache: two auth-bypass/smuggling CVEs — first coverage for our in-scope Varnish hosts ★★
We have `Varnish` in our top in-scope tech list with zero prior KB/digest coverage. Two CVEs matter:
- **CVE-2026-50052 — HTTP/2→HTTP/1.1 request smuggling / auth bypass.** Improper validation of HTTP/2 pseudo-headers/framing during the H2→H1.1 conversion lets a crafted request be interpreted as one request by Varnish but two by the backend → cache poisoning, auth bypass, info disclosure. **Affected:** Varnish Cache < 9.0.3 (Varnish Enterprise "Vinyl Cache" < 9.0.1). **Only exploitable when HTTP/2 support is explicitly enabled** (off by default) — narrows real-world exposure. Published 2026-06-04.
- **CVE-2026-34475 — URL `/`-path canonicalization auth bypass.** CWE-180 (validate-before-canonicalize): unchecked `req.url` handling for HTTP/1.1 requests with a bare `/` path can desync cache-key logic from backend routing → cache poisoning/auth-bypass. **Affected:** Varnish Cache < 8.0.1, Varnish Enterprise < 6.0.16r12. CVSS 5.4 (Moderate). Published 2026-03-27.
- **Detect (unauth, remote):** Varnish rarely exposes its version directly, but check `Via`/`X-Varnish` response headers (some configs leak `Varnish/x.y`) and jsintel/Wappalyzer version strings. HTTP/2 exposure for CVE-2026-50052 is only confirmable by observing whether the origin actually negotiates h2 to the Varnish front (ALPN) — a safe, passive observation, not a probe.
- **Action:** both are LEAD-only per our KEV/version doctrine (config-dependent, no safe exploit primitive to fire) — note any host confirmed running an in-range Varnish version for the operator; don't attempt smuggling/cache-poison PoCs autonomously (destructive/third-party-cache risk).
- **Sources:** [GHSA-m9gq-cmcj-p62x](https://github.com/advisories/GHSA-m9gq-cmcj-p62x), [SentinelOne CVE-2026-50052](https://www.sentinelone.com/vulnerability-database/cve-2026-50052/), [SentinelOne CVE-2026-40396](https://www.sentinelone.com/vulnerability-database/cve-2026-40396/) (DoS via workspace overflow, Varnish 9.0.0, HTTP/1 pipelining — also worth a version-match note)

## 2. NEW — CVE-2026-18431, Avada theme + Fusion Builder — zero-click unauth RCE, published 4 days ago ★★
- **What:** A 6-weakness chain (authz + input-validation + trust-boundary + file-handling) lets an unauthenticated request reach a public endpoint, cross into a privileged Fusion Builder component, and write/execute arbitrary PHP — **no login, no admin interaction required** ("zero-click RCE"). CVSS 9.8.
- **Affected:** Avada theme ≤ 7.16, Fusion Builder (bundled/required plugin) ≤ 3.16. ThemeFusion shipped fixes 2026-08-25 — published 2026-08-27, so this is a live same-week n-day window, same tier as the Elementor Pro/Forminator upload-bypass pattern from the last two digests.
- **Detect (unauth, in-range-verifiable):** Avada is a commercial theme (ThemeDum/ThemeForest, one of the best-selling WP themes) — fingerprint via `wp-content/themes/Avada/style.css` `Version:` header (standard WP theme convention) or the `fusion-builder`/`Avada` strings in jsintel JS bundles.
- **Action:** version-match (Avada ≤7.16 / Fusion Builder ≤3.16) = strong LEAD. Exact endpoint/technique not disclosed in the public writeups yet (responsible-disclosure gap) — don't attempt to reverse it into a live payload; flag for `recon-mood wordpress`/`avada` sweep, operator confirm-then-stop once technical details land.
- **Sources:** [SOCRadar](https://socradar.io/blog/cve-2026-18431-avada-wordpress-rce/), [CyberExperts](https://cyberexperts.com/2026-08-28-critical-avada-wordpress-theme-flaw-enables-zero-click-rce/)

## 3. WATCH — GraphQL WebSocket-subscription endpoint bypasses introspection lockdown (technique, not tied to our stack) ★
Referenced via CVE-2026-32594 (Parse Server): disabling introspection over HTTP is a common hardening step, but the **GraphQL-over-WebSocket subscription endpoint** can sit outside the same middleware stack and still answer introspection queries — the HTTP lockdown gives a false sense of closure. Worth checking on any in-scope GraphQL host: if HTTP introspection 403s/is disabled, still probe the `wss://`/`ws://` subscription endpoint (if discoverable from JS) with a bare `{__schema{types{name}}}` — read-only, fits our existing `recon_graphql.sh` primitive, just a new transport to try. Not urgent enough to build now; noting for `class-graphql.md`.
