## 2. GraphQL alias/array batching = rate-limit bypass engine (`class-graphql.md`)
Distinct from the APQ-safelist bypass already in our KB (2026-08-15 digest) — this is about the rate limiter sitting at the wrong layer (HTTP) while GraphQL executes N independent operations per request.


A `200 OK` with 100 distinct results in one response array — where individual sequential requests
would have hit a 429 — confirms the bypass. This turns a rate-limited enumeration endpoint into an
unthrottled one; relevant to our IDOR-candidate ranker (a numeric-ID `user(id:)`-style query becomes
much higher-EV to test if aliasing works, since the normal per-request throttle doesn't apply).

**Auth/brute-force implication (human-in-the-loop only, own accounts):** the same technique batches
N login/2FA-verify mutations with varying password/code variables in one request; a `sessionToken` in
any one of the N results = successful auth bypass of the rate limiter. This is a HUMAN-driven,
owned-account test per our IDOR doctrine (never against a real target account) — but recon-graphql
should FLAG any unauth-reachable mutation whose args include a credential/OTP-shaped field as a
priority "test alias-batch rate-limit bypass" lead, since it's the highest-severity outcome of this class.

**Detection/testing method:** (1) baseline the target's normal per-request rate limit (watch for
`RateLimit-*` headers or a 429 threshold on sequential single-op requests); (2) send the same N ops
as aliases in one POST; (3) a 200 with N distinct results where N sequential requests would 429 = confirmed.
Read-only recon use (safe): batching plain read queries to enumerate faster is unauth-safe IF the
underlying single-op query is itself unauth-reachable (no new authz boundary crossed) — but batching a
brute-force primitive stays gated to owned-account/human testing per our NEVER-list.
