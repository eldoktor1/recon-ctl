## 3. CDN-fronted origin exposure — concrete discovery + confirm workflow (`class-cdn-origin-bypass`)
Directly relevant given Cloudflare/Cloudflare Bot Management/CloudFront/Varnish dominate our in-scope tech list.


curl -vk --resolve <host>:443:<candidate-ip> https://<host>/cdn-cgi/trace
```
- Through Cloudflare: `/cdn-cgi/trace` returns Cloudflare's own diagnostic metadata (ray ID, colo, etc.).
- Direct-to-origin (bypassed): the same path 404s with NO Cloudflare metadata and no `cf-ray` header — that
  asymmetry is the confirm signal, safe and read-only (one GET, no auth, no state change).
- Cross-check: a malicious-looking payload against the CDN returns a branded Cloudflare 403 (WAF page,
  identifiable server/cf-ray headers); the same payload sent `--resolve`'d direct to the candidate IP either
  reaches the origin unfiltered (403/404 with NO Cloudflare fingerprint = WAF fully bypassed) or times out
  (origin firewalled to Cloudflare's published IP ranges only = secure, note as FP/secure and move on).

**What we do NOT do with a confirmed origin bypass:** this is functionally a WAF/CDN bypass — our own
[[feedback_403bypasser_waf_ban]] doctrine and per-program scope carve-outs apply. Confirming the bypass
with one safe GET is fine; do NOT then run bulk scanning/fuzzing directly against the bare origin (that's
exactly the burn-risk + scope-violation pattern that gets a researcher IP/account banned on programs that
explicitly protect origin infra or ban scanner traffic). The finding IS "origin IP exposed, WAF/rate-limit/
bot-protection fully bypassable" — report that, don't escalate past it. Authenticated Origin Pulls
(client-cert-gated origin, Cloudflare's official mitigation) is the "secure" state — if present, note and
move on, don't try to bypass mTLS.
```
