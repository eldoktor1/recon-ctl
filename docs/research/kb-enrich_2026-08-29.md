## 1. SSRF — concrete filter-bypass payload catalog + a distinct "validate-then-redirect" bypass (`class-ssrf`)

Our doc already covers DNS-rebinding TOCTOU and multi-cloud metadata headers, but has no concrete IP-encoding/parser-confusion payload list, and treats redirect-based bypass as folded into "filter bypass" generically. Two things are worth calling out as distinct from what's already written:

- **Redirect bypass is not the same bug as DNS rebinding** — it's "validate once, follow redirects blindly" (a June 2026 disclosed case in crewAI's scrape tools: the guard checked the original URL, then the HTTP client followed a 30x to an internal/metadata target with zero re-validation). Our doc's DNS-rebinding section could be read as covering this; it doesn't — worth a one-line split so hunters test both independently (does the sink follow redirects at all? does it re-validate the *final* URL, not just the *requested* one?).
- **A real payload catalog** for probing allowlist/blocklist SSRF guards (safe to *test acceptance of*, not to fetch internal data — same OOB-only confirm discipline applies): decimal (`http://2130706433/`), hex (`http://0x7f000001/`, per-octet `0x7f.0x0.0x0.0x1`), octal (`0177.0.0.1`, dotless `017700000001`), short-form (`127.1`), octet-overflow (`127.0.0.257`), IPv4-mapped IPv6 (`[::ffff:169.254.169.254]`), userinfo-injection (`http://allowed.com@169.254.169.254/`), fragment confusion (`http://169.254.169.254#@allowed.com/`), IDNA decorated-unicode digits (`①②⑦.⓪.⓪.①` → `127.0.0.1`), and exotic schemes (`gopher://`, `dict://`) where the app allows non-http(s) schemes at all.

Source: [IntruderLabs — SSRF Bypasses: why each filter-evasion technique works](https://intruderlabs.com.br/en/blog/ssrf-bypass-techniques/), [crewAI issue #6520 — redirect-based SSRF guard bypass](https://github.com/crewAIInc/crewAI/issues/6520).



## 2. JWT — concrete `jku`/`kid` exploitation payloads beyond our current LEAD-only fingerprint (`class-jwt-attacks`)

Our doc flags `jku`/`x5u`/`kid` presence as LEAD-only signals without example payloads for the actual forge step. These are the missing concrete techniques (still gated by our doctrine — forging a working signature is an active-PoC step, own-account, human-in-the-loop, never auto-minted):

- **`kid` SQL injection** — when `kid` indexes a DB lookup for the signing key: `kid: "x' UNION SELECT 'attacker_secret'-- -"` forces the server's key-lookup query to return an attacker-chosen value, which the attacker then uses as the HMAC secret to sign a forged token — bypasses cryptography via the key-*lookup* path, not the algorithm. Time-based confirm variant: `'; WAITFOR DELAY '0:0:5'-- -`.
- **`kid` path traversal** (filesystem-based keystores): `kid: "../../dev/null"` (empty key → forge with empty HMAC secret) or arbitrary-file-read paths.
- **`jku` allowlist bypass tricks** beyond "point it at a domain we control": subdomain-suffix spoofing (`https://allowed.com.evil.com/`), userinfo injection (`https://allowed.com@evil.com/` — some allowlist regexes match the leading host-looking string), and open-redirect-on-the-trusted-domain (`https://allowed.com/redirect?to=https://evil.com/jwks.json`) chaining through a redirect the allowlist never re-checks — same "validate the input, not the final resource" bug family as the SSRF redirect bypass above.

These stay exactly where our doctrine already puts them: fingerprint from already-crawled JS/tokens (no new target traffic) → LEAD → human-owned-account active-PoC to actually forge and use a signature.

## 3. AWS Amplify legacy trust-policy takeover — a Cognito sub-lane our doc doesn't cover (`class-cognito-unauth`)

Distinct from the "unauth guest role over-permissioned" primitive our doc already documents in depth: **CVE-2024-28056** — Amplify CLI (July 2018–Aug 2019 vintage projects) generated IAM trust policies for `authRole`/`unauthRole` **missing the Cognito identity-pool audience condition**, so `AssumeRoleWithWebIdentity` via Cognito Basic authflow + STS can assume the role **without the intended scoping to that specific identity pool** — and critically, the over-permissioned role often survives as a dormant "backdoor" even after the project's auth was later removed. AWS patched Amplify tooling Jan–Apr 2024 (new deployments are safe), but this only prevents *new* vulnerable policies — old dormant projects are unaffected by the fix. Detection is fully passive/safe: `authRole`/`unauthRole`-pattern ARNs are internet-scale enumerable (8,000+ found by researchers), and confirming exploitability just extends our existing unauth Cognito test (`get-id`/`get-credentials-for-identity`, no `--logins`) — the finding is the **missing audience restriction in the trust policy**, not a new probe primitive. Worth adding as a specific thing to check on any Cognito pool we already have provenance for, especially older/legacy-looking Amplify configs (predates 2019 in the JS bundle's build metadata is a cheap tell).

Source: [Mallory — AWS Amplify IAM Role Takeover Flaw Exposed Cognito-Linked Roles](https://www.mallory.ai/stories/019e59ea-36a4-79e9-9431-fa3fc572a19d). ⚠️ CVE-2024-28056 is from 2024 (already fixed for new Amplify deployments) — this is a *legacy-config* lead, not a fresh 0-day; NVD-verify the CVE ID before citing it in any report, and confirm the target project predates the 2024 fix before treating a hit as more than a lead.
