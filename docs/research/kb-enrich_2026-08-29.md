## 1. Cognito — the *other* Cognito bug: authenticated privesc via writable custom attributes + enumeration bypass (`class-cognito-unauth.md`)
Our doc only covers unauth **Identity Pool** credential issuance. Two adjacent, dup-resistant **User Pool** primitives are worth capturing in the same file (clearly flagged as a distinct attack surface) since we already harvest pool config from JS/sourcemaps:
- **Custom-attribute write privesc:** Cognito custom attributes (`custom:role`, `custom:tier`, `custom:org_id`, …) default to **mutable (write-enabled)** unless the developer explicitly locks them read-only in the App Client's attribute permissions. An authenticated user can call `update-user-attributes` / `UpdateUserAttributes` and set `custom:role=admin` directly — classic mass-assignment, but Cognito-specific and easy to miss because it's a *default*, not a coding bug. PoC: `GetUser`/`InitiateAuth` response to enumerate which custom attrs exist on your own token, then `aws cognito-idp update-user-attributes --access-token <own-token> --user-attributes Name="custom:role",Value="admin"` — own-account only, exactly our ACTIVE-PoC doctrine (prove then stop). — [secforce.com](https://www.secforce.com/blog/aws-cognito-pitfalls-default-settings-attackers-love-and-you-should-know-about/)
- **Enumeration-protection bypass via SignUp:** `prevent_user_existence_errors` only normalizes errors on `InitiateAuth`/login flows — it does **not** cover the `SignUp` endpoint, so attempting to register an already-existing email still returns a distinguishing error (`UsernameExistsException`) even when the pool is "hardened" against enumeration on login. Safe, unauth, single-request check. — [hackingthe.cloud: Bypass Cognito Account Enumeration Controls](https://hackingthe.cloud/aws/enumeration/bypass_cognito_user_enumeration_controls/)



## 2. JWT — 2026 CVE cluster confirms `alg` confusion is still live + concrete `kid` injection PoC payloads (`class-jwt-attacks.md`)
Our doc already flags `alg` swap and `kid` misuse as LEAD-grade signals but has no concrete PoC payloads or the current CVE evidence that this class is still actively shipping in 2026. Adding both:
- **Case-variant `alg:none` bypass** (`nOnE`, `NoNE`, `NONE`) defeats naive string-match denylists that only block the literal `none`.
- **CVE-2026-34950 (fast-jwt, Node)**: an "incomplete fix" regex used a *starting anchor* to detect RSA public keys before allowing HS256 verification against them; prefixing the key material with leading whitespace (space/tab/newline) defeats the regex, re-opening RS256→HS256 confusion in a library that had already patched it once. — [thehackerwire.com](https://www.thehackerwire.com/fast-jwt-algorithm-confusion-re-enabled-cve-2026-34950/), [securityonline.info](https://securityonline.info/fast-jwt-authentication-bypass-cve-2026-34950-whitespace/)
- **CVE-2026-22817 (Hono, TS/JS, CVSS 8.2)** and **CVE-2026-23993 (HarbourJwt, Go)**: same RS256→HS256 / unknown-algorithm-acceptance bug class shipping across languages in 2026 — this is not a legacy-library-only issue.
- **CVE-2026-23552 (Keycloak)**: missing `iss` claim validation let cross-realm tokens be accepted — relevant to any multi-tenant Cognito/Auth0/Keycloak setup we hit; worth an explicit "does the app validate `iss` per-tenant" check.
- **Concrete `kid` PoC payloads** (path traversal / SQLi) — file-backed key lookup: forge with `kid: ../../../../../../../dev/null` + JWK `k: AA==` (base64 for a single zero byte) so the empty file becomes the HMAC secret and the forged signature validates; DB-backed key lookup: inject SQL into `kid` to force the query to return an empty/known string, sign HS256 with that same string. — [Invicti: kid path traversal](https://www.invicti.com/web-application-vulnerabilities/jwt-signature-bypass-via-kid-path-traversal), [Invicti: kid SQLi](https://www.invicti.com/web-application-vulnerabilities/jwt-signature-bypass-via-kid-sql-injection)
