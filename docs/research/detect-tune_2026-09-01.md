# Research digest — detect-tune — 2026-09-01

## 1. Nginx CVE-2026-42926 (HTTP/2 desync via proxy) — version range directly hits our fingerprinted `Nginx:1.29.7` (HIGH PRIORITY — feeds `tech-nginx.md` + `class-request-smuggling.md`)
- **What:** HTTP/2 request injection in `ngx_http_proxy_module` — when `proxy_http_version 2` is set **and** `proxy_set_body` is used, an attacker-controlled request body can inject raw HTTP/2 frame bytes into the traffic NGINX forwards upstream, desyncing NGINX from the upstream peer. CVSSv3.1 5.8 (medium).
- **Affected:** **1.29.4 – 1.30.0**. Fixed 1.31.0+ / 1.30.1+.
- **Why it matters to us:** our own top-tech list already fingerprints `Nginx:1.29.7` in-scope — that version sits *inside* the vulnerable range. This is a direct, ready-to-run version-gate for `recon_nday.sh`: any host whose `Server:`/error-page banner reads `nginx/1.29.4`–`nginx/1.30.0` is an in-range candidate.
- **Confirm primitive / doctrine fit:** the vulnerable config (`proxy_http_version 2` + `proxy_set_body`) is server-side and NOT remotely visible — so a version match alone is a **LEAD, never P0** (same KEV-unverified-version clamp we already apply everywhere). The only way to move it to CONFIRMED is an actual HTTP/2 desync differential probe (inject a crafted body and observe cross-request bleed on a second concurrent request) — that's active smuggling exploitation, which stays out of the unattended pipeline; treat as an operator-reviewed n-day candidate, not an auto-probe.
- Sources: [nginx.org security advisories](https://nginx.org/en/security_advisories.html), [SentinelOne CVE-2026-42926](https://www.sentinelone.com/vulnerability-database/cve-2026-42926/), [F5 K000161131](https://my.f5.com/manage/s/article/K000161131)

## 2. Nginx CVE-2026-42055 (heap overflow, HTTP/2 proxy + gRPC modules) — version range unresolved between sources, flag ⚠️ before minting (feeds `tech-nginx.md`)
- **What:** heap buffer overflow in `ngx_http_proxy_v2_module`/`ngx_http_grpc_module` when HTTP/2 proxying (`proxy_http_version 2` or `grpc_pass`) is combined with `ignore_invalid_headers off` and `large_client_header_buffers` set above 2 MB per buffer. CVSSv3.1 8.1 / CVSSv4 9.2 — reliable worker-crash DoS, RCE possible without ASLR.
- **Affected:** sources disagree — ZeroPath's writeup says mainline 1.31.1 (fixed 1.31.2) + stable 1.30.0–1.30.2 (fixed 1.30.3); an nginx.org advisory summary said 1.13.10–1.31.1 (fixed 1.31.2+/1.30.3+), which would also cover our `1.29.7`. ⚠️ **NVD-verify the exact range before treating any 1.29.x host as in-range** (per our doctrine on LLM-search CVE hallucination risk) — but if the broader range holds, this is a second hit on our own fingerprinted version.
- **Detection:** version-gate only; no safe unauth trigger (requires the 3-directive combo above, which is not remotely observable) — LEAD at most, same as #1.
- Sources: [ZeroPath CVE-2026-42055](https://zeropath.com/blog/cve-2026-42055-nginx-http2-heap-buffer-overflow), [Penligent CVE-2026-42055](https://www.penligent.ai/hackinglabs/cve-2026-42055/), [nginx.org security advisories](https://nginx.org/en/security_advisories.html)

## 3. Cloudflare Pingora — 3 new request-smuggling CVEs + a cache-poisoning CacheKey collision, but ONLY exploitable on **self-hosted** Pingora, not Cloudflare's own edge (feeds `class-request-smuggling.md` + `class-cdn-origin-bypass.md`)
- **What:** independent researcher found 3 request-smuggling bugs (CVE-2026-2833, CVE-2026-2835, CVE-2026-2836) and 1 cache-poisoning bug in Cloudflare's open-source Pingora reverse-proxy framework, all exploitable under **default config**. Root causes: (a) Pingora switched to passthrough mode on an `Upgrade` header *before* the backend confirmed with `101 Switching Protocols`, letting a smuggled second request ride the upgraded connection straight to the backend; (b) non-RFC-compliant HTTP/1.0 handling — close-delimited bodies + mishandled `Transfer-Encoding: chunked`; (c) the default `CacheKey` for the alpha proxy-caching feature hashed only the URI **path** — no `Host` header, no upstream scheme — so two different hosts requesting the same path could poison each other's cached response. Fixed in **Pingora 0.8.0**.
- **Why it matters / caveat:** Cloudflare's *own* CDN edge sits behind extra architectural layers that block exploitation, so this is **not** a lever against Cloudflare-fronted targets in general. It matters for the (growing) set of companies that vendor Pingora themselves as their own reverse proxy / API gateway (Rust shops, anyone who adopted the OSS crate) — a distinct, dup-resistant target class since almost nobody is fingerprinting for "is this proxy Pingora" yet.
- **Detection reality check:** Pingora has **no distinctive default `Server:` banner** — deployments commonly rewrite/strip it (the crate's own docs highlight header-rewriting as a selling point), so blind banner-grabbing is unreliable. Better signals: (1) leaked build artifacts referencing the `pingora`/`pingora-proxy`/`pingora-core` Rust crate (Cargo.lock in a public repo, error-page stack trace, `/debug`-style endpoint) — feeds our existing GitHub-leak lane; (2) behavioral: a host that upgrade-switches to passthrough on a bare `Upgrade:` header before any `101` response is a strong signal, but confirming it means sending a live smuggling PoC — active exploitation, so treat any positive as CONFIRMED-primitive per our transition-gate `ALWAYS_MINT` class (like `auth-bypass`/`wcd-purge`), not a state to suppress on repeat sighting.
- Sources: [Cloudflare blog — Fixing request smuggling in Pingora OSS](https://blog.cloudflare.com/pingora-oss-smuggling-vulnerabilities/), [GitHub advisory GHSA-93c7-7xqw-w357](https://github.com/cloudflare/pingora/security/advisories/GHSA-93c7-7xqw-w357), [cybersecuritynews.com summary](https://cybersecuritynews.com/cloudflare-pingora-vulnerabilities/)
