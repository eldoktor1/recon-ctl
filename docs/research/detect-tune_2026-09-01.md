## 1. Safe single-request timing primitive for HTTP desync confirm — closes the gap our own KB flagged (HIGH PRIORITY, feeds `class-request-smuggling.md`)
Our `tech-nginx.md` already notes CVE-2026-42926 (HTTP/2→upstream desync) is "the most promising for a future safe differential-probe design" but no primitive exists yet. James Kettle's "HTTP/1.1 must die: the Desync Endgame" (PortSwigger, 2025) formalizes exactly this: a **parser-discrepancy scan** that finds smuggling-capable configs from response **timing/behavior on a single crafted request** — not a two-request victim-impacting exploit. The specific technique for the "0.CL" class (front-end treats `Content-Length` as implicitly 0, back-end doesn't): send one request with an ambiguous body-framing; a real discrepancy manifests as the origin **timing out / hanging** waiting for bytes that never arrive (a deadlock, not data leakage) — this is detectable and non-destructive if capped with a short client-side timeout and never followed by a second "smuggled" request.
- **Actionable, non-destructive confirm design:** for a host flagged version-in-range for CVE-2026-42926 (Nginx, `proxy_http_version 2`+`proxy_set_body`) or CVE-2026-50052 (Varnish HTTP/2 desync): send ONE probe with a deliberately malformed/ambiguous framing, cap wait at ~3-5s, classify: fast-clean-response = likely not vulnerable / proxy normalizes; hang-then-timeout or an anomalous partial/garbled response = parser-discrepancy LEAD (still not P0 — no other user's traffic is touched, so this stays a LEAD needing operator judgment call, but it's a real signal beyond "version in range").
- **Source:** [portswigger.net/research/http1-must-die](https://portswigger.net/research/http1-must-die), [portswigger.net/blog/http-1-1-must-die-conquering-the-0-cl-challenge](https://portswigger.net/blog/http-1-1-must-die-conquering-the-0-cl-challenge)

## 2. CVE-2026-40460 (Nginx HTTP/3 IP-spoofing) — the exploitation mechanism is an ACL/rate-limit BYPASS, not just DoS; our KB only had the version range (feeds `tech-nginx.md`)
Already in our KB as a bare version-range row (1.25.0–1.30.0, our `nginx:1.29.7` fingerprint is in-range) but without the mechanism. Confirmed: NGINX's QUIC/HTTP-3 handling can trust a **source IP asserted inside the QUIC layer without validating it against actual connection state** (UDP has no handshake to bind it to) — so IP-based allowlists, geo-restrictions, and rate-limiting keyed on "client IP" can be bypassed on HTTP/3-enabled Nginx in the vulnerable range. This is a genuine access-control bypass class, not cosmetic — relevant to us because IP-gated admin/internal endpoints are exactly what we look for.
- **Safe detection (passive, no spoofing sent):** `curl -sI https://<host> | grep -i alt-svc` → `h3` present = HTTP/3 enabled; combine with `Server: nginx/1.25–1.30.0` = in-range LEAD. Actual exploitation requires crafting spoofed-source QUIC datagrams — that's active IP-spoofing traffic, stays operator-reviewed/out of the unattended pipeline (same doctrine as the 42926 desync above — confirming it for real risks looking like an attack on the target's own controls).
- **Source:** [SentinelOne CVE-2026-40460](https://www.sentinelone.com/vulnerability-database/cve-2026-40460/)
