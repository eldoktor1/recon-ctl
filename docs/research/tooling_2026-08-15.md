# Research digest — tooling — 2026-08-15 (pass 4)

## Tooling Watch

### 1. AuthProbe (jbarach2012/AuthProbe) — **EVALUATE, high priority**
- **What it is:** Fresh (arXiv preprint July 22 2026, repo pushed same window) black-box BOLA/IDOR scanner. Drives tests off an **OpenAPI spec** + **2+ operator-controlled identities**: (1) auto-detects object-returning resources from the spec, (2) discovers what each identity legitimately owns via collection endpoints, (3) attempts cross-identity reads, (4) confirms a leak by diffing against a ground-truth fetch by the true owner, plus supplementary checks for enumerable IDs / missing auth.
- **Why it matters:** this is a byte-for-byte match to our locked SOP (`feedback_authed_idor_burp_flow` — "A/B sessions → shared anchor → IDOR enumerate-then-differential, owned-ids only → verdict after full matrix") — currently done by hand via Claude-in-Chrome/Burp. AuthProbe could **mechanize the enumerate+differential step** once we have 2 owned accounts and an OpenAPI/Swagger spec (which our `recon-graphql`/jsintel/autoswagger lanes already surface for many targets).
- **Safety fit:** hard-codes the authorization gate itself — refuses non-local targets unless `--i-have-authorization` is passed. Matches our doctrine (in-scope+authorized+2-owned-accounts, never guessed third-party IDs) rather than fighting it.
- **Maturity:** young (145 stars, Apache 2.0, single-author academic release) — not battle-tested at our scale yet, and it needs a real OpenAPI spec (many of our targets don't publish one; would need to pair with autoswagger/kiterunner-derived specs).
- **Verdict: EVALUATE** — trial it on ONE target where we already have 2 owned accounts + a real OpenAPI spec (e.g. a `tool-autoswagger`-mined host) before wiring it into the authed flow. Do not let it auto-run against live targets — same human-in-the-loop gate as everything else in that lane.
- Sources: [arXiv 2607.20574](https://arxiv.org/html/2607.20574v1), [github.com/jbarach2012/AuthProbe](https://github.com/jbarach2012/AuthProbe)

### 2. GraphCrawler (gsmith257-cyber/GraphCrawler) — **SKIP (archived/dead)**
- Was the closest GraphQL-testing peer to our `recon_graphql.sh` (introspection→schema reasoning, Clairvoyance field-suggestion fallback when introspection is off — same technique we already use). **Repo archived (read-only) 2025-08-23** — no further updates coming. Confirms our native `recon_graphql.sh` is the right call over adopting a third-party GraphQL toolkit; nothing else in this search (InQL, graphql-scanner, BatchQL) offered a capability we lack.
- Source: [github.com/gsmith257-cyber/GraphCrawler](https://github.com/gsmith257-cyber/GraphCrawler)

### 3. Cache-poisoning scanners (toxicache, autoPoisoner, WCPVS) — **SKIP (redundant)**
- All three are narrower than **WCVS**, which we already run (9 techniques incl. unkeyed-header/param poisoning, parameter cloaking, fat GET, HMO/HMC/HHO, request-smuggling-adjacent checks) and is purpose-built with a crawler + cache-adaptive testing. No capability gap found.
- Sources: [toxicache](https://github.com/xhzeem/toxicache), [autoPoisoner](https://github.com/Th0h0/autopoisoner), [WCVS](https://github.com/Hackmanit/Web-Cache-Vulnerability-Scanner)

### 4. JS endpoint/secret extractors (JSHunter, Extractify, Whispers) — **SKIP**
- Generic regex-based extractors; none demonstrate AST-level parsing (jsluice's edge) or verified-credential validation superior to trufflehog `--only-verified`. No clear upgrade path found this pass — not worth displacing the current jsluice+trufflehog combo.
