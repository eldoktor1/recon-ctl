# Research digest — vulns — 2026-09-11

## 1. NEW — CVE-2026-76581, WPMU DEV Dashboard — unauth admin-session forgery via SSO HMAC canonicalization confusion ★★
- **What:** Two unauthenticated AJAX actions (`wdpsso_step1`, `wdpsso_step2`) are supposed to jointly validate an HMAC over SSO params. Step 1 signs/discloses an **unseparated concatenation** of `token+state+redirect+domain`; step 2 verifies a **different concatenation that omits `domain`** — the signature-canonicalization mismatch lets an attacker take a signature legitimately obtained from step 1 and replay it against step 2 to forge a fully authenticated **administrator** session. Different bug class from the file-upload-bypass run this month (Elementor/Forminator/WPvivid) — this is HMAC/signing-string confusion, same family as JWT `alg`/canonicalization bugs.
- **Prerequisite:** site must be connected to the **WPMU DEV Hub with Hub SSO enabled and mapped to an admin account** — narrows exposure but is common on WPMU-DEV-managed agency sites.
- **Affected:** WPMU DEV Dashboard ≤ 5.0.1. Fixed in **5.0.2** (released 2026-08-24, vendor acked 2026-08-21). CVSS 9.8.
- **Detect (unauth, in-range-verifiable):** fingerprint via `wpmudev-updates`/`wpmudev-dash` plugin readme or jsintel string; SSO-enabled state not remotely visible.
- **Action:** don't autonomously replay step1→step2 — the outcome is a forged admin session, i.e. account takeover, same authorization-gate as the Kirki reset-confusion bug (2026-08-15 digest). Flag for `recon-mood wordpress` sweep, hand to operator to confirm-then-stop.
- **Sources:** [WPScan](https://wpscan.com/vulnerability/c09f0c03-da61-4e3e-b45c-54426b2d7824/), [IONIX](https://www.ionix.io/threat-center/cve-2026-76581/)

## 2. WATCH — CVE-2026-34356, Apache HTTP Server mod_proxy_http cookie-rewrite heap overflow — touches our actual top-tech (Apache) but config-gated
- **What:** Heap-based buffer overflow in the `Set-Cookie` `Domain=`/`Path=` rewriting logic used by `ProxyPassReverseCookieDomain`/`ProxyPassReverseCookiePath`. Only reachable on hosts configured as a **reverse proxy with cookie rewriting enabled** — not visible remotely, and a crash primitive (DoS/potential RCE), not a safe unauth confirm.
- **Detect:** `Server: Apache/x.y.z` header; exploitability itself is invisible without config knowledge. Version-in-range only ⇒ LEAD per our KEV-tech-class doctrine — same treatment as the AJP connector CVEs from the same wave (CVE-2026-28780/33857/34032/34059, which need direct AJP-port access, typically not externally exposed — only relevant if a portscan shows 8009 open on an in-scope host).
- **Action:** do not probe. Note any in-scope Apache host actually behind a reverse-proxy cookie-rewrite config as a version-match LEAD only; not independently actionable this cycle.
- **Source:** [SentinelOne](https://www.sentinelone.com/vulnerability-database/cve-2026-34356/)

## Reusable technique — GraphQL alias-batching for IDOR/BOLA enumeration (adds to our reasoning-only ranker, not a new probe)
Recurring pattern across 2026 disclosed reports: send a single GraphQL query with **N aliased copies of the same object-fetch field**, each with a different ID (`a0: user(id:1){...} a1: user(id:2){...} ...`). This turns a rate-limited per-request IDOR guess into one batched request, and — more usefully for us — the **response shape reveals which IDs return real objects vs null/error**, which is exactly the object-ref surface `recon_idor_candidates.py`/`recon_graphql.sh` already rank. Fits our doctrine as a REASONING aid for scoring GraphQL IDOR candidates (does the schema expose a field taking an ID arg that supports aliasing = higher worklist rank) — not something to auto-fire (batch-querying live IDs is still the human 2-account-confirm step).


{ a0: user(id:"1"){id name email} a1: user(id:"2"){id name email} a2: user(id:"3"){id name email} }
```
This is a scoring signal for `recon_idor_candidates.py`/`recon_graphql.sh`, not an auto-probe:
- a field that (a) takes a bare ID arg, (b) returns PII/financial fields, and (c) is reachable
  without auth or with only session auth (no per-object ownership check visible in the schema)
  should rank HIGHER because alias-batching makes exploitation trivially efficient for whoever
  tests it — i.e. it is a stronger real-world IDOR candidate, not just a theoretical one.
- Do NOT alias-batch against live/enumerated third-party IDs ourselves — this is a ranking
  heuristic for the worklist; actual confirmation stays a human 2-owned-account test per doctrine.
- Rate-limit note for the eventual human test: batching many aliases in one request bypasses
  simple per-request rate limits on some backends — worth a line in the operator's confirm
  instructions when handing off a GraphQL IDOR lead.
```
