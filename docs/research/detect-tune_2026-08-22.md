## 1. Spring Boot CVE-2026-40976: env values are MASKED in 4.0 — re-prioritize `recon_actuator_chain.py` toward heapdump (HIGH PRIORITY, directly tunes our actuator chain lane)
New clarification on the CVE we already track (`CVE-2026-40976.yaml`): **Spring Boot 4.0 changed the default `Sanitizer` to redact ALL `/actuator/env` property *values* to `******` regardless of property name** — not just known-sensitive keys as in older Spring Boot. So on a confirmed-vulnerable 4.0.0–4.0.5 host, `/actuator/env` now leaks only **key names / config structure** (recon-grade), not the DB passwords/cloud keys our CHAIN-TO-IMPACT law wants recovered. `/actuator/heapdump` is **not** subject to the Sanitizer at all — it's the only endpoint on 4.0.x that still yields actual in-memory credentials.
- **Actionable**: in `recon_actuator_chain.py`, treat a Spring Boot **4.0.x** host's `/env`-only hit as a LEAD (structure disclosure), not a credential recovery — only mint CONFIRMED off `/heapdump` (or `/configprops` if it still echoes real values pre-4.0) for 4.0.x targets. Pre-4.0 Spring Boot keeps the old behavior (named-key redaction only) so `/env` can still yield real secrets there — version-gate the severity logic.
- **Heapdump extraction patterns** (from a working writeup): search extracted HPROF strings with targeted patterns rather than blind grep — `AKIA` (AWS access key ID prefix), `ey` (JWT prefix, then validate 3-segment b64), DB-driver keywords (`postgres`, `jdbc:`, `mongodb://`). Matches our existing `engine/impact.py` `scan_secrets` approach; worth adding these as explicit heapdump-specific candidate patterns since HPROF binary noise makes plain regex noisier than text config.
- Sources: [GitHub vulnerability-lookup#379](https://github.com/vulnerability-lookup/vulnerability-lookup/issues/379), [spring.io CVE-2026-40976](https://spring.io/security/cve-2026-40976/), [HeroDevs writeup](https://www.herodevs.com/blog-posts/cve-2026-40976-spring-boot-4-0-actuator-authorization-bypass), [heapdump extraction technique](https://a6z.co/exploiting-exposed-spring-boot-heapdump-endpoint)



## 2. Cloudflare `cf-mitigated: challenge` header — authoritative, zero-ambiguity signal for our edge-vs-app block classifier (feeds the 2026-08-20 burn-trap fix)
Confirmed from Cloudflare's own docs: when a Challenge Page (managed/interactive/JS challenge) fires, the response carries `cf-mitigated: challenge` — this is the *only* value it ever takes, present across all challenge-page types, and it is Cloudflare's own documented mechanism for callers to detect a challenge deterministically (vs guessing from body text). This directly strengthens `safe_probe_worker.py`'s `block_source: edge` vs `app` classification added 2026-08-20: a response carrying this header is unambiguously an edge-layer block the origin app never saw, regardless of status code (403/429/503) or body branding — a stronger signal than the current heuristic (branded page + no app fingerprint). A 429 with **no** `cf-mitigated` header is more likely genuine app/origin rate-limiting, not edge triage.
- **Actionable**: in `safe_probe_worker.py`'s edge-classifier, check for the `cf-mitigated` response header first (any value) and classify as `edge` unconditionally when present — cheaper and more reliable than body/branding heuristics, and removes false "app blocked us" classifications that would otherwise trip the full 900s circuit-breaker instead of the short edge cooldown.
- Source: [Cloudflare docs — Detect a Challenge Page response](https://developers.cloudflare.com/cloudflare-challenges/challenge-types/challenge-pages/detect-response/), [Cloudflare Challenges reference](https://developers.cloudflare.com/waf/reference/cloudflare-challenges/)
