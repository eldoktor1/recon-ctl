## 1. GraphQL Relay `node(id:)` field bypasses per-operation authz checks — generic technique, applies beyond the CVE it was found in (HIGH PRIORITY — new confirm primitive for `recon_graphql.sh`, feeds `class-graphql.md`)
Two independent 2026 disclosures show the same root cause: any GraphQL server implementing the **Relay Global Object Identification spec** (the standard `node(id: ID!): Node` root field, used far beyond the frameworks named in the CVEs — GitHub GraphQL API, Shopify Storefront API, Apollo Federation gateways, and any Relay-compliant schema commonly expose it) can have security/authz rules wired onto the *named* query (`book(id:)`, `user(id:)`) while the *generic* `node(id:)` resolver fetches the same underlying object with **no authz check at all**, because it resolves purely off the opaque global ID without re-running the field-level permission logic.
- **api-platform/core / api-platform/graphql — CVE pending (GHSA-cg3c-245w-728m)**: PoC is exactly this swap —
  `query { book(id:"/books/1"){title} }` (checked) vs `query { node(id:"/books/1"){ ... on Book { title } } }` (bypassed, returns any entity to anyone). Fixed 4.0.22 / 3.4.17; affected <4.0.21 / <3.4.16.
- **Actionable — add to `recon_graphql.sh` schema-reasoning step**: after introspection, check if root `Query` exposes a `node(id: ID!): Node` field (or `nodes([ID!]!)`). If so, and the schema ALSO has authz-gated named queries returning the same GraphQL types, that's a LEAD: attempt `node(id:"<global-id-of-a-normally-protected-object>")` — but per our hard line this stays **read-only + reasoning-only** unless the ID is one we OWN (2-owned-account IDOR discipline still applies; global IDs are typically base64 of `Type:id`, easy to construct from a type name + numeric/uuid seen elsewhere in the app). Global-ID format itself (`base64("Book:1")`-style) is a useful ES full-text/JS-intel signal to hunt for even before hitting `node`.
- **Hasura CVE-2026-54698 (GHSA-r27x-gc74-qmxh, CVSS 7.7)**: separate but same theme — row-level permissions scoped by role can be defeated via a `where` clause filtering on a **computed field**, letting a caller brute-force protected row values the RLS was meant to hide. Affects Hasura GraphQL Engine <2.49.2 (and 2.45.x <2.45.5) — version-gate as an n-day LEAD (Hasura is one of the two engines our own doctrine already names as introspection-on-by-default).
- Sources: [github.com/api-platform/core/security/advisories/GHSA-cg3c-245w-728m](https://github.com/api-platform/core/security/advisories/GHSA-cg3c-245w-728m), [GHSA-r27x-gc74-qmxh (Hasura)](https://github.com/hasura/graphql-engine)
