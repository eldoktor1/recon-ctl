# Research digest — vulns — 2026-09-05

## 1. NEW — HTTP/2 framing WAF-bypass techniques (multi-proxy research) — general class, testable now, extends our existing bypass KB ★★
- **What:** A CTBB Labs study of 6 reverse-proxy+WAF stacks found HTTP/2-frame-level gaps that let a malicious body slip past inspection while the backend app still processes it in full:
  - **Body-timing race** (out-of-process WAFs, e.g. HAProxy+Coraza SPOA): the WAF inspects at HEADERS-frame arrival, before DATA; delaying the DATA frame gets the request pre-approved with an empty body, then the real payload lands uninspected.
  - **Body-size-limit gap**: WAF inspection buffers cap around 64KB — pad the payload with junk before the real content so it lands past the inspected window.
  - **Content-Type gap**: ModSecurity's `REQUEST_BODY` var (Apache mod_security2, Caddy+Coraza) only parses `form-urlencoded`; the identical payload as `application/json` sails through unfiltered. **Nginx+libmodsecurity3 was immune to every tested bypass** — a useful negative baseline.
  - **Extended-CONNECT method conversion** (RFC 8441): H2→H1 translation rewrites CONNECT to GET, defeating method-based ACLs.
  - **Path-normalization gap**: rules matched against the *encoded* path (`/.env` blocked, `/%2eenv` not) on engines that don't decode-before-match.
- **Relevance:** directly extends our `class-403-bypass` / `class-cdn-origin-bypass` KB with concrete, safe, black-box test steps (not just "try more 403-bypass headers"). Apache (mod_security2 JSON gap) is one of our top in-scope tech entries.
- **Safe test (unauth, non-destructive):** fingerprint the fronting proxy (`Server:`/error-page signature), send a known-blocked pattern (e.g. `{"cmd":"../../etc/passwd"}`) as both `application/x-www-form-urlencoded` and `application/json` and diff the response code — a 403→200 flip on the JSON variant is a genuine WAF-inspection gap, zero exploitation needed to prove it (the "finding" would still need a real payload that does something on the backend to be reportable, per PoC-OR-GTFO — a bare bypass alone is Info-only).
- **Source:** [CTBB Labs — H2 WAF Bypasses](https://lab.ctbb.show/research/h2-WAF-Bypasses)



## 2. NEW — AWS WAF HTTP/2 multi-frame body-inspection bypass, CVE-2026-13762 (CloudFront, already fixed server-side) + CVE-2026-13763 (ALB, needs customer reconfig) — direct match to our top-tech Amazon CloudFront
- **What:** A crafted multi-frame HTTP/2 request causes AWS WAF to inspect only part of the request body, letting a malicious payload in the uninspected remainder reach the origin uninspected — same bug family as item #1 above, AWS-specific.
- **Status:** **CVE-2026-13762 (CloudFront)** — AWS remediated this server-side; no customer action, so not testable/actionable against CloudFront-fronted hosts anymore. **CVE-2026-13763 (Application Load Balancer)** — fix requires the *customer* to reconfigure how their ALB's WAF inspects HTTP/2 bodies; unpatched-by-default until they do, so this is a live testable gap on any in-scope host sitting behind an **ALB** (not raw CloudFront) with AWS WAF attached.
- **Detect/confirm (unauth, safe):** identify ALB-fronted (not pure CloudFront) in-scope hosts (response headers/cert chain), then run the content-type/body-padding differential from item #1 against the WAF — a bypass confirms the host hasn't applied AWS's recommended ALB WAF reconfiguration.
- **Action:** LEAD until an actual payload lands past the WAF and demonstrates real impact (XSS/SQLi/etc reaching the app unfiltered) — bare bypass alone is Info, not reportable.
- **Source:** [AWS Security Bulletin 2026-048](https://aws.amazon.com/security/security-bulletins/2026-048-aws/)

## 3. WATCH-ONLY — "CDN Tsunami" HTTP/3→HTTP/1.1 amplification DoS — matches our top-tech HTTP/3, but no safe PoC exists (destructive/DoS)
- **What:** QPACK header-compression + H3 multiplexing let a small client request expand into up to 350x the bandwidth/connections at the origin when a CDN translates HTTP/3 down to HTTP/1.1 backend. Confirmed against Cloudflare, CloudFront, Fastly, Alibaba, Baidu, Tencent (Cloudflare immune to the connection-amplification variant only, via request buffering).
- **Status:** No CVE assigned, no known ITW exploitation, mitigations are CDN-edge-side (dynamic-table caps, request buffering) — nothing to fix or test at the origin.
- **Action:** **DO NOT fire** — this is a volumetric DoS primitive against shared CDN infrastructure, explicitly excluded by our NEVER-list (no DoS, no third-party harm). No safe detection primitive exists either (amplification only observable by actually sending the flood). Noted for awareness only; skip in the worklist.
- **Source:** [The Hacker News](https://thehackernews.com/2026/08/cdn-tsunami-attack-abuses-http3.html)
