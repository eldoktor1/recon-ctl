# Research digest — kb-enrich — 2026-08-23 (run 2)

## 1. SQLi — JSON-payload WAF bypass is a confirmed cross-vendor gap (`class-sqli`)
Claclaroty/Team82 research (disclosed to vendors, patches shipping through 2025-2026) found **Palo Alto, AWS, Cloudflare, F5, and Imperva WAFs all failed to parse SQL injection delivered inside JSON syntax** — the WAF's tokenizer chokes on JSON structure while the backend DB (MySQL/Postgres/MSSQL/SQLite all have native JSON functions) parses it fine. Directly relevant: our SQLi confirm lane (`recon-params confirm sqli`) targets in-scope+paying JSON APIs — this is a concrete, still-live bypass angle to try when a plain `'`/`''` differential is silently swallowed by an edge WAF (403/edge-block on raw payload, 200 on JSON-wrapped). Some hosts may already be patched (vendors added JSON inspection per the disclosure) — treat a working bypass as a stronger signal, not assume it's universal.
⚠️ Payload example and vendor list came from a single secondary blog (picussecurity) summarizing the Team82 work — verify against Claroty's own writeup before citing vendor names in a report.

## 2. GraphQL — nested-resolver BOLA bypasses root-level auth (`class-graphql`)
Multiple independent 2026 sources describe the same real pattern: **auth is checked at the root query resolver but does not cascade to nested/relationship resolvers.** A guard on `user(id)` doesn't re-run when the same object is reached via a different path (e.g. `order(id) { user { ssn } }`, `booking { customer { paymentToken } }`). This is a genuine escalation beyond "introspection enabled" — it's a real object-level authz gap our current lane doesn't specifically probe for.
- **Detection technique (safe, unauth-appropriate for our lane):** from the harvested schema, find every type reachable via **more than one path** (a root query AND as a field on a sibling/parent type). Test the SAME sensitive field/object through both paths — if the root path 403s/redacts but the nested path returns the data, that's the bypass firing.
- **Differential-testing companion:** run the identical query as two different authenticated roles/sessions and diff the response for fields the lower-privileged role shouldn't see — the standard human-confirm step for this stays 2-owned-accounts, unchanged from our existing IDOR discipline.
Sources note tools like Burp's GraphQL extensions (Raider/Intruder) for the enumeration side, consistent with our existing Burp-MCP tooling.
