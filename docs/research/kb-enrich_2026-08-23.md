## 1. Spring Boot Actuator — two NEW auth-bypass CVEs beyond CVE-2026-40976 (`tech-spring-boot-actuator`)
CVE-2026-22731 and CVE-2026-22733 (disclosed 2026-03-19) are a **different bug class** from the CVE-2026-40976 dependency-state bug already in our KB — a Spring Boot config pattern where an *application* endpoint gets silently swept under Actuator's permissive-access policy. Version range is much wider than 40976 (down to 2.7.31 for 22733), but exploitation is condition-gated, not universal — treat as LEAD requiring config confirmation, per our KEV-clamp doctrine.
- **CVE-2026-22733 (CloudFoundry path bypass):** if an app maps an authenticated endpoint under `/cloudfoundryapplication/<subpath>` (the CloudFoundry Actuator discovery path), Spring Boot applies Actuator's permit-all policy to the whole prefix and the authenticated endpoint becomes unauth-reachable. Affects Spring Boot 4.0.0-4.0.3, 3.5.0-3.5.11, 3.4.0-3.4.14, 3.3.0-3.3.17, **2.7.31 and earlier**. Fixed: 4.0.4 / 3.5.12 (OSS); 3.4.15/3.3.18/2.7.32 enterprise-only.
- **CVE-2026-22731 (health-group path bypass):** if `management.endpoint.health.group.<name>.additional-path=server:/<path>` is configured AND an authenticated app endpoint lives under that same subpath (e.g. `/healthz/admin` when the health group additional-path is `/healthz`), the health group's permit-all leaks onto the app endpoint. Affects 4.0.0-4.0.3, 3.5.0-3.5.11, 3.4.0-3.4.14. Fixed: 4.0.4/3.5.12/3.4.15.
- **Recon-relevant:** both need `management.endpoints.web.exposure` + Spring Security on the classpath, so any host already flagged for actuator probing is a candidate. Probe primitive: try common app-shaped subpaths (`/admin`, `/users`, `/settings`) appended under `/cloudfoundryapplication/` and under any discovered health-group additional-path — a 200/data response where the same path 401s at its normal root = the bypass firing. This is a **safe, unauth GET-only confirm** — fits `recon_actuator_chain.py` cleanly as a second bypass mode alongside CVE-2026-40976 version-gating.
- Sources: [spring.io/security/cve-2026-22733](https://spring.io/security/cve-2026-22733/), [spring.io/security/cve-2026-22731](https://spring.io/security/cve-2026-22731/), [HeroDevs writeup](https://www.herodevs.com/blog-posts/spring-boot-authentication-bypass-two-new-cves-that-enterprise-teams-cannot-afford-to-ignore-cve-2026-22731-cve-2026-22733)

## 2. IDOR — concrete disclosed-report patterns with exact payloads (`class-idor`)
A 250-report empirical dataset (thebughunter.blog) surfaces techniques distinct from what's already in our KB (the 08-15/08-18 additions covered presigned-URLs and general BOLA taxonomy) — these are specific, high-bounty exploitation shapes worth adding to the confirm/report playbook:
- **GraphQL node substitution (8.4% of the dataset, growing 140% 2020-22→2023-25):** mutations that accept an `ids`/`id` array with no field-level ownership check. Snapchat #1819832 ($15K): `mutation DeleteStorySnaps { deleteStorySnaps(ids: ["VICTIM_ID"], storyType: SPOTLIGHT_STORY) }` deleted another creator's monetized content — server checked auth (valid token) but never object ownership. Directly extends our GraphQL lane: after schema harvest, any mutation taking an object-ref array is now explicitly a top IDOR candidate, not just queries.
- **Session-object misbinding via SSO deterministic secrets (rare but critical):** Mozilla #3154983 ($6K) — SSO users share a deterministic `authPW` hash, so `POST /v1/account/destroy {email, authPW}` with a valid attacker session + victim's email (no victim password needed) deleted the victim's account. Worth a specific check when profiling auth: does the target's SSO/passwordless flow derive a *predictable* secret from a public identifier (email)? If so a "requires password" gate is cosmetic.
- **Import/export pipeline hijacking:** GitLab #743953 ($20K) — the project importer trusted attacker-supplied foreign-key ID arrays in an import payload (`issue_ids`, `merge_request_ids`) and reassigned those objects to the attacker's project without an ownership check (`project_tree_restorer.rb`). Generalizes: any bulk import/export/clone/duplicate feature that accepts client-supplied object IDs is a distinct IDOR surface from the usual `GET /object/{id}` pattern — add to WSTG BUSL-class checklist items alongside standard object-ref tests.
- **Economics for severity framing (useful for honest-severity report language, PoC-OR-GTFO doctrine):** average bounty by op — READ $1,090, UPDATE $5,870, DELETE $14,333 (2.6x read avg). Confirms our doctrine that a read-only IDOR PoC is real but should NOT be framed as equivalent severity to a write/delete IDOR — lead with accurate operation-class framing.
- **Chain pattern:** Uber #1145428 ($5,750) — enumerate-voucher-ID IDOR + modify-voucher-target IDOR + auth-bypass-apply chained to arbitrary charge. Reinforces EXHAUST-EACH-HOST doctrine: a single low-sev IDOR read is often step 1 of a chain, not the whole finding.
- Source: [thebughunter.blog IDOR case study (250 reports)](https://www.thebughunter.blog/case-studies/idor-analysis)

## 3. SQLi — JSON-syntax WAF bypass + ORM raw-query escape hatches (`class-sqli`)
Two additions worth folding in. Note: the JSON-WAF-bypass technique (Team82/Claroty origin) predates our 12-month window but is still **absent from our KB** and remains broadly effective against JSON-blind WAF rule sets in 2026 writeups — flagging as foundational-but-undocumented rather than brand-new.
- **JSON-syntax WAF bypass:** WAF signature libraries historically don't parse SQL keywords wrapped inside JSON function syntax. Payload: `' or JSON_LENGTH("{}") <= 8896 union distinctrow select @@version#` — the `JSON_LENGTH()`/`JSON_EXTRACT()` wrapper evades signature matching on MySQL/PostgreSQL/MSSQL/SQLite backends that natively support JSON functions, while still executing the union/boolean logic. Originally shown effective against Palo Alto, AWS, Cloudflare, F5, Imperva (largely patched since); still worth a differential-test variant (`'`vs`''` inside a JSON-function wrapper) when our standard boolean-diff primitive gets WAF-blocked but the raw param looks reflective. ⚠️ vendor-patched broadly since original disclosure — treat as a bypass-when-normal-diff-fails technique, not a fresh universal hole.
- **ORM raw-query escape hatches (the actual fresh finding for JS/Python/Java stacks we crawl):** every major ORM has an intentional "drop to raw SQL" method that reintroduces injection once a developer string-formats into it instead of using bind params — worth a fingerprint note since our jsintel/source-map lane recovers original (un-minified) server code in some cases:
  - Django: `Model.objects.raw(f"SELECT * FROM t WHERE x = '{user_input}'")` — vulnerable; `.raw(query, params=[...])` is safe.
  - SQLAlchemy: `db.execute(text(f"SELECT * FROM t WHERE name = '{name}'"))` — vulnerable; `text(...).bindparams(...)` is safe.
  - General signal: `information_schema` queries, `SLEEP()`, or `UNION SELECT` executed by an app-service DB account is never legitimate — a detection heuristic if we ever get log/error visibility (actuator/heapdump chains sometimes expose exactly this).
- **Second-order confirm reminder:** stored-then-detonated injection (e.g. a username stored unsanitized, later interpolated into a password-reset query) won't show up on the same request that stores it — our differential-confirm primitive should re-test on any endpoint that *reads back* a value the target let us set (profile fields, display names, referral codes), not just the original write endpoint.
- Sources: [Picus Security — WAF Bypass Using JSON-Based SQLi](https://www.picussecurity.com/resource/blog/waf-bypass-using-json-based-sql-injection-attacks), [Hive Security — SQL Injection 2026 guide](https://hivesecurity.gitlab.io/blog/sql-injection-complete-guide-2026/)

### Session-object misbinding via deterministic SSO secrets (rare, critical when found)
If an SSO/passwordless flow derives a "password"-equivalent secret deterministically from a
public identifier (email), a "requires password" check degrades to "requires only the
victim's email". Example — Mozilla #3154983 ($6K): `POST /v1/account/destroy
{email, authPW}` with attacker's own valid session + victim's email deleted the victim's
account. When profiling an SSO/passwordless target, check whether the secondary-secret is
derivable from a public value.

### Import/export pipeline hijacking
Bulk import/export/clone/duplicate features that accept client-supplied foreign-key object
IDs are a distinct IDOR surface from `GET /object/{id}`. Example — GitLab #743953 ($20K):
project import JSON (`issue_ids`, `merge_request_ids`) with foreign IDs got blindly
reassigned to the attacker's project (`project_tree_restorer.rb`), moving private issues/MRs/
CI secrets across tenants. Add explicit import/export-endpoint checks to the WSTG BUSL pass.

### Severity-framing economics (for honest-severity reports, not just detection)
Average bounty by operation class: READ $1,090, UPDATE $5,870, DELETE $14,333 (deletion/
modification IDORs pay ~2.6x read-only). Frame report severity by the operation actually
demonstrated — don't inflate a read-only IDOR PoC to write/delete-class severity, and don't
under-claim a demonstrated write/delete as if it were read-only.

### Chain pattern reminder
Uber #1145428 ($5,750): enumerate-ID IDOR → modify-target IDOR → auth-bypass chained to
arbitrary charge. A single low-severity IDOR read is frequently step 1 of a chain — keep
exhausting the host (ties to NO-PREMATURE-EXHAUSTION doctrine) rather than reporting the
first weak primitive found.
