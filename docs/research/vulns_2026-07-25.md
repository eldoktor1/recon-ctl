# Research digest — vulns — 2026-07-25 (supplemental)

## 1. NEW — PHP SOAP extension UAF RCE, CVE-2026-6722 (CVSS ~9.5) — hits our top-tech PHP directly ★
- **What:** Use-after-free in the SOAP extension's object-deduplication map — duplicate keys inside an `apache:Map` node during SOAP request deserialization free a pointer that's still referenced; an attacker who controls the SOAP request body can reclaim that memory via subsequent PHP string allocations → RCE.
- **Affected:** PHP 8.2.x < 8.2.31, 8.3.x < 8.3.31, 8.4.x < 8.4.21, 8.5.x < 8.5.6 — **any app using `SoapServer`/`SoapClient`**.
- **Detect (unauth, in-range-verifiable):** requires the target to expose a SOAP endpoint — look for `?wsdl`, `Content-Type: text/xml`/`application/soap+xml`, `SOAPAction` header, or a WSDL file in jsintel/fulltext ES corpus. Combine with PHP version disclosure (`X-Powered-By`, error banners, `phpinfo` leaks). SOAP is a narrower surface than generic PHP, but where present + version-in-range this is a genuine unauth RCE LEAD, not just a tech-class match — worth a `recon-nday` pass over ES for `soap`/`wsdl` fulltext hits combined with our PHP fingerprint set.
- Source: [SentinelOne CVE-2026-6722](https://www.sentinelone.com/vulnerability-database/cve-2026-6722/), [Pinaka.sh technical writeup](https://pinaka.sh/blog/cve-2026-6722-php-soap-use-after-free-rce/)

## 2. NEW — Apache HTTP Server CVE-2026-23918 (HTTP/2 double-free) — top-tech, but authenticated-only
- **What:** Double-free in the HTTP/2 handler, CVSS 8.8. Public PoC exists.
- **Affected:** Apache HTTP Server 2.4.66, fixed in 2.4.67. **Trigger requires an authenticated network attacker** — not directly usable in our unauth-first lane, but worth a version-fingerprint note for later authed/PoC work if we ever land credentials on an Apache-fronted host.
- **Detect:** `Server: Apache/2.4.66` banner (many hosts suppress this — treat absence as unknown).
- Source: [The Hacker News](https://thehackernews.com/2026/05/critical-apache-http2-flaw-cve-2026.html)

## 3. Varnish CVE-2026-34475 — full detail (prior digest was cut off) — kb-proposal below
Root cause confirmed: CWE-180 (validate-before-canonicalize). `req.url` VCL var passed unchecked to a backend accepting absolute-form URIs — mishandling of HTTP/1.1 requests whose path is literally `/` (root only; `/whatever` paths are NOT affected) enables cache poisoning or URL-based-ACL auth bypass.
- **Affected:** Varnish Cache ≤ 8.0.0, Varnish 6.0 LTS ≤ 6.0.16, Varnish Enterprise 6.0.x ≤ 6.0.16r11.
- **Fixed:** Varnish Cache 8.0.1, Varnish 6.0 LTS 6.0.17, Varnish Enterprise 6.0.16r12, Vinyl Cache 9.0.
- **Detect:** `Via`/`X-Varnish` response headers for version; test surface is narrow (root-path requests only) — fits our `recon_wcd.sh` differential-probe pattern (own cache-buster key, never poison the real cache).
- Source: [Varnish security advisory VSV00018](https://vinyl-cache.org/security/VSV00018.html), [GHSA-m9gq-cmcj-p62x](https://github.com/advisories/ghsa-m9gq-cmcj-p62x)

## 4. Reusable JWT bypass patterns worth adding to our KB (not tied to one product) — kb-proposal below
Two 2026 disclosures generalize into checks we should run on ANY authed JWT-based API we test:
- **CVE-2026-29000 (pac4j-jwt, CVSS 10.0):** library treated an **RSA public key as if it could be used to forge a valid encrypted/signed token** — full auth bypass using only the public key (which is often exposed via JWKS endpoints). Generalized check: does the target's JWT verification accept a token whose signature was produced with the PUBLIC key material (classic RS256→HS256 confusion variant)?
- **CVE-2026-23993 (HarbourJwt):** verification for an "unknown" `alg` value returns an **empty string** instead of failing closed, and the signature comparison doesn't treat that as fatal — so a forged token with an unrecognized `alg` + empty signature validates. Generalized check: try garbage/unsupported `alg` values, not just `none`.
- Sources: [CodeAnt AI — pac4j-jwt writeup](https://www.codeant.ai/security-research/pac4j-jwt-authentication-bypass-public-key), [PentesterLab — HarbourJwt unknown-alg bypass](https://pentesterlab.com/blog/cve-2026-23993-harbourjwt-unknown-alg-jwt-bypass)
