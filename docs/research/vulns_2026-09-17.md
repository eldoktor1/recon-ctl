## 1. NEW — CVE-2026-3125, OpenNext-on-Cloudflare SSRF via `/cdn-cgi/image/` path-normalization bypass — unauth, directly testable, fits our interactsh SSRF lane ★★★
- **What:** `@opennextjs/cloudflare` (the standard adapter for deploying Next.js on Cloudflare Workers) ships a dev-only `/cdn-cgi/image/` handler. In production, Cloudflare's edge is *supposed* to intercept `/cdn-cgi/image/` before it reaches the Worker — but substituting a backslash (`/cdn-cgi\image/`) slips past the edge intercept, and the Worker's JS `URL` class then normalizes the backslash back to a forward slash, matching the handler anyway. The handler performs an **unvalidated server-side fetch of an attacker-supplied URL** → classic SSRF, plus it can serve attacker content from the victim's own origin (same-origin-policy violation) and expose cached `/cdn-cgi/` content.
- **Affected:** `@opennextjs/cloudflare` npm package < **1.17.1**. CVSS 6.5.
- **Why relevant to us:** hits the intersection of our two top-tech entries **Cloudflare** and (via our existing `tech-nextjs.md` KB) Next.js — any in-scope host that is Next.js-on-Cloudflare-Workers is a direct match, not a stretch.
- **Detect + CONFIRM (unauth, safe, fits our SSRF-via-canary doctrine exactly):** fingerprint Next.js + Cloudflare Workers hosting (CF headers + Next.js build markers in jsintel), then request `GET /cdn-cgi\image/width=100/https://<our-interactsh-canary>` — an OOB callback to our own collector is a clean, safe, unauthenticated confirm primitive (same pattern as our existing SSRF interactsh lane), no internal-network targeting needed to prove it.
- **Sources:** [GitHub Advisory GHSA-c7mq-gh6q-6q7c](https://github.com/opennextjs/opennextjs-cloudflare/security/advisories/GHSA-c7mq-gh6q-6q7c), [SentinelOne](https://www.sentinelone.com/vulnerability-database/cve-2026-3125/), [NVD](https://nvd.nist.gov/vuln/detail/CVE-2026-3125)

## 2. UPDATE — CVE-2026-34356, Apache `mod_proxy_http` ProxyPassReverseCookie heap overflow — now has full version range + fix, still config-gated
- Previously flagged 2026-09-11 as a WATCH item with truncated detail. Now confirmed: **heap-based buffer overflow, affects Apache HTTP Server 2.4.0 – 2.4.67**, triggered via `ProxyPassReverseCookie` directive with a malicious backend response. Fixed in **2.4.68**.
- **Detect (unauth, fingerprint-only):** `Server: Apache/2.4.x` header where x < 68 narrows to in-range; but exploitability requires the site's config to actually use `ProxyPassReverseCookie` (reverse-proxying with cookie rewriting) — not remotely visible. Same doctrine as the earlier Varnish/nginx items: **version-in-range = LEAD only**, don't attempt to trigger (crash/heap-corruption primitive, destructive).
- **Action:** note any in-scope Apache host on 2.4.0–2.4.67 for the operator; this is a version-flag, not a probe.
- **Sources:** [SentinelOne CVE-2026-34356](https://www.sentinelone.com/vulnerability-database/cve-2026-34356/)
