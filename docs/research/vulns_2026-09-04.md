## 1. NEW — CVE-2026-19949, All-in-One WP Migration and Backup — unauth 2nd-order SQLi → RCE, 5M+ installs ★★
- **What:** The archive-restore functionality builds SQL queries from unsanitized/unprepared user input. It's **second-order**: an unauthenticated attacker first plants a crafted payload via a **trackback submission to any public post** (sits inert in the DB); when a site admin later exports and re-imports/restores the site with the plugin, the payload fires as SQL injection during restore, letting the attacker steal the `ai1wm_secret_key` — which is then leveraged for RCE. Different bug class from the file-upload-bypass pattern seen the last two weeks (Elementor Pro/Forminator/WPvivid), same "WP plugin, unauth entry, needs an admin/config precondition" shape as WooCommerce-HPOS.
- **Affected:** All-in-One WP Migration and Backup ≤ 7.109 (5M+ active installs, ~3.2M still vulnerable as of Sep 3). Fixed in **7.110** (released 2026-08-20).
- **Detect (unauth, in-range-verifiable):** `GET /wp-content/plugins/all-in-one-wp-migration/readme.txt` → `Stable tag`; also `ai1wm`/`all-in-one-wp-migration` string in jsintel JS bundles on WordPress-fingerprinted hosts. The trackback-plant step itself is a safe, non-destructive unauth POST (just leaves inert data) — but exploitation only completes if/when an admin performs an export+restore, which is not remotely observable/triggerable by us.
- **Action:** version-match (≤7.109) = LEAD (plant primitive is safe to note but do not chain toward the SQLi/RCE — completion requires admin-side action outside our control and crosses into exploitation per doctrine). Add to `recon-mood wordpress` sweep.
- **Sources:** [SecurityWeek](https://www.securityweek.com/over-3-million-wordpress-sites-affected-by-migration-plugin-vulnerability/), [dev.to writeup](https://dev.to/anoymask/all-in-one-wp-migration-cve-2026-19949-from-second-order-sql-injection-on-restore-to-site-takeover-21be), [SentinelOne](https://www.sentinelone.com/vulnerability-database/cve-2026-19949/)

## 2. WATCH — CVE-2026-13762/13763, AWS WAF HTTP/2 multi-frame body-inspection bypass — touches our top-tech CloudFront, but not independently actionable
- **What:** A crafted multi-frame HTTP/2 request could cause AWS WAF to inspect only a partial request body, letting a malicious payload (SQLi/XSS/etc.) slip past managed-rule body inspection undetected. `-13762` = CloudFront-fronted deployments (**AWS has already remediated this server-side; no customer action needed**). `-13763` = ALB-fronted deployments (customers must configure HTTP/2 body-inspection settings themselves).
- **Why noted:** Amazon CloudFront and AWS WAF are both on our detected in-scope tech list, and this is a genuine disclosed CVE against that exact stack — but it's already fixed for the CloudFront path and gives us no new probe (a WAF-bypass proves nothing on its own; the underlying injection still needs its own primitive). Treat as background awareness only, not a lane addition.
- **Source:** [AWS Security Bulletin 2026-048](https://aws.amazon.com/security/security-bulletins/2026-048-aws/)
