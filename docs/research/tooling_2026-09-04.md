## 1. EVALUATE — `google/aura-inspector` (Mandiant AuraInspector) — fills the class-salesforce-aura tooling gap
- **What it is:** Salesforce Experience Cloud / Aura-framework misconfiguration tester, released by Mandiant (Google) Jan 2026. 106★/29 forks, Apache-2.0. Automates discovering **guest-user-accessible records**, self-registration exposure, and unauthorized Aura-controller access — i.e. it directly probes the exact primitive (guest-context object exposure) that turns "Aura enabled" from an Info-line into a real unauth-data-exposure finding.
- **Why it matters:** we already carry `docs/knowledge/class-salesforce-aura.md` but no dedicated tool in the stack — this is currently a manual `apex_extractor`/curl exercise (per the same search sweep, `p4b3l1t0/apex_extractor` mines `aura://`/`apex://` controller URLs from JS, which pairs well as a feeder). Fits our chain-to-impact law directly: "Aura endpoint exists" is the dup-trap the crowd files; "guest user can read `<sensitive object>` via Aura" is the payable chain.
- **Doctrine fit:** unauth-safe ✅ (guest-context, unauthenticated by definition), non-destructive ✅ (read-only record enumeration, no writes), dup-resistant ✅ (Salesforce Aura misconfig is under-hunted vs generic subfinder/nuclei sweeps). Caveat: maintenance cadence past the initial 7-commit release is unclear — re-check before treating it as durable infra.
- **Alternative checked:** `cosad3s/salsa` (31★, GPL-3.0) does similar Aura enumeration/dump but the author states in-repo "this tool is now hard to maintain" — **skip**, aura-inspector is the better-backed pick.
- **Verdict: EVALUATE** — trial against one in-scope host running Salesforce Experience Cloud/Aura; if it reliably surfaces guest-readable objects, wire as the confirm step for any future `class-salesforce-aura` lane (still needs the sensitive-data classifier from `engine/impact.py` before minting — guest-readable-by-design marketing content ≠ a finding).

## 2. EVALUATE (KB addition) — CDN re-fronting (`RyanJarv/cdn-proxy`) — a second origin-bypass technique beyond what we've documented
- **What it is:** 272★/25 forks, actively maintained (125 commits, CI workflows). Different technique from what `class-cdn-origin-bypass.md` already covers (CT-log/favicon-hash/grey-cloud OSINT + CloudFlair-style direct-IP verification): it exploits **IP-allowlisted origins that trust "any request from the shared CDN's IP pool."** The operator stands up their OWN CloudFront/Cloudflare distribution pointed at the same origin — since the origin only allowlists the CDN's IP range (not the specific distribution), the attacker-controlled distribution can reach the origin directly, bypassing the target's own WAF/CDN security layer entirely (not just finding the IP — routing real requests around the security layer via a sibling distribution on the same network).
- **Why it's new to us:** our KB's origin-bypass primitive assumes the origin is reachable directly once its IP is found; this covers the case where the origin is IP-allowlisted to "traffic from Cloudflare/CloudFront only" (common AWS/Cloudflare setup) and no direct-IP path exists — a distinct, currently-undocumented bypass path.
- **Doctrine fit:** requires operator-controlled cloud infra (AWS account / Cloudflare zone) — a one-time setup cost, not a daemon-safe primitive; testing through it is unauth-safe/non-destructive (GET/HEAD only) once stood up, same as our existing verification primitive. In-scope+pays gate applies identically.
- **Verdict: EVALUATE + KB-PROPOSE** — add as a documented *second* bypass path in `class-cdn-origin-bypass.md` (distinct from the discovery-techniques section) for on-demand use when direct-IP discovery fails but the target sits behind a shared CDN with IP-allowlisted origin.
