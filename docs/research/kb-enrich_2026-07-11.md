## KB Enrichment Digest — 2026-07-11

Two proposals this run, both targeting our top money classes (IDOR ID-type scoring + GraphQL BOLA detection). No genuinely new tech/class gap found worth a `kb-new` — GraphQL, SSRF, and Next.js SSRF are already well-covered in our KB from prior research passes.

### 1. UUIDv7 timestamp-prefix narrows "harvestable" IDs (`class-idor.md`)
Our current ID-type scoring treats all UUIDs as one bucket ("uuid=harvestable, need a leak vector"). That's stale: UUIDv7 (RFC 9562, now the default in several ORMs replacing sequential ints) embeds a 48-bit **millisecond Unix timestamp** as its first bits — so a leaked/observed creation time (e.g. from a listing endpoint, an `Airplane-Table` timestamp, or just "this account signed up today") collapses the brute-force space from 2^122 to a narrow per-millisecond window of pure randomness. This is a materially different risk tier from UUIDv4 and should be scored separately.

### 2. GraphQL nested-resolver BOLA gap + mass assignment (`class-graphql.md`)
Distinct from the object-ref-arg pattern we already rank: auth is frequently enforced only at the **gateway/top-level query**, not inside nested-type resolvers — a mutation like `updateOrder(id)` or a nested `order { customer { ssn } }` field can resolve a referenced object without re-checking ownership, because the resolver trusts the input/parent id. Separately, mutations accepting a full input type (`updateProfile(input: {name,email,role})`) without field allow-listing are a mass-assignment privesc vector (client just adds `role` to the input JSON — no schema violation, no error). Both are worth adding to our worklist-ranking reasoning (not just object-ref top-level args).
