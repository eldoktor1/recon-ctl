### 1. CVE-2026-44578 — Next.js WebSocket-upgrade SSRF (May 2026, unauthenticated, ~79k exposed instances)
Self-hosted Next.js (`next start`) has an asymmetric safety check in the WS-upgrade proxy path (`router-server.ts`) that only validates `parsedUrl.protocol`, not the `finished`/`statusCode` routing-approval flags the normal HTTP path checks. Sending an **absolute-form request-target** with an `Upgrade: websocket` header makes Next.js proxy the request server-side to whatever host is embedded in the URI — no auth, one request, reaches port 80 on anything network-reachable (cloud metadata `169.254.169.254`, internal admin/API/monitoring). Affects 13.4.13–15.5.15 and 16.0.0–16.2.4; Vercel-hosted apps are NOT affected (self-hosted `next start` only). Fixed in 15.5.16 / 16.2.5.
Directly relevant: WordPress/PHP/Nginx aside, Next.js shows up across our surface and this is exactly the OOB-confirmable (interactsh canary in the metadata-path host, or a benign external canary first) SSRF our pipeline's confirm primitive already handles — just needs a WS-upgrade-shaped probe added to the sink list.

### 2. Generalized pattern: absolute-form request-target → any Node/Express backend behind a passthrough reverse proxy
Not Next.js-specific. Any Nginx/ALB/reverse-proxy config that passes the raw request-target through untouched, into a Node/Express app that does `new URL(req.url)` or equivalent without checking for a leading `/`, turns the proxy into an unauthenticated forward proxy — full-read SSRF to localhost-bound services and internal hosts. Same trigger shape (`GET http://target/path HTTP/1.1`) works against any Node backend with this pattern, not just the WS-upgrade path — worth testing on every in-scope Node/Express host we jsintel-fingerprint, not only Next.js ones.
