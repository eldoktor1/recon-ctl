# Research digest — vulns — 2026-07-21

## 1. NGINX CVE-2026-42533 — status update: ASLR-defeat detail + scanner is LOCAL-ONLY (not usable for our external unauth recon)
Already flagged 2026-07-19 with a cut-off caveat. New detail resolves it:
- **Patched:** confirmed nginx 1.30.4 (stable) / 1.31.3 (mainline) / NGINX Plus 37.0.3.1, released 2026-07-15. Vulnerable range 0.9.6–1.31.2 — our fingerprinted `nginx:1.29.7` stays in-range.
- **Correction to severity model:** it does **not** require ASLR already disabled — the bug carries its own info-leak primitive that defeats ASLR from a single unauthenticated GET, so RCE is more reachable than the "DoS unless ASLR off" framing we had.
- **The public "scanner" (0xCyberstan/CVE-2026-42533-Config-Scanner, per TechTimes) is a static `nginx.conf` directive-order reader — it needs local filesystem access to the config, not a remote probe.** There is still no safe external unauth fingerprint beyond the `Server:` version banner. **No change to our doctrine: version-range LEAD only, never trigger, no live PoC exists to raise it past LEAD.**
- Sources: [SC Media](https://www.scworld.com/brief/f5-fixes-critical-nginx-vulnerability-cve-2026-42533), [SecurityAffairs](https://securityaffairs.com/195674/hacking/cve-2026-42533-critical-nginx-bug-could-turn-http-requests-into-server-takeovers.html), [TechTimes](https://www.techtimes.com/articles/321018/20260720/nginx-map-regex-rce-gets-public-scanner-patch-now-full-exploit-due-august.htm)

**CVE-2026-42055** (grpc/proxy_v2 heap overflow) previously flagged ⚠️NVD-unverify on 2026-06-26 — now confirmed legitimate, CVSS 9.2, part of the same F5 out-of-band patch batch. Same detection as before: `Server: nginx` + `grpc-status` header or `Content-Type: application/grpc`, requires grpc-proxying config. Add to the nday sweep alongside 42533/42945.

## 2. NEW — Varnish Cache CVE-2026-34475: auth-bypass / cache-poisoning via `req.url` canonicalization order — extends our WCD lane, zero prior coverage
Varnish is one of our top fingerprinted tech and we've never tracked a Varnish CVE before.
- **What:** CWE-180 (validate-before-canonicalize) bug — Varnish mishandles HTTP/1.1 requests whose path is `/` in "certain unchecked `req.url` scenarios," letting malformed requests bypass cache-key/VCL auth logic that inspects `req.url`. Impact: cache poisoning and potential auth-check bypass.
- **Affected:** Varnish Cache < 8.0.1, Varnish Enterprise < 6.0.16r12. Patched: 8.0.1 / 6.0.16r12.
- **Detect (unauth):** no universal remote fingerprint — exploitability is VCL-config-dependent. Practical move: version-banner via `Via`/`X-Varnish` headers on in-scope Varnish hosts → LEAD, then feed into `recon-wcd` as a candidate for the path-confusion/cacheability-flip test we already run (this is a variant of the same class, not a new tool needed).
- Not in KEV, no public exploit yet.
- Sources: [SentinelOne CVE-2026-34475](https://www.sentinelone.com/vulnerability-database/cve-2026-34475/), [GitHub Advisory GHSA-m9gq-cmcj-p62x](https://github.com/advisories/GHSA-m9gq-cmcj-p62x), [Glexia CVE Intel](https://security.glexia.com/cves/CVE-2026-34475)

## 3. NEW technique — GraphQL Relay global-ID decode/increment/re-encode is the dominant BOLA pattern in a 200-report HackerOne study
Academic taxonomy of 107 classified BOLA/IDOR disclosures (HackerOne/GitLab/Shopify, 2021–2026): the single most common GraphQL BOLA pattern is a base64 "global ID" (Relay spec, e.g. `VXNlcjox` = `User:1`) that's trivially decodable, the numeric component incrementable, then re-encoded and replayed. This directly upgrades our `recon-graphql` worklist logic — currently we rank object-ref args generically; this gives a concrete, high-yield sub-signal (base64-looking ID arg + decodes to `Type:digits` = near-certain enumerable object ref, elevate over opaque-UUID args).
- Source: [arXiv 2605.25865 — BOLA empirical taxonomy](https://arxiv.org/html/2605.25865)
