# Research digest — vulns — 2026-07-17

## Vuln/CVE + Writeup Watch — 2026-07-17 (last ~14 days)

### 1. NGINX "Rift" wave — 3 stacked pre-auth CVEs, one is a DIRECT version hit on our stack ⚡
Our own top-tech list names an **exact running version: `Nginx:1.29.7`**. That version falls inside the vulnerable range for the headline CVE below — this is a rare case where our doctrine's "confirmed in-range version" bar is already cleared by our own ES data, not just a tech-class guess.

- **CVE-2026-42945 ("NGINX Rift")** — heap buffer overflow in `ngx_http_rewrite_module`, CVSS 9.2. Unauthenticated, crafted-HTTP-request trigger; DoS reliably, RCE possible only where ASLR is off. **Affected: nginx 0.6.27 – 1.30.0 (OSS), NGINX Plus R32–R36. Fixed: 1.30.1 / 1.31.0.** → **`1.29.7` is IN-RANGE.**
  - Detection caveat (important, not just tech-class): the flaw only fires when the site's actual config has a `rewrite` directive using an *unnamed* PCRE capture (`$1`/`$2`) with a `?` in the replacement string, followed by another `rewrite`/`if`/`set` in the same scope. Version-in-range alone is a LEAD per our own doctrine — need the config pattern too, which for unauth recon means inferring from response behavior/headers, not source. Treat as `kev_needs_verify`-style: version match = LEAD, not P0, unless we can show the rewrite chain fires (e.g. via response-length/500 differential on a crafted `?`-laden path).
  - Source: [NVD CVE-2026-42945](https://nvd.nist.gov/vuln/detail/CVE-2026-42945), [AlmaLinux patch notes](https://almalinux.org/blog/2026-05-13-nginx-rift-cve-2026-42945/), [Plesk advisory](https://support.plesk.com/hc/en-us/articles/40461457542807-Vulnerability-CVE-2026-42945-DoS-and-RCE-in-nginx-before-1-31-1-1-30-1)

- **CVE-2026-9256** — second rewrite-module heap overflow (overlapping captures), disclosed as a follow-up to Rift. **Affected: 0.1.17 – 1.31.0. Fixed: 1.30.2 / 1.31.1+.** `1.29.7` also in-range. Patching Rift (1.30.1/1.31.0) does **not** close this one — needs its own patch. Source: [NVD CVE-2026-9256](https://nvd.nist.gov/vuln/detail/CVE-2026-9256), [lilting.ch writeup](https://lilting.ch/en/articles/nginx-njs-8711-rewrite-9256-second-wave)

- **CVE-2026-8711** — njs `js_fetch_proxy` heap overflow, pre-auth, config-specific (needs a location calling `ngx.fetch()` with a client-controlled URL var). **Affected: njs 0.9.4–0.9.8. Fixed: 0.9.9.** Only relevant if a target's njs module is in use (rarer than core nginx — check `Server` header / njs-specific behavior before chasing). Source: [lilting.ch](https://lilting.ch/en/articles/nginx-njs-8711-rewrite-9256-second-wave)

**Action for our pipeline:** `recon-mood nginx` / `recon-nday` should flag any host fingerprinted `nginx/1.29.x` (or the broader 0.6.27–1.31.0 band) as a Rift/9256 LEAD, then attempt the config-pattern differential before minting anything above LEAD. Version alone stays clamped per doctrine.

### 2. Varnish Cache — auth bypass / cache poisoning overlaps our WCD lane directly
**CVE-2026-34475** — Varnish Cache before 8.0.1 (and Varnish Enterprise before 6.0.16r12) mishandle a request URL whose path is exactly `/` for HTTP/1.1 (validate-before-canonicalize bug, CWE-180), leading to **cache poisoning or auth bypass**. This is squarely in our `recon_wcd.sh` lane's wheelhouse — Varnish is on our top-tech list and this is a *real cacheability-flip primitive*, not the generic "introspection enabled"-style Info-FP we already filter.
- Detect: fingerprint Varnish via `Via: 1.1 varnish` / `X-Varnish` headers, then test whether a bare `/` path request produces divergent caching behavior vs the canonical form — exactly the kind of dynamic-vs-cacheable differential our WCD safe-probe already does.
- Fixed: 8.0.1 (OSS) / 6.0.16r12 (Enterprise).
- Source: [NVD CVE-2026-34475](https://nvd.nist.gov/vuln/detail/CVE-2026-34475), [SentinelOne](https://www.sentinelone.com/vulnerability-database/cve-2026-34475/), [GitHub Advisory](https://github.com/advisories/GHSA-m9gq-cmcj-p62x)
