# Vuln/CVE + Writeup Watch — 2026-07-17 (last ~7-14 days)

## Top actionable items (our tech stack)

### 1. NGINX CVE-2026-42945 — heap overflow in `ngx_http_rewrite_module`, ACTIVELY EXPLOITED (CVSS 9.2)
- **Affected**: nginx 0.6.27 – 1.30.0 (open source; introduced 2008, disclosed/exploited May 2026)
- **Trigger**: a `rewrite`/`if`/`set` directive using an unnamed PCRE capture (`$1`,`$2`) in a replacement string that contains a `?`. RCE only if ASLR is off; otherwise worker crash/DoS.
- **Detect (per our doctrine — version-reason, don't assume)**: `Server: nginx/<=1.30.0` is necessary but NOT sufficient — researchers note it "relies on a specific config... not universally identifiable through banner grabbing." Treat as **LEAD** (version-in-range) unless we can also observe rewrite-driven URL transformation behavior (e.g. `$1` reflected into a redirect/Location with odd `?` handling) confirming the vulnerable pattern is live.
- Also disclosed in the same wave (patched by F5, same nginx codebase): **CVE-2026-42530** (use-after-free, `ngx_http_v3_module` — **HTTP/3**, which is in our top-tech list), **CVE-2026-42055** (heap overflow, `ngx_http_proxy_v2_module`/`ngx_http_grpc_module`), **CVE-2026-8711** (`ngx_http_js_module`), **CVE-2026-9256** (`ngx_http_rewrite_module`, distinct from -42945), **CVE-2026-40701** (resolver UAF, OCSP), **CVE-2026-27654** (`ngx_http_dav_module` overflow). Same LEAD-not-P0 treatment for all — confirm version via `Server` header/error page, never claim RCE from tech-match alone.
- Sources: [The Hacker News](https://thehackernews.com/2026/05/nginx-cve-2026-42945-exploited-in-wild.html), [F5 K000161307](https://my.f5.com/manage/s/article/K000161307), [F5 K000161377](https://my.f5.com/manage/s/article/K000161377), [nginx security advisories](https://nginx.org/en/security_advisories.html)

### 2. Varnish CVE-2026-34475 — cache poisoning / auth-bypass via `req.url` canonicalization (unauth, no privileges required)
- **Affected**: Varnish Cache **< 8.0.1** (OSS), Varnish Enterprise **< 6.0.16r12**
- **Root cause** (CWE-180): validation happens *before* canonicalization — Varnish mishandles HTTP/1.1 requests whose path is `/` in certain unchecked-`req.url` VCL scenarios, letting an attacker desync the cache key from the actual served content → cache poisoning, or bypass URL-based access-control decisions in VCL.
- **Direct fit for our web-cache-deception lane** (`recon_wcd.sh`) — this is a Varnish-specific *new* poisoning primitive, not just generic path-confusion. For in-scope hosts fronted by Varnish (`Via: 1.1 varnish`/`X-Varnish` header present), our existing WCD cache-buster methodology can be pointed specifically at root-path (`/`) HTTP/1.1 requests with unusual encodings to test this. Still SAFE-detect-only per our rule (unique cache-buster key, never poison the real cache).
- No public detection primitive for the exact version yet (advisory unreviewed, no version-disclosure header) — treat as LEAD until a Varnish header/error page confirms version.
- Sources: [GHSA-m9gq-cmcj-p62x](https://github.com/advisories/GHSA-m9gq-cmcj-p62x), [SentinelOne](https://www.sentinelone.com/vulnerability-database/cve-2026-34475/)

- **miniOrange OAuth SSO / Social Login & Register plugin — CVE-2026-57807** (disclosed by Patchstack 2026-07-09): auth bypass via the plugin's password-recovery flow (CWE-288, alternate-path auth bypass). Affects **all versions ≤ 38.5.8**. No auth, no interaction required. **Still UNPATCHED as of this writing** — high-value, time-sensitive n-day. Detect: plugin slug/version in `wp-content/plugins/miniorange-*` readme.txt or enqueued asset query-strings.
- **Hippoo Mobile App for WooCommerce — CVE-2026-XXXX** (July 2026): unauthenticated admin-account-takeover via REST API. Affects **all versions ≤ 1.9.4**. Detect: plugin presence + REST route fingerprint (`/wp-json/hippoo/...` or similar — verify exact namespace before use).
- Both are exactly our profile: WordPress is a top in-scope tech, unauth+no-interaction, high payout ceiling if confirmed in-range.
- Sources: [GBHackers](https://gbhackers.com/critical-wordpress-oauth-sso-plugin-flaw/), [Cyberpress](https://cyberpress.org/wordpress-bug-enables-takeover/)

### 4. CloudFront + AWS WAF — path-blocking bypass via hex URL-encoding (technique, not a CVE)
- WAFs/CloudFront rules that block sensitive paths (e.g. `/actuator`, admin panels) by string-matching the **raw** path before decoding can be bypassed by hex-encoding characters in the blocked path — the WAF's matcher doesn't recognize the encoded form, but the origin still decodes and routes it.
- **Directly useful for our n-day/actuator-hunting lane** on CloudFront+WAF-fronted hosts: if a direct `/actuator` probe 403s at the edge, retry with hex-encoded path segments before concluding the path is blocked/absent — a real fingerprint difference (edge-block vs true 404) matters for our KEV-tech-class LEAD scoring.
- Source: [waf-bypass.com SSRF/WAF tag](https://waf-bypass.com/tag/ssrf/) (aggregator; techniques attributed to various 2026 researchers — verify per-target before relying on it)
