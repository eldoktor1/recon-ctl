# Research digest — vulns — 2026-07-19

## Vuln/CVE + Writeup Watch — 2026-07-19 (last ~14 days)

### 1. WordPress core RCE chain "wp2shell" — CVE-2026-63030 + CVE-2026-60137 — **directly in our top tech, PoC public**
- **What:** REST API batch-route confusion (`CVE-2026-63030`) lets one sub-request run under another sub-request's handler when a batch call errors, chained with a SQLi (`CVE-2026-60137`) → unauthenticated RCE. No account/interaction needed.
- **Affected:** WP core 6.8.0–6.8.5 (SQLi only, no RCE), **6.9.0–6.9.4** and **7.0.0–7.0.1** (full unauth RCE chain). Fixed in 6.9.5 / 7.0.2.
- **Detect (unauth, in-range verifiable):** hit `/wp-json/batch/v1` (or `?rest_route=/batch/v1`) — presence confirms REST batch is enabled; combine with `/wp-json` core version disclosure (`generator` meta tag or `wp-json` root `"description"`/`"gmt_offset"` won't give version, but `readme.html`/`?ver=` on core scripts often does) to place the host in-range before treating as more than a LEAD.
- **PoC:** public GitHub PoC as of 2026-07-18 (per thehackernews writeup) — worth a version-gated `recon-nday` template.
- Source: [The Hacker News](https://thehackernews.com/2026/07/new-wp2shell-wordpress-core-flaw-lets.html), [Rapid7](https://www.rapid7.com/blog/post/etr-cve-2026-63030-wp2shell-a-critical-remote-code-execution-vulnerability-in-wordpress-core/), [Beazley Labs advisory](https://labs.beazley.security/advisories/BSL-A1193)

### 2. NGINX heap overflow via `map` regex captures — CVE-2026-42533 — **matches our nginx:1.29.7 fingerprint**
- **What:** `map` directive regex matching corrupts memory when a string expression references capture vars from a map before the output var (or a non-cacheable var is used similarly) → unauth heap buffer overflow in the worker → DoS, RCE if ASLR is off/bypassed.
- **Affected:** 0.9.6–1.31.2 (our observed `nginx:1.29.7` is in-range). Fixed: 1.30.4 stable / 1.31.3 mainline.
- **Caveat:** exploitability is CONFIG-DEPENDENT (needs a specific vulnerable `map` construct) — an unauth prober can't confirm the config remotely, so per our doctrine this is version-in-range = LEAD, not P0, until we can otherwise infer map usage (e.g. from disclosed nginx.conf/error strings).
- Two companion mediums also fixed same release, less severe but same version band (1.15.8–1.31.2 / 0.8.11–1.31.2): `ngx_http_slice_module` memory disclosure (CVE-2026-60005), `ngx_http_ssi_module` use-after-free (CVE-2026-56434).
- Source: [SOC Prime analysis](https://socprime.com/blog/cve-2026-42533-analysis/), [nginx CHANGES](https://nginx.org/en/CHANGES), [nginx security advisories](https://nginx.org/en/security_advisories.html)

### 3. Varnish Cache auth-bypass / cache-poisoning — CVE-2026-34475 — **direct hit on our WCD lane + `tech-varnish`**
- **What:** unchecked `req.url` handling for HTTP/1.1 requests with path `/` (validate-before-canonicalize bug, CWE-180) lets an attacker poison the shared cache or bypass URL-based auth checks enforced at the Varnish layer.
- **Affected:** Varnish Cache **< 8.0.1**, Varnish Enterprise **< 6.0.16r12**.
- **Detect:** fingerprint via `X-Varnish`/`Via: 1.1 varnish` response headers, then version-check against the fix. This is a genuine unauth primitive (not just a heuristic) — worth wiring into `recon_wcd.sh` as a dedicated version-gated check ahead of the generic path-confusion probes.
- Source: [SentinelOne CVE DB](https://www.sentinelone.com/vulnerability-database/cve-2026-34475/), [GitHub Advisory GHSA-m9gq-cmcj-p62x](https://github.com/advisories/ghsa-m9gq-cmcj-p62x)

- Jan 2026 PortSwigger research generalizes cache attacks around **URL/HTTP parser discrepancies between edge and origin** (not just path-suffix WCD), including chaining **cache-key confusion with a "non-exploitable" open redirect** to rewrite a cached static JS response for cross-domain execution. Companion OSS tool `CacheKiller` automates discrepancy discovery.
- **Actionable:** evaluate `CacheKiller` (github.com/PortSwigger/cache-killer) as a `recon_wcd.sh` companion for CDN-fronted in-scope hosts — broader technique class than our current path-confusion-only detector, still SAFE (own cache-buster key) if we honor its detect-only mode.
- Source: [PortSwigger preview](https://portswigger.net/research/a-hacking-hat-trick-previewing-three-portswigger-research-publications-coming-to-def-con-amp-black-hat-usa), [CacheKiller repo](https://github.com/PortSwigger/cache-killer)
