## 1. Race conditions — byte-limit-breaking sync + multi-endpoint substates (class-race-conditions)
Our doc stops at the 2023 single-packet-attack basics (20-30 reqs/packet). Two real gaps:
- **First Sequence Sync** (GMO Flatt Security, 2025) breaks the ~1,500-byte single-packet ceiling via IP fragmentation + deliberate TCP sequence-number reordering — sent 10,000 synchronized requests in ~166ms. This matters for our doctrine because it's what makes exhaustive OTP/PIN-space races (not just 20-30-attempt limit-overrun) unauth-safe-primitive-plausible at scale. PoC: `first-sequence-sync` repo (benchmark + PIN-bypass demo).
- **Multi-endpoint hidden-substate races** (PortSwigger, "Smashing the state machine") — a class beyond limit-overrun: race a login request against a request to a privileged endpoint to land in the window where a session is valid but MFA hasn't yet been enforced, or race checkout-validation against checkout-completion to land in the sub-state between "balance checked" and "balance debited." Endpoint-pairing signal, not single-endpoint.

## 2. Cognito User Pool — AuthFlow downgrade + writable custom-attribute privesc (class-cognito-unauth)
Our doc is scoped entirely to **Identity Pool** unauth credential issuance (the Logitech primitive). Genuinely separate surface: **User Pool** authentication-flow misuse — worth its own section since we already harvest Amplify configs.
- **AuthFlow downgrade**: client SPA/mobile JS may request `USER_SRP_AUTH` but the User Pool app client still permits `USER_PASSWORD_AUTH`/`ADMIN_NO_SRP_AUTH`. If the backend accepts a client-supplied `AuthFlow` param, swap it to `USER_PASSWORD_AUTH` and append a plaintext `PASSWORD` field — turns a protected SRP flow into a plain credential-stuffing/brute-force target. Check the app client's enabled auth flows (visible in a leaked `aws-exports.js`/`amplifyconfiguration.json` — same harvest path we already use for Identity Pool IDs).
- **Writable custom attributes → cross-tenant privesc (own-account PoC only, fits our active-PoC doctrine)**: several disclosed chains hinge on a `custom:*` attribute (e.g. `custom:m_id` / merchant ID, `custom:deployment_admin`) that the backend trusts for authorization but doesn't gate write access to. Test:
  1. `aws cognito-idp get-user --access-token <own-token>` — list your own custom attributes.
  2. `aws cognito-idp update-user-attributes --access-token <own-token> --user-attributes Name=custom:<attr>,Value=<other-value>` — own account only, harmless value first.
  3. Re-auth and observe if backend authorization now reflects the new value (only escalate to a real cross-tenant value if step 2 proves the field is unvalidated AND the target value is your own second account's — never a guessed/third-party tenant ID).
  - Root cause pattern: no pre-token Lambda trigger or server-side check re-validates Cognito attributes against the backend's own source of truth.
- ⚠️ CVE-2026-6911/6912 cited in secondary aggregators for "AWS Ops Wheel" — these are third-party product CVEs, not an AWS-service CVE; NVD-verify before citing, standard KB caveat.
