## 1. SSRF — protocol-scheme severity signal + GCP header-bypass + DNS-rebinding tooling (class-ssrf)

Three additions, none of which change our confirm primitive (still OOB-canary only via interactsh — never chase gopher/dict data past confirmation):

- **Protocol-scheme acceptance is a severity multiplier, not just a bypass.** If a sink lets you control the *scheme* (not just host/path), `gopher://`/`dict://` reachability means the backend can speak raw TCP protocols to internal services (Redis `FLUSHALL`/config-set, Memcached `stats`, SMTP relay) — far more severe than an HTTP-only fetch. We still only confirm via an `http(s)://<canary>.oast...` OOB ping per doctrine; but when reasoning about severity post-confirm, check whether the sink's URL parser accepts non-http schemes at all (many HTTP client libraries do by default) and note it in the report as a blast-radius indicator, not something we execute.
- **GCP metadata isn't always header-gated.** Some unpatched/legacy instances still serve `http://metadata.google.internal/computeMetadata/v1beta1/instance/service-accounts/default/token` **without** requiring `Metadata-Flavor: Google` (the v1beta1 legacy path predates the header enforcement). Worth a quick differential check (v1 vs v1beta1) when reasoning about a GCP target's actual exposure — updates our existing "all three clouds are header-gated" assumption with a caveat.
- **DNS-rebinding-as-a-service tooling exists for severity confirmation of TOCTOU sinks**: `1u.ms` (public rebinding service, e.g. `http://make-1.2.3.4-rebind-127.0.0.1-rr.1u.ms/`) and NCC Group's **Singularity** (self-hosted rebinding harness) automate the "resolve once for validation, resolve differently for fetch" attack our doc already flags conceptually. These are the concrete tools to reach for if a validate-then-fetch SSRF pattern is suspected and needs a rebinding PoC — still OOB-confirm discipline applies.

## 2. Race conditions — multi-endpoint alignment tricks + partial-construction race (class-race-conditions)

Our doc already has the single-packet Turbo Intruder primitive and endpoint-signal list. New, concrete additions for the operator-confirm step, sourced from PortSwigger's own Race Conditions methodology (authoritative — same source family already implicitly used):

- **Connection warming** — before firing the single-packet batch, send a few throwaway requests down the same connection first. This absorbs backend connection-setup jitter so the *real* batch lands tighter, needed on targets where the naive single-packet attack shows partial (not full) success.
- **Rate-limit-abuse-induced delay** — on a high-jitter target, deliberately trip a rate/resource limit with junk requests first; the resulting server-side backpressure widens the TOCTOU window enough for the single-packet batch to land inside it. Useful when a straight single-packet attempt against `/limit`/`/quota` endpoints from our signal list shows 0/20 success.
- **Session-based locking bypass** — some frameworks serialize concurrent requests *per session token* (defeating single-packet racing within one login). Sending the same race batch across N different session tokens (e.g. N accounts, or N refreshed tokens for the same account if the app allows concurrent sessions) sidesteps that serialization.
- **Partial-construction race** — a distinct sub-class from the balance/coupon races already listed: racing an object *during creation*, injecting empty-array (`param[]=`) or null values into a field mid-construction to catch an uninitialized-state window (e.g. a permissions/role field that briefly defaults to admin/empty-array-means-all before the real value is set). Worth adding to the endpoint-signal list wherever a multi-step "create" flow exists (registration, resource creation with role/permission fields).
