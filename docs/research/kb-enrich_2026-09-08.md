## 1. GraphQL — disabling introspection leaves 3 independent schema-disclosure paths open (`class-graphql.md`)
New CVEs show the field-suggestion technique we already use (Clairvoyance-style) isn't the only bypass — vendors keep shipping *separate* code paths that leak schema even when `__schema`/`__type` is blocked:
- **APQ registration echo** — Automatic Persisted Queries' registration response can echo back enough of the query shape to reconstruct schema fragments, independent of the introspection flag.
- **Alternate schema endpoints** — Directus **CVE-2026-35413**: a `/graphql/system` resolver (`server_specs_graphql`) returns a full SDL dump and was never wired to the same introspection-disable check as the main endpoint. Generalizable fingerprint: probe for a *second* GraphQL-ish endpoint (`/graphql/system`, `/graphql/admin`, `/internal/graphql`) when the primary one 403s introspection.
- **WebSocket subscription transport bypass** — Parse Server **CVE-2026-32594**: the GraphQL WS endpoint for subscriptions doesn't route through the same Express middleware stack, so introspection works over the WS upgrade even when blocked over HTTP. Check: if a host exposes a `graphql-ws`/`subscriptions-transport-ws` handshake, try `__schema` over that channel even if HTTP introspection is closed.
- **Inline-fragment nesting bypass** — Parse Server **CVE-2026-30854**: `__type` queries nested inside inline fragments (`... on Query { __type(name:"User"){name} }`) slipped past a naive string-match introspection filter. Cheap thing to always try even when a flat `{__schema{...}}` gets rejected.
All four are read-only/unauth-safe checks (schema recon only, no mutation) — fits our existing lane exactly, just widen the probe set beyond flat introspection + Clairvoyance suggestions.
Sources: [SentinelOne CVE-2026-35413](https://www.sentinelone.com/vulnerability-database/cve-2026-35413/), [GitLab Advisory CVE-2026-30854](https://advisories.gitlab.com/pkg/npm/parse-server/CVE-2026-30854), [dev.to APQ bypass](https://dev.to/roxdavirox/graphql-apq-registration-bypasses-query-allowlists-and-introspection-controls-20p2)

## 2. Cognito — the exact Amplify mechanism behind our proven win, now with a fingerprint (`class-cognito-unauth.md`)
Our doc already covers the Amplify→pool→unauth-creds chain (the Logitech win) but not the root-cause CVE, which gives a concrete unauth pre-check. **CVE-2024-28056** (Datadog Security Labs, disclosed 2024-04-15 — older than our usual window but the mechanism underpins our exact lane and isn't yet recorded): Amplify CLI-generated IAM trust policies omitted the Cognito identity-pool **audience (`aud`) restriction**, so any identity pool ID (harvested from JS/`.map`s, our existing method) can be used with Cognito's **Basic authflow + STS `AssumeRoleWithWebIdentity`** to assume the role with zero extra auth. Two vulnerable windows: legacy CLI projects (Jul 2018–Aug 2019) and an "auth component removed but role left behind" bug (Aug 2019–Jan 2024). Datadog found **8,000+ public IAM role ARNs** via the naming convention `authRole`/`unauthRole` — a cheap grep-able fingerprint on any harvested ARN. AWS patched Amplify CLI/Studio Jan 2024 and hardened STS cross-account assumption Apr 2024, but **same-account exploitation on legacy unpatched roles persists** — still worth testing on any pool discovered via our jsintel/sourcemap flow. Add `authRole`/`unauthRole` ARN-name grep to the discovery step, before the credential-issuance probe.
Source: [Mallory.ai summary of Datadog Security Labs research](https://www.mallory.ai/stories/019e59ea-36a4-79e9-9431-fa3fc572a19d)
