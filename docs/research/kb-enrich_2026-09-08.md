## 1. SQLi — JSON-wrapped payloads bypass WAF signature matching (`class-sqli`)
Claroty Team82 disclosed that major WAF vendors (Palo Alto, AWS, Cloudflare, F5, Imperva) don't parse JSON syntax in their SQLi signature engines, even though MySQL, PostgreSQL, SQLite, and MSSQL all natively execute SQL through JSON functions. Wrapping the injection inside a JSON function call (e.g. `' or JSON_LENGTH("{}") <= 8896 union distinctrow select @@version#`) slides past keyword/pattern signatures that would catch the bare `union select` form. All 5 vendors patched after disclosure, but plenty of unmanaged/self-hosted WAF rulesets won't have picked it up. Detection for our lane: on any host where our safe `'` vs `''` differential is blocked by a WAF page, retry the same differential with the payload JSON-wrapped before writing off the param as protected — this is a bypass check, not a new injection primitive, so it stays within our existing safe/non-destructive confirm flow. — [picussecurity.com](https://www.picussecurity.com/resource/blog/waf-bypass-using-json-based-sql-injection-attacks)

## 2. NoSQLi — nesting an operator inside `$or`/`$and` bypasses top-level-only sanitization (`class-nosqli`)
CVE-2025-23061 (GHSA-vg7j-7cwx-8wgw, CVSS 9.1) is a bypass of Mongoose's own fix for CVE-2024-53900: the original patch blocked `$where` only at the top level of a `populate().match` object, but Mongoose never recursed into arrays under `$or`/`$and`, so `{$or: [{$where: "..."}]}` still reached the query unfiltered — arbitrary JS execution in the query engine. Fixed in Mongoose ≥8.9.5/7.8.4/6.13.6. **Generalizable pattern for our lane, not Mongoose-specific:** any NoSQLi filter/sanitizer that denylists dangerous operators (`$where`, `$function`, `$accumulator`, `$expr`) by walking only the top level of the input object should be re-tested with the same operator nested one level deeper inside `$or`/`$and`/`$nor` — a very common blind spot in hand-rolled Express/Mongoose input sanitizers, not just this one library. Safe check: differential response/timing on `{"field":{"$or":[{"$where":"sleep(3000)"}]}}` vs the unnested form — a difference between the two proves the top-level-only gap even where the flat form is already blocked. — [GHSA-vg7j-7cwx-8wgw](https://github.com/advisories/GHSA-vg7j-7cwx-8wgw), [OPSWAT](https://www.opswat.com/blog/technical-discovery-mongoose-cve-2025-23061-cve-2024-53900)

## 3. IDOR/BOLA — batch/bulk endpoints authorize the endpoint, not each object in the array (`class-idor`)
A recurring real-world BOLA pattern: an endpoint accepting an array of object IDs (`POST /invoices/batch {"ids":[1,2,3]}`, bulk export, multi-delete, GraphQL mutations taking `ids: [ID!]!`) checks that the *caller* may call the batch endpoint at all, but never re-checks ownership of each individual ID inside the array — a single-object IDOR test on the same route can pass clean while the batch variant leaks. Directly actionable for our jsintel/endpoints ranker: any endpoint whose param/body schema has an array-of-IDs or array-of-object-ref shape should score at least as high as a single object-ref ID, and — where we already hold 2 owned IDs for human-confirm — the batch variant (`[own_id, own_id, other_owned_id]` mixed-array probe) is a distinct test from the single-ID swap, not a duplicate of it. Still human-in-the-loop / 2-owned-account only per our hard line; this just adds a shape to check for, not a new automated primitive. — [levo.ai: Why WAFs Fail Against BOLA/IDOR](https://www.levo.ai/resources/blogs/bola-idor-waf-fail)
