### IDOR/BAC — new patterns worth adding

**1. HTTP parameter pollution bypass.** Duplicate the object-ref param with different values; application logic processes first (victim's id) while validation sees only second (attacker's id). `?userId=VICTIM&userId=ATTACKER` — test both query-string AND JSON body. Source: [0xgaurang.medium.com](https://0xgaurang.medium.com/case-study-bypassing-idor-via-parameter-pollution-78f7b3f9f59d)

**2. UI/API authorization divergence.** Harbor CVE-2024-22278: the UI enforced role checks; the raw API endpoints had no authorization enforcement for `PUT/POST/DELETE /projects/{id}/metadatas/{meta_name}`. Systematic probe: find every UI-blocked action → replay the raw API endpoint as lower-priv. Source: [unit42](https://unit42.paloaltonetworks.com/bola-vulnerability-impacts-container-registry-harbor/)

**3. WebSocket IDOR.** Object-ref IDs in WebSocket/real-time message payloads are almost never tested. Swap the `id` field in WS frames — auth checks on HTTP path ≠ auth checks in WS message handlers.

**4. Multi-step purchase-flow IDOR.** Purchase → confirmation → receipt = object IDs returned at step N, consumed at N+1 without re-validation. Intercept mid-flow and substitute another account's order/invoice ID.

**5. JWT `sub` claim IDOR.** Unsubscribe/preference endpoints decode the token's `sub` claim to derive the user, but don't re-check that the action's target matches the caller. Source: [ajakcybersecurity.medium.com](https://ajakcybersecurity.medium.com/exploiting-jwt-token-leads-to-idor-ec48cb8888bb)

### GraphQL — new patterns worth adding

**1. Introspection bypass via fragment obfuscation (2024, CVE-2024-37155).** Beyond our existing whitespace/`\n` bypass: query fragments (`...on Query { __schema { ... } }`) evade regex-based block filters that look for `__schema` at the query root. Source: [dailycve.com](https://dailycve.com/opencti-graphql-introspection-restriction-bypass-cve-2024-37155-moderate-dc-jun2026-542/)

**2. GraphQLer — dependency-graph based testing (2025).** Builds a dependency graph between queries/mutations/types from real API responses, then chains operations to reach authorization flaws unreachable by static probes. Detected 11 vulns vs 3 by EvoMaster in comparative research. Source: [arxiv.org/abs/2504.13358](https://arxiv.org/html/2504.13358v1)

**3. Subscription endpoint leakage.** WebSocket upgrade for subscriptions often bypasses the same auth middleware applied to HTTP. Test subscriptions independently — token exposure in WS handshake + missing auth re-check on the WS channel.

**4. Strawberry GraphQL multipart CSRF (CVE-2024-47082).** Multipart upload enabled by default in the Django integration → CSRF protection bypassed. Affects Strawberry < 0.243.0. Source: [github.com/advisories/GHSA-79gp-q4wv-33fr](https://github.com/advisories/GHSA-79gp-q4wv-33fr)

**5. Content-Type mutation bypass.** Our graphql-cop already checks `get_based_mutation` + `post_based_csrf` — but the actionable escalation: when the server accepts `application/x-www-form-urlencoded` and processes mutations, it likely bypasses CORS+CSRF protections on modern stacks. Combine with a SENSITIVE mutation (not `__typename`) for a real finding.

### GraphQLer — dependency-graph based testing (2025)
**GraphQLer** (https://arxiv.org/html/2504.13358v1) constructs a dependency graph between queries,
mutations, and object types from REAL API responses at runtime, then chains operations to reach
authorization flaws that require a specific sequence (e.g. create object → query it → mutate with its
ID). Traditional tools (static + single-operation probes) miss multi-step auth escalations.

Benchmark: 11 unique vulnerabilities found vs 3 by EvoMaster on the same targets.

**Practical use:** on a complex GraphQL API, run GraphQLer in read-only/recon mode to map the dependency
graph, then hand the chained worklist to the operator for the human-confirm step. Supplement our
existing introspection→rank pipeline for APIs where multi-step object creation is required before IDOR
can be demonstrated.

Note: GraphQLer sends actual mutations (needed to build the dependency graph). This makes it
OPERATOR-ONLY, not autonomous — run under supervision on confirmed in-scope+paying targets.

Source: https://arxiv.org/html/2504.13358v1

### Subscription endpoint leakage
WebSocket-based GraphQL subscriptions are often wired through a DIFFERENT server-side path than the
HTTP POST endpoint — and that path may skip the same auth middleware. Two-vector surface:

1. **Missing auth on the WS upgrade** — subscribe without an Authorization header; if the server
   accepts the WS connection and sends subscription events, auth is missing on the channel.
2. **Token exposure in the handshake** — subscription connections carry the auth token in a graphql
   `connection_init` message over WS; intercept this to harvest the token format/structure for
   other tests.

Signal: any GraphQL schema with `Subscription` types = a surface to probe with a bare WS upgrade
(`websocat ws://host/graphql` + `{"type":"connection_init","payload":{}}` + subscribe payload without auth).

### Strawberry GraphQL multipart CSRF (CVE-2024-47082)
Strawberry GraphQL (Python) < 0.243.0 + Django integration: multipart file upload is **enabled by
default**, bypassing Django's CSRF protection. An attacker page can POST a `multipart/form-data`
mutation to a victim's authenticated session.

**Hunt signal:** `graphql-cop` `post_based_csrf` + engine fingerprint = Strawberry/Python → check
version + confirm multipart is enabled. Any state-changing mutation behind a Strawberry endpoint
< 0.243.0 is a CSRF target.

Source: https://github.com/advisories/GHSA-79gp-q4wv-33fr

### Content-Type mutation bypass → real CSRF escalation
Our lane already detects `get_based_mutation` and `post_based_csrf` (via graphql-cop) as structural
flags. The escalation path for a real finding (not just a theoretical CSRF note):

1. Confirm the server accepts `application/x-www-form-urlencoded` or `multipart/form-data` for mutations
   (graphql-cop `post_based_csrf` = YES).
2. Identify a **SENSITIVE mutation** in the schema (not `__typename`) — password reset, account change,
   payment action, role grant.
3. Craft a cross-origin HTML form that POSTs the mutation; confirm it executes as the victim's session
   without the custom Content-Type + CORS preflight.
4. THIS is the reportable finding — not the "CSRF possible" flag alone. Impact = the mutation's impact.

Per the FP/dup section: theoretical CSRF without a real sensitive op behind it = N/A. The gate is step 2.

Source: https://checkmarx.com/blog/whats-old-becomes-new-again-csrf-attacks-on-graphql-apis/

### Apollo Router CVE-2025-32032 (query planner DoS)
Apollo Router < 1.61.2 / < 2.1.1: deeply nested queries with repeated named fragments exhaust the
query planner's optimization phase — 5–10 concurrent requests cause full DoS. Only relevant if:
(a) the program pays DoS AND (b) the endpoint runs Apollo Router. For most programs this is OOS/Info;
note it as a LEAD if the engine fingerprint = Apollo Router and the version is in range.

Source: https://gbhackers.com/apollo-router-vulnerability/
