# Research digest — tooling — 2026-09-06

## 1. ACTIONABLE — Next.js May 2026 security release (13 CVEs) — feeds n-day lane + matches our doctrine directly
Next.js sits in our top in-scope tech list and we already carry `tech-nextjs.md`, but this coordinated release (patched Next.js **15.5.18 / 16.2.6**, some issues fixed earlier at 15.5.16/16.2.5) hasn't been version-reasoned into our worklist yet. Several of the 13 advisories map to our **chain-to-impact** primitives directly rather than being version-only Info:

- **CVE-2026-44578 — SSRF via WebSocket upgrade handler** (CVSS 8.6). Self-hosted Next.js (built-in Node server) `13.4.13 – <15.5.16` and `16.0.0 – <16.2.5`. **Vercel-hosted deployments are NOT affected** — hard gate before flagging a target. A single unauthenticated HTTP request with `Upgrade: websocket` + `Connection: Upgrade` headers makes the server issue an internal GET to an attacker-chosen host:80 and return the response — this is a **textbook fit for our existing interactsh OOB-canary SSRF confirm primitive** (point it at our canary, callback = definitive, never `file://`/internal data). [Sentinel­One](https://www.sentinelone.com/vulnerability-database/cve-2026-44578/) · [Hadrian](https://hadrian.io/blog/next-js-websocket-ssrf-unauthenticated-access-to-internal-resources-cve-2026-44578-2) · [Horizon3.ai](https://horizon3.ai/attack-research/vulnerabilities/cve-2026-44578/)
- **Three middleware/App-Router bypass advisories** (bundled under CVE-2026-23870's release, exact CVE IDs per-advisory) — **auth bypass shape**, which per our own TRANSITION GATE doc is in the `ALWAYS_MINT` exemption list (not a state-observation, a confirmed primitive). Same family as the well-known CVE-2025-29927 middleware bypass we should already be checking for.
- **SSRF/cache-poisoning/XSS rounding out the 13** — cache poisoning maps to `recon_wcd.sh`, XSS (CSP-nonce bypass, `beforeInteractive` script XSS) maps to our XSS lane's confirm-via-execution gate. [Vercel changelog](https://vercel.com/changelog/next-js-may-2026-security-release) · [Netlify writeup](https://www.netlify.com/changelog/2026-05-08-react-nextjs-security-vulnerabilities/) · [webhani summary](https://www.webhani.com/blog/nextjs-security-release-may-2026)

**Verdict: ADOPT into `recon_nday.sh` version-reasoning** — add this CVE cluster (with the self-hosted-only gate on the SSRF one) to the Next.js version-check table, and route a confirmed-in-range SSRF hit straight to the interactsh confirm primitive we already run for other SSRF leads (no new tooling needed — this is a target/version-list update, not a new tool). Standalone scanner repos exist (`nextjs-cve-2026-23870-checker`, `NextSecureScan`) but are unnecessary — our own version-fingerprinting + interactsh primitive already covers detection+confirm; don't add a redundant dependency.

## 2. EVALUATE — `hahwul/jwt-hack` — fills a real tooling gap (we carry `class-jwt-attacks.md` but no wired tool)
- **What it is:** JWT attack/analysis CLI+API-server toolkit — `alg:none`, RS256→HS256 confusion, `jku`/`x5u` header attacks (built-in JWKS server for redirect-style attacks), `kid` header injection, JWE probing, signature malleability, claims tampering, dictionary/brute-force secret cracking. Go, MIT, 1.1k★, 705 commits.
- **Why it's worth a look:** **same author as `dalfox`**, which we already run and trust for our XSS confirm primitive — hahwul has a track record of tools that fit our unauth-safe/CLI-pipeline shape rather than GUI/Burp-extension tooling. `ticarpi/jwt_tool` is the more battle-tested incumbent in the space (older, larger footprint) if a second opinion is wanted, but jwt-hack is the leaner CLI that composes more naturally into a shell pipeline.
- **Doctrine fit:** the attack modes here (alg confusion, kid injection, jku/x5u) are all **detection-of-a-forgeable-primitive** — you craft a token and see if the app accepts it, which is the same "primitive fires = confirmed" shape as our other confirm steps, not a destructive action. Every one of these still needs a live app response to matter (not a mint-on-state case).
- **Verdict: EVALUATE** — no `recon_jwt.sh` lane exists today; JWTs surface incidentally via jsintel/params mining on our targets. Worth a manual trial against a target with visible JWT auth (kid/jku headers in the token, or an RS256 API) before deciding whether it's worth a dedicated lane vs. staying an on-demand tool for authed hunts.
