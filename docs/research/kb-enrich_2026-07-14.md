## Key findings (SSRF)

1. **IMDSv2 is NOT a hard stop — it's conditional on primitive richness.** IMDSv2 requires a `PUT
   /latest/api/token` handshake before the token-bearing `GET`. An SSRF primitive that only controls
   the URL (method fixed to GET, no custom headers) genuinely can't complete the handshake. But an
   SSRF that lets the attacker control **method + headers** (webhook configs, HTTP-client wrappers,
   proxy/fetch features) CAN do the PUT+GET dance itself. Real 2025 case: Typebot.io webhook block
   (Nov 2025) leaked EKS node-role creds through IMDSv2 this way. **Actionable for our ranker:** don't
   downgrade a webhook/fetch-configurable sink just because "IMDSv2 blocks it" — check whether the
   sink exposes method/header control first.
2. **Multi-cloud metadata, not just AWS 169.254.169.254/latest/meta-data/.** GCP
   (`http://metadata.google.internal/computeMetadata/v1/` — needs `Metadata-Flavor: Google` header,
   another method/header-control-dependent case), Azure (`http://169.254.169.254/metadata/instance?api-version=...`
   — needs `Metadata: true` header). A canary-only OOB confirm doesn't need the cloud-specific header,
   but knowing the header requirement matters when reasoning about severity/exploitability post-confirm.
   Also: newer AWS services (e.g. Bedrock AgentCore Runtime's MMDS) have shipped WITHOUT IMDSv2-style
   token enforcement (Unit 42 disclosure, 2025) — a service-specific metadata endpoint is a fresh
   fingerprint to check for on any AWS-hosted target running newer managed AI/compute services.
3. **New/underused sinks — the actual attack surface expansion:**
   - **SVG upload → image processor (ImageMagick etc.) SSRF.** SVG is XML; an `<image href="http://169.254.169.254/...">` (or interactsh URL) embedded in an uploaded SVG gets server-side-fetched when the processor rasterizes/thumbnails it. Any avatar/logo/document-upload feature that accepts SVG is a candidate — distinct from the classic "URL param SSRF," no visible URL param needed at all.
   - **PDF generators** (wkhtmltopdf, Puppeteer/headless-Chrome-to-PDF, WeasyPrint) — anywhere user HTML/URL is rendered to PDF, external resource refs (`<img src>`, `@import`, `iframe`) are server-fetched. Classic bounty-worthy pattern (Intigriti's dedicated guide); check invoice/report/export-to-PDF features.
   - **Webhook config + URL-preview/unfurl features** — often not linked in the UI, only discoverable via JS (fits our jsintel-mined endpoint surface directly — flag any endpoint whose param/body looks like `webhookUrl`/`callbackUrl`/`previewUrl`/`importUrl`).
4. **URL-parser confusion is still the core bypass class**, not a specific payload list: the
   validator and the actual HTTP client parse the URL differently (userinfo `@` tricks, backslash
   normalization, unicode/IDN homoglyphs, `#` fragment truncation). Treat allowlist/blocklist-based
   SSRF filters as inherently bypassable rather than a "protected" signal.
5. **DNS rebinding / TOCTOU** — validate-then-fetch flows that resolve DNS once for the check and
   again for the actual request (separate resolution steps) are rebindable. Craft CMS's GraphQL Asset
   mutation SSRF advisory is a disclosed real-world instance of exactly this pattern.
