### 1. Real 2025/2026 disclosed BOLA case (airline GraphQL API) — concrete methodology proof
A disclosed red-team writeup shows the exact "rank IDOR-arg candidates → test unauth" flow our lane already encodes, working end-to-end: sequential-integer `bookingRetrieveByBookingId(bookingId: N)` resolver, reachable **without auth**, returned a different customer's full PII (DOB, masked card, 2-year itinerary) on every sequential ID. Anonymous session also had **428 mutations** exposed via introspection, including `flightDelete`/`priceOverride`/`contactsChange` — i.e. write access, not just read. Confirms our ranking spine (mutations-first, sequential-ID boost, unauth-gate test) matches how real bugs are found; worth citing as a training example.
— [Wiz: Red Agent POV — Exploiting BOLA in an Airline GraphQL API](https://www.wiz.io/blog/red-agent-pov-bola)

### 2. GraphQL-specific mutation-input bypass: array-wrapping and mass assignment (NEW pattern, distinct from REST)
Two GraphQL-native authz-bypass shapes not yet in our doc (the existing REST-side array/JSON-coercion section in `class-idor.md` doesn't cover the GraphQL mutation-variable variant):
- **Array-wrap a scalar ID variable**: sending a delete/update mutation's `id` variable wrapped in an array (`ids: [victimDocId]` instead of `id: victimDocId`) can skip an ownership check written for the scalar case while the resolver still processes element `[0]`.
- **Mass assignment via full input types**: mutations that accept a broad `*Input` object (e.g. `updateProfile(input: UserInput)`) and persist it without field allowlisting let a caller set fields like `role`/`isAdmin` that the UI never exposes — same class as REST mass-assignment but reachable purely via the exposed schema (no source needed, introspection hands you the field list).
— [DEV: Authorization Bypass in GraphQL — Reproduction and Detection](https://dev.to/crud5th-273-/authorization-bypass-in-graphql-reproduction-and-detection-techniques-893)

### 3. Concrete alias-batching brute-force example + what "protected" looks like
Confirmed concrete payload for the alias-batching class already in our tool table (`graphql-cop alias_overloading`), useful for recognizing real exploitation beyond the detection probe:
```graphql
mutation {
  login(username: "Tom", password: "password")
  second: login(username: "Tom", password: "password123")
  third: login(username: "Tom", password: "TomTheBest")
}
```
N aliased calls = N credential/OTP attempts in ONE HTTP request, invisible to per-request rate limiters (rate limiters see 1 call, not N resolver executions). Defense signature to recognize: **GraphQL Armor** (or any alias/depth-limit middleware) caps aliases-per-field (commonly default 1) — if a target rejects >1-2 aliases with a limit error, it's hardened; don't waste further alias-based batching attempts there.
— [Escape.tech: Avoid GraphQL DoS via batching/aliasing](https://escape.tech/blog/graphql-batch-attacks-cause-dos/)

### Real disclosed auth-bypass case (reinforces existing "test every mutation unauth" methodology)
A HackerOne-disclosed bug found an unauthenticated `CreateAdminUser` mutation reachable directly at the
GraphQL layer (the mutation was meant to be internal-service-only, gated by network position, not
GraphQL-level auth — the schema exposed it anyway). Confirms the existing methodology in this doc
("re-run the high-value op list UNAUTHENTICATED") is the correct and sufficient test — no new primitive
needed, just don't skip auth-mutation names (`register`, `resetPassword`, `changeEmail`, `*admin*`) when
enumerating the unauth-reachable set.
