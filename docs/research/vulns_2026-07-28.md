## 1. CVE-2026-34475 — Varnish Cache auth-bypass/cache-poisoning — full detail (completes 07-28 supplemental cutoff)
- **What:** CWE-180 (validate-before-canonicalize failure) in HTTP/1.1 absolute-form URI parsing. If a backend accepts absolute-form request targets and `req.url` is passed to it unchecked, a crafted request can poison the cache or bypass URL-based auth controls.
- **Severity:** CVSS 5.4 (Medium) — narrower than earlier framing suggested. **Attack surface is limited to root `/` paths** (`https://example.com/` only, not `/whatever`) — a real constraint on exploitability.
- **Affected:** Varnish Cache < 8.0.1, Varnish 6.0 LTS < 6.0.17, Varnish Enterprise < 6.0.16r12. Fixed versions released 2026-03-16 — this has been patched for ~4 months, so unpatched instances now are laggards, a decent signal.
- **Detect (unauth):** Varnish doesn't reliably banner its version; look for `X-Varnish`/`Via: varnish` response headers as presence-fingerprint (version itself isn't disclosed by the header — treat as tech-match, not confirmed-in-range, per KEV-tech-class doctrine). No PoC or active exploitation reported as of this search.
- **Action:** LEAD only (tech-class + no version confirmation possible remotely) — same as existing doctrine, no P0 upgrade. Not urgent to prioritize a sweep given no PoC/no ITW and the narrow `/`-only surface.
- **Sources:** [SentinelOne](https://www.sentinelone.com/vulnerability-database/cve-2026-34475/), [GitHub Advisory GHSA-m9gq-cmcj-p62x](https://github.com/advisories/GHSA-m9gq-cmcj-p62x), [Varnish VSV00018](https://vinyl-cache.org/security/VSV00018.html), [NVD](https://nvd.nist.gov/vuln/detail/CVE-2026-34475)

## 2. Origin-IP discovery via apex/www split-DNS scan — new enumeration technique for our existing CDN-bypass lane
Checked `docs/knowledge/class-cdn-origin-bypass.md` — this technique isn't in it yet. A disclosed methodology: bulk-check whether a domain's apex (`example.com`) and `www` subdomain resolve to **different IPs** — legacy orgs often keep apex DNS on old infra (MX/routing) while only `www` fronts through Cloudflare, leaking the real origin via the apex A record. One published sweep found 30+ confirmed exposures out of ~40k domains checked this way — a cheap, high-signal passive check (DNS only, zero target traffic) we don't currently run.
- **Action:** add to the origin-discovery techniques list — cheap `dig`/passive-DNS diff of apex vs `www` A records across our in-scope root domains, flag mismatches as origin-IP candidates, feed into the existing CloudFlair-style verification primitive already in the KB.
- **Source:** [Cloudflare-Bypass: Origin server deserves some love too](https://medium.com/@smitgharat0001/cloudflare-bypass-origin-server-deserves-some-love-too-e8bd2182cfea)
