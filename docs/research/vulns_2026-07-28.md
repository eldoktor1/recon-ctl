# Research digest — vulns — 2026-07-28 (supplemental #2)

## 1. CORRECTION — CVE-2026-23918 (Apache HTTP/2 double-free) is UNAUTHENTICATED, not auth-required as prior digest stated ★ top-tech impact
- Our 2026-07-25 digest flagged this as "trigger requires an authenticated network attacker." UC Berkeley ISO's advisory language does not gate exploitation on auth — re-verified via fetch: **RCE requires Apache 2.4.66 built with APR configured for the `mmap` allocator** (common on Debian-derived systems / default httpd Docker images); **DoS requires `mod_http2` + a multi-threaded MPM** (worker/event) — no auth barrier stated for either path.
- **Affected:** Apache HTTP Server 2.4.66 only. Fixed in 2.4.67.
- **Detect (unauth, in-range-verifiable):** `Server: Apache/2.4.66` banner (suppressed on many hardened hosts — treat absence as unknown, not clean); presence of HTTP/2 (`h2` in ALPN/`alt-svc`) narrows to the DoS precondition. mmap-allocator precondition is not remotely fingerprintable — treat RCE path as version-range LEAD, DoS path as version+protocol-range LEAD. No PoC crash probe should be run (DoS is out of bounds for our safe-probe doctrine — worker crash is a real availability hit).
- **Action:** re-scan ES for any `Server: Apache/2.4.66` hits and re-flag from "authed-only, low value" to a genuine unauth n-day LEAD.
- **Sources:** [security.berkeley.edu](https://security.berkeley.edu/news/critical-apache-2466-http2-flaw-allows-rce-dos-cve-2026-23918), [CVE-2026-23918 NVD](https://www.cve.org/CVERecord?id=CVE-2026-23918), [csa.gov.sg advisory](https://www.csa.gov.sg/alerts-and-advisories/alerts/al-2026-049/)

## 2. NEW — Varnish Cache CVE-2026-34475: auth-bypass / cache-poisoning detail (matches our fingerprinted `tech-varnish`)
- **What:** CWE-180 (validate-before-canonicalize) flaw in HTTP/1.1 request-line parsing — a request whose URL path is exactly `/` (absolute-form, e.g. `GET http://example.com/ HTTP/1.1`) is mishandled by `req.url` in VCL, so if VCL passes `req.url` unchecked to a backend that accepts absolute-form URIs, an attacker can poison the cache or bypass URL-based auth checks. Narrow surface: **only root-path (`/`) requests are affected**, not arbitrary paths.
- **Affected:** Varnish Cache < 8.0.1, Varnish Cache 6.0 LTS < 6.0.17, Varnish Enterprise < 6.0.16r12.
- **Fixed:** 8.0.1 / 6.0.17 / 6.0.16r12 (all released 2026-03-16 — this CVE is ~4 months old but still worth a version pass since we haven't covered it before).
- **Detect (unauth, in-range-verifiable):** `Server: Varnish` / `X-Varnish` / `Via: varnish` header at the root path; version usually not banner-disclosed — treat any Varnish-fingerprinted host as version-unknown-in-range LEAD unless we can pull the version elsewhere (admin/CLI banner, error page). Safe non-destructive test: send `GET http://<host>/ HTTP/1.1` in absolute-form (own cache-buster, never poison the real shared cache — same discipline as `recon_wcd.sh`) and diff cache behavior; do NOT test against the live production cache key.
- **Pipeline fit:** this is a Varnish-specific instance of our existing WCD lane pattern (`recon_wcd.sh`), not a new tool — add as a version-gated check when a Varnish-fingerprinted host is queued for `recon-wcd`.
- **Sources:** [SentinelOne CVE-2026-34475](https://www.sentinelone.com/vulnerability-database/cve-2026-34475/), [GitHub Advisory GHSA-m9gq-cmcj-p62x](https://github.com/advisories/ghsa-m9gq-cmcj-p62x), [Ubuntu CVE-2026-34475](https://ubuntu.com/security/CVE-2026-34475)
