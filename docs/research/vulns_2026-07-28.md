# Research digest — vulns — 2026-07-28 (third pass)

## 1. CVE-2026-7261 — PHP SOAP `SoapServer` Use-After-Free, CVSS 9.8 — companion bug to CVE-2026-6722 (07-25 digest), **already under active scanning** ★★
- **What:** UAF in `SoapServer` when `SOAP_PERSISTENCE_SESSION` is enabled — persistence logic frees the handler object on a SOAP request that errors, but a dangling pointer to it survives; a follow-up request reclaims that memory → memory corruption / info-disclosure / crash, RCE-capable.
- **Distinct from CVE-2026-6722** (object-dedup map UAF in `apache:Map` deserialization, flagged 07-25) — both landed in the **same PHP security release** (8.2.31 / 8.3.31 / 8.4.21 / 8.5.6), same affected-version bands. Treat as two independent SOAP-surface bugs, both in-range on the same version fingerprint.
- **Urgency:** BitNinja reports automated internet-wide scanning for vulnerable SOAP endpoints spiked within 72h of patch release — disclosure-to-exploitation window has collapsed to days, not weeks.
- **Detect (unauth, in-range-verifiable):** identical to CVE-2026-6722 — `?wsdl`, `Content-Type: text/xml`/`application/soap+xml`, `SOAPAction` header, or WSDL file in jsintel/fulltext ES corpus, combined with PHP version disclosure (`X-Powered-By`, error banners). `SOAP_PERSIST` usage isn't remotely fingerprintable, so presence of a SOAP endpoint + in-range PHP version = LEAD (not confirmed exploitable without knowing the persistence config).
- **Action:** widen the existing `recon-nday` SOAP/WSDL sweep (built for CVE-2026-6722) to flag both CVEs on the same hit — no new detection logic needed, just tag both CVE IDs.
- **Sources:** [SentinelOne](https://www.sentinelone.com/vulnerability-database/cve-2026-7261/), [BitNinja](https://bitninja.com/blog/cve-2026-7261-urgent-update-for-php-users/), [Strix.ai CVE record](https://www.strix.ai/cve/CVE-2026-7261)

## 2. CVE-2026-34475 — Varnish Cache auth-bypass/cache-poisoning — full mechanism now confirmed (extends 07-28 supplemental #2) ★ matches `tech-varnish`
- **Mechanism (CWE-180, validate-before-canonicalize):** Varnish mishandles HTTP/1.1 requests with **absolute-form URI whose path is exactly `/`** (e.g. `GET http://example.com/ HTTP/1.1`) when `req.url` is passed unchecked to a backend that accepts absolute-form URIs. Attack surface is narrow — root URL only (`https://example.com/`), not `https://example.com/whatever`.
- **Affected:** Varnish Cache < 8.0.1 and < 6.0.17 (LTS); Varnish Enterprise < 6.0.16r12.
- **Fixed:** Varnish Cache 8.0.1, 6.0.17 LTS; Varnish Enterprise 6.0.16r12.
- **Detect (unauth):** `Via: varnish` / `X-Varnish` response headers give the fingerprint; version is not usually banner-disclosed, so treat any Varnish-fronted in-scope host as version-unknown-LEAD unless a version string leaks (VCL error page, `Server:` on backend passthrough). PoC test would be sending an absolute-form root request and diffing cache behavior — this is a **live cache-poisoning test against production traffic**, out of bounds for autonomous unauth probing per our cache-deception safety doctrine (own-cache-buster only). Human-confirm only, on an owned test path.
- **Sources:** [SentinelOne](https://www.sentinelone.com/vulnerability-database/cve-2026-34475/), [Varnish VSV00018 advisory](https://vinyl-cache.org/security/VSV00018.html), [GitHub Advisory GHSA-m9gq-cmcj-p62x](https://github.com/advisories/GHSA-m9gq-cmcj-p62x)
