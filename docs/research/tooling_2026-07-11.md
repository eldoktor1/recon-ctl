# Research digest — tooling — 2026-07-11

## Tooling Watch — 2026-07-11

**Bottom line: no clear adopts this run.** Surveyed JS-endpoint mining, IDOR/BOLA scanners, secrets scanning, S3/bucket scanning, and HTTP request smuggling. Nothing beats what we run; one genuine gap (request smuggling) surfaced but carries a doctrine conflict that needs an operator call before any adoption, not a tooling one.

### 1. Nosey Parker (praetorian-inc) — SKIP (dead project)
Rust AST/entropy secrets scanner, previously well-regarded (faster than TruffleHog/Gitleaks on large corpora, high-precision 188-rule set, cross-match dedup). **Archived by Praetorian on 2026-04-24 — read-only, no further commits.** Also lacks TruffleHog's live-verification-against-provider-API step, which is the exact feature (`--only-verified`) our JS-intel lane depends on to kill the 53%-FP token-shaped noise. No reason to switch off a maintained tool for an abandoned one.
Sources: [praetorian-inc/noseyparker](https://github.com/praetorian-inc/noseyparker), [Praetorian blog](https://www.praetorian.com/blog/nosey-parker-ai-secrets-scanner-release/), [Rafter secret-scanner comparison](https://rafter.so/blog/secrets/secret-scanning-tools-comparison)

### 2. JShunter / JSpider — SKIP (regression, not upgrade)
Newer JS-endpoint-extraction CLIs surfaced in searches, but both are regex/pattern-based extractors. Our jsluice (AST-based, extracts by usage not just shape) already catches dynamically-constructed routes these tools structurally can't see — this is a downgrade, not an upgrade. No action.
Sources: [cc1a2b/JShunter](https://github.com/cc1a2b/JShunter)

### 3. Automated Burp IDOR/BOLA extensions (Auto-IDOR-Hunter, BurpAPISecuritySuite, "zero-config BOLA/IDOR" Rust tool) — SKIP (doctrine conflict, not just dup-trap)
Several 2025/2026 tools do automated ID mutation/fuzzing + session-swap detection for IDOR/BOLA. These are structurally incompatible with our hard line: IDOR confirmation requires **two accounts the researcher owns**, never guessed/enumerated third-party IDs. A tool built to auto-mutate object-ref IDs across a target will, by design, touch IDs we don't own the moment it's pointed at anything live. Not adopting; the human-in-the-loop 2-account swap stays the only sanctioned confirm path for this class.
Sources: [SecureByChaos/Auto-IDOR-Hunter](https://github.com/SecureByChaos/Auto-IDOR-Hunter), [Teycir/BurpAPISecuritySuite](https://github.com/Teycir/BurpAPISecuritySuite)

### 4. YES3 Scanner (FogSecurity) — SKIP (wrong threat model for us)
A newer (103★, active commits through 2026) S3 posture scanner covering ransomware-resilience checks (Object Lock, versioning, lifecycle policy) beyond plain ACL/public-read grading. Looked promising as an S3Scanner complement, but it **requires AWS credentials for the target account** — it's a defensive self-audit tool for bucket *owners*, not an unauthenticated external hunter. Doesn't fit our provenance-confirmed, unauth-only bucket lane at all.
Sources: [FogSecurity/yes3-scanner](https://github.com/FogSecurity/yes3-scanner)

### 5. HTTP request smuggling — genuine CATEGORY GAP, but needs an operator scoping decision before EVALUATE
We run no smuggling/desync detection lane at all. Two live options:
- **PortSwigger `http-request-smuggler` v3.0** (2025) — added parser-discrepancy detection that bypasses common desync defenses; most actively maintained, but it's a Burp extension (manual, GUI-driven — doesn't fit our headless-daemon pipeline).
- **`danielthatcher/smuggles`** (Go CLI, 25★, low-traffic-per-host random-order scanning designed for scanning at scale, resumable) — fits our automation model better, but low star count and unclear recent-commit cadence mean maintenance confidence is weak.

The real blocker isn't tooling, it's doctrine: request smuggling detection works by desyncing the front-end/back-end connection pool, which **can poison or leak *other users'* in-flight requests on shared infrastructure** — a different risk class than our current unauth-safe/non-destructive primitives (GET/HEAD/OPTIONS, OOB canary, math-only SSTI). That's a third-party-impact question, not a tool-selection one. Recommend: don't adopt either tool yet; if the operator wants this lane, it needs an explicit scope/safety carve-out (like the archive-egress or active-PoC doctrine entries) before any tool gets wired in.
Sources: [PortSwigger/http-request-smuggler](https://github.com/PortSwigger/http-request-smuggler), [danielthatcher/smuggles](https://github.com/danielthatcher/smuggles), [defparam/smuggler](https://github.com/defparam/smuggler)
