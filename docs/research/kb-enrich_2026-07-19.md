### 3. Second-order SQLi — a distinct test our single-pass differential misses entirely
Our confirm primitive (immediate `'`/`''` on the same param/response) only catches FIRST-order SQLi.
Second-order: a payload stored harmlessly via one endpoint (registration field, profile name, address
line, support-ticket subject) gets pulled unsanitized into a DIFFERENT query at a DIFFERENT endpoint
later (login, admin dashboard render, export/report generation, search-by-stored-field).
**Test approach (own-account only, consistent with our 2-account/own-data discipline):**
1. Register/create a record with a boolean-differential-style payload (`'||(SELECT ...)||'`-shaped,
   inert on write) in every writable string field.
2. Walk the app normally afterward — login, view profile, trigger admin-visible operations, exports,
   search that reads the stored field back into a query (not just renders it — that's XSS territory).
3. Compare timing/error/content behavior at the SECOND site vs a control record with a benign value.
**Why it matters for us:** automated single-request scanners (and our own real-time differential)
structurally cannot catch this — it requires state that persists across two separate requests. Add
as an explicit manual step in the on-demand `recon-params confirm sqli` SOP when the direct differential
comes back clean but the host has multiple stored-then-displayed-elsewhere fields (profile name → order
history, ticket subject → admin queue, etc).
Sources: https://portswigger.net/kb/issues/00100210_sql-injection-second-order , https://bugbounty.info/Attack-Surface/Web/Injection/SQLi/Second-Order , https://www.comolho.com/bug-bounty-glossary/second-order-sql-injection
