# Research digest — tooling — 2026-09-03

## 1. ADOPT — `PortSwigger/jwt-editor` (official Burp Suite JWT extension)
- **What it is:** PortSwigger's own Burp Suite extension for JWT manipulation — detects JWTs in HTTP/WebSocket traffic, edits/signs/verifies/encrypts/decrypts, and **automates the canonical JWT attack primitives**: `alg:none`, HMAC key-confusion (RS256→HS256 using the public key as the HMAC secret), embedded-JWK header injection, empty-HMAC-secret (CVE-2019-20933), ECDSA "psychic signatures" (CVE-2022-21449), Collaborator-based header-processing tests, and weak-secret brute-force.
- **Why it matters to us:** we have a `class-jwt-attacks.md` KB topic but **no dedicated JWT tool** in the current stack — JWT testing has been ad hoc. This is official PortSwigger tooling (751 commits, 53★/11 forks, latest release 2.6.1 tagged 2026-04-19 — actively maintained, not a toy), and it slots directly into our Burp-first workflow (`reference_burp_mcp_and_automation` — "ALWAYS use Burp to the max"). Every attack it automates is a *test primitive*, not a blind exploit — fits our confirm-don't-guess posture.
- **Alternative considered:** `chawdamrunal/JWTLens` (55★, single author, updated Mar 2026, 62 checks incl. passive scanning) — more checks on paper, but single-author/less-established vs. PortSwigger's official repo. Not worth running both; jwt-editor is the safer pick for a Burp-centric flow.
- **Doctrine fit:** unauth-safe for the passive/detection checks ✅; the forge/replay attacks are the same class as our other "confirm-the-primitive" tests — use human-in-the-loop the same way we already gate authed testing (fires only against in-scope+authorized targets, via the operator's Burp session).
- **Verdict: ADOPT** — install into the operating Burp Pro instance (Windows), use for any target where JWTs appear in `recon_jsintel.sh`/auth-header discovery. No pipeline wiring needed — it's Burp-side, not CLI.

## 2. EVALUATE — `RyanJarv/cdn-proxy` (CDN re-fronting / origin IP-allowlist bypass)
- **What it is:** Toolkit (Python + Go scanner + Burp extension, 272★/25 forks) that stands up your own CloudFront/Cloudflare distribution pointed at a target's origin to bypass IP-allowlist restrictions that assume "traffic only arrives via our CDN" — since shared CDNs share IP pools, a second attacker-controlled distribution on the same network can reach origins the target meant to lock down to CDN-only traffic.
- **Why it's relevant:** our in-scope top-tech list is CDN-saturated (Cloudflare, CloudFront, Google Cloud CDN, Varnish) — any origin that trusts "request came from our CDN's IP range" as an authz boundary is exactly this bug class, and it's a genuine bypass primitive, not a state-observation (fits chain-to-impact, not a dup-trap — the crowd rarely stands up a second CDN distribution to test this).
- **Caveats:** maturity signal is mixed — decent star count but stale-package warnings in its own README ("PyPi version is not the latest") suggest thinner recent maintenance than the star count implies; it also requires standing up real cloud infra (a CloudFront/Cloudflare distribution) under our own account, which is more setup than our other lanes.
- **Verdict: EVALUATE** — trial manually on ONE Cloudflare/CloudFront-fronted host where we suspect IP-allowlisted origin logic (e.g. an API gateway host from `recon_kr.sh`), before deciding whether it's worth scripting into `recon_uncover.sh`-adjacent tooling. Not autonomous-pipeline material yet.
