## 1. NEW — CVE-2026-32475, Elementor Pro unauth file-upload → RCE — **published TODAY (2026-08-20), patched yesterday** ★★
- **What:** Forms module's File Upload field runs the extension-blocklist check and the file-move step as two separate loops with different empty-file handling. Submitting **two file parts for the same field** skips the extension blocklist entirely → an unauthenticated attacker writes a `.php` file into a public directory → RCE. No auth, no interaction (attack complexity rated "high" only because of the two-part-upload trick, not a real barrier).
- **Affected:** Elementor Pro (WordPress) through **4.2.1**. Fixed in **4.2.2**, released 2026-08-19 — i.e. this is a same-week n-day window, prime racing territory.
- **Prerequisite:** target site needs a **published Elementor form with a File Upload field** — not universal, but common on WP marketing/contact sites.
- **Detect (unauth, in-range-verifiable):** Elementor Pro version via readme/plugin metadata or the `elementor-pro` JS bundle in jsintel; then confirm the site has a live form with a file-upload field (visible in the rendered page/DOM — no probe needed). CVSS 9.0.
- **Action:** version-match (≤4.2.1) + form-with-upload-field present = strong LEAD, same-week freshness. Don't fire the actual bypass autonomously (crosses into exploitation) — flag for `recon-mood wordpress`/`elementor` sweep and hand to operator for confirm-then-stop.
- **Sources:** [The Hacker News](https://thehackernews.com/2026/08/elementor-pro-flaw-could-let.html), [IONIX](https://www.ionix.io/threat-center/cve-2026-32475/), [Patchstack](https://patchstack.com/articles/critical-unauthenticated-file-upload-to-rce-in-elementor-pro-plugin/)

## 2. NEW — CVE-2026-15748, Forminator Forms unauth file-upload → RCE, CVSS 9.8, 300k+ still-vulnerable sites ★
- **What:** Attacker manipulates a form containing both a **Select field and a File Upload field**, injects forged upload-config data, bypasses the dangerous-extension filter, uploads an executable PHP file. Unauth, no interaction.
- **Affected:** Forminator ≤ **1.56.1**. Fixed in **1.56.2** (2026-07-31) — patch is ~3 weeks old but 300k+ sites were still unpatched at public disclosure (2026-08-17), so this is still a live window.
- **Prerequisite:** form must have both a Select field + File Upload field (visible in rendered DOM).
- **Detect:** Forminator version via readme/plugin metadata or `forminator` JS bundle in jsintel.
- **Action:** same treatment as #1 — version+form-shape match = LEAD, sweep our WordPress-fingerprinted hosts for the `forminator` plugin.
- **Sources:** [The Hacker News](https://thehackernews.com/2026/08/forminator-wordpress-flaw-can-enable.html), [SecurityWeek](https://www.securityweek.com/300000-wordpress-sites-potentially-exposed-to-hacking-due-to-form-plugin-flaw/), [securityonline.info](https://securityonline.info/cve-2026-15748-forminator-rce/)

## 3. NEW — CVE-2026-66447, "WordPress File Upload" plugin unauth SQLi, CVSS 9.3
- **What:** Improper sanitization of a parameter (`uniqueuploadid`, per WPScan's tracking as CVE-2026-17044 — two IDs referencing the same disclosure, verify which NVD assigns before citing) used directly in a SQL statement — unauthenticated, full DB-read exposure.
- **Affected:** WordPress File Upload plugin < **5.1.8**. Disclosed 2026-08-05/06.
- **Detect:** plugin version via readme/metadata (`wp-file-upload` slug).
- **Action:** version-match = LEAD. Confirm via our standard safe `'` vs `''` SQLi differential (never sqlmap `--dump` per doctrine) if a candidate host surfaces.
- **Sources:** [Patchstack](https://patchstack.com/database/wordpress/plugin/wp-file-upload/vulnerability/wordpress-wordpress-file-upload-plugin-5-1-7-sql-injection-vulnerability?_s_id=cve), [locaterisk.com analysis](https://locaterisk.com/en/cve-2026-66447-wordpress-file-upload-sqli/), [WPScan](https://wpscan.com/vulnerability/364c99a4-4ce9-4e5f-bccc-2b4081e4031d/)

## 4. LOW-ACTIONABILITY — CVE-2026-42945, Nginx `ngx_http_rewrite_module` heap overflow, CVSS 9.2 — our #1 top-tech, but not safely testable
- **What:** Config-dependent bug: a `rewrite` directive with an **unnamed PCRE capture** (`$1`/`$2`) + a **replacement string containing `?`**, followed by another `rewrite`/`if`/`set` in the same scope → heap buffer overflow in the worker process → crash, RCE possible with ASLR bypassed.
- **Affected:** NGINX OSS 0.6.27–1.30.0, Plus R32–R36. Fixed: OSS 1.30.1/1.31.0, Plus R32 P6/R36 P4.
- **Why it's a dead end for us:** triggering it **crashes the worker process** — that's DoS, out of our non-destructive safe-probe scope. It's also **not remotely fingerprintable** without the config being visible (no version banner reveals this specific directive combo) — a version-in-range match alone is very low-confidence since most nginx configs don't use this pattern. Not worth an active sweep; note for awareness only, don't build a probe.
- **Source:** [SOCPrime](https://socprime.com/blog/cve-2026-42945-critical-nginx-rewrite-flaw/), [F5/AWS advisory](https://my.f5.com/manage/s/article/K000161019)
