# Research digest — kb-enrich — 2026-09-03 (pass 5)

Two proposals this run, both aimed at cloud-creds/data-exposure lanes (`class-firebase`, `class-bucket-exposure`) — genuinely new primitives our current docs don't cover, both source-grounded from 2025 writeups.

## 1. Firebase — anonymous self-signup escalates "authenticated" rules to effectively-unauth (`class-firebase.md`)

The #1 real-world Firebase misconfiguration in 2025 disclosures isn't an open DB — it's `allow read, write: if request.auth != null` used as the ENTIRE gate. Any Firebase project with Anonymous Auth enabled (a checkbox, often left on from onboarding/guest-cart flows) lets *anyone* mint a valid `idToken` with zero registration, then present it to satisfy that rule. This turns a "requires login" collection into effectively public — our current doc treats `databaseURL`/config extraction and shallow-key reads but has no authenticated-escalation primitive. — [blog.m1tz.com (2025-07)](https://blog.m1tz.com/posts/2025/07/hacking-firebase-projects-enumeration-and-common-misconfigurations/), [deepstrike.io](https://deepstrike.io/blog/exploiting-firebase-authentication-misconfigurations)

## 2. Cloud storage — Azure Blob anonymous container listing + GCS per-object legacy-ACL gap (`class-bucket-exposure.md`)

Our current doc explicitly notes "Azure = manual, no S3Scanner support" and has no GCS-specific test beyond the S3-pattern object GET. Two gaps closed: (a) Azure containers set to "Full public read" are directly enumerable over REST with no auth and no tooling gap anymore — trivial to add as a manual lane; (b) GCS Uniform Bucket-Level Access "secures" the bucket at the IAM layer but **legacy per-object ACLs set before UBLA was enabled persist and are NOT revoked by enabling UBLA** — so a bucket that correctly 403s at list-level can still have individually public objects. — [hackingthe.cloud](https://hackingthe.cloud/azure/anonymous-blob-access/), [haxoris.com](https://haxoris.com/haxoris-wiki/cloud-vulnerabilities/gcp/gcs-public-buckets), [Google Cloud docs (public access prevention)](https://docs.cloud.google.com/storage/docs/public-access-prevention)


POST https://identitytoolkit.googleapis.com/v1/accounts:signUp?key=<apiKey>
Content-Type: application/json
{"returnSecureToken":true}
```
`apiKey` is the public Firebase Auth key already harvested from `/__/firebase/init.js` or the JS bundle
(never a secret — existing doctrine). Response = `{"idToken":...,"localId":...}` — a brand-new anonymous
UID, not a real user; no signup form, no email, nothing third-party.

Then present that `idToken` to the SAME endpoints already in this doc:
```
GET https://firestore.googleapis.com/v1/projects/<pid>/databases/(default)/documents/<collection>
Authorization: Bearer <idToken>

GET https://<rtdb>/<path>.json?auth=<idToken>
```
- **200 with data** where the fully-unauth request 403'd → **CONFIRMED**: the "auth required" rule is
  satisfied by a throwaway anonymous identity anyone can mint. This is the finding — the collection was
  never actually access-controlled, only login-walled, and the login wall has a free bypass.
- **403 still** → check if the rule adds `request.auth.token.firebase.sign_in_provider != 'anonymous'`
  (the documented correct fix) — if so this is the SECURED state, note + move on.
- Stay inside the no-harvest hard line: pull ONE document / `shallow=true` on RTDB to prove the read
  succeeds, do not page/dump. Same severity ladder as the existing RTDB section (config-only = Low,
  user/PII node = escalate to operator, never read values past proving the node exists).

### Why this is dup-resistant
The crowd's Firebase checks stop at "is the DB world-readable" (fully unauth). This lane requires
noticing Anonymous Auth is enabled AND that the rule only checks `auth != null` — both require reading
the app's actual auth flow, which commodity scanners don't reason about.
```

```
## GCS — legacy per-object ACLs survive Uniform Bucket-Level Access
A GCS bucket with UBLA enabled correctly returns 403 on the bucket-level list/IAM checks — but **objects
uploaded before UBLA was turned on keep their individual legacy ACL grants**, which UBLA does not revoke
retroactively. A bucket that looks secured at the bucket level can still leak specific objects.
- Test individual known/referenced object paths even after a bucket-level 403:
  `curl -I https://storage.googleapis.com/<bucket>/<object>` — 200 on an object despite 403 on the
  bucket listing = the legacy-ACL gap; note it as a distinct (lower-noise, provenance-object-specific)
  finding, not "bucket public."
- Also test the alternate authenticated-proxy domain `storage.cloud.google.com/<bucket>/<object>` —
  it enforces IAP/organization policy differently than `storage.googleapis.com` in some GCP setups; a
  divergence between the two (one 200s, one prompts Google login) is worth noting, not a bug on its own.
- **Public Access Prevention (PAP)** is an org-policy constraint (`storage.publicAccessPrevention`) some
  GCP orgs enforce that makes public buckets structurally impossible regardless of IAM/ACL — if a target
  org clearly has PAP (all buckets consistently 403 including on known-old objects), that's a secured
  posture worth a host_note so we don't keep re-testing the same org's buckets.
- Tool mention (dup-heavy permutation tool, same caution as GrayhatWarfare — Lane C only): GCPBucketBrute.
```
