## 1. React2Shell (CVE-2025-55182 / disputed CVE-2025-66478) — unauthenticated RCE in React Server Components / Next.js, with a SAFE fingerprint (`tech-nextjs`)
Disclosed Dec 2025, CVSS 10.0, actively exploited with public PoCs (multiple GitHub repos, Dec 4 2025 onward). Directly relevant — Next.js is one of our documented tech-fingerprints and the bug hits any RSC-based app (Next.js, React Router RSC mode, Waku, Parcel RSC, Vite RSC, RedwoodSDK).

- **Root cause:** `getOutlinedModel()` in the RSC "Flight" protocol deserializer walks object paths without a `hasOwnProperty` guard, so a crafted `Next-Action` POST (multipart, field refs like `$1:__proto__:then`) reaches `constructor` → `Function` constructor → arbitrary JS execution server-side. Single unauthenticated request, no session needed.
- **Affected:** `react-server-dom-{parcel,turbopack,webpack}` 19.0.0/19.1.0/19.1.1/19.2.0; Next.js 15.0.4–16.0.6 and 14.3.0-canary.77+. Fixed: React 19.0.1/19.1.2/19.2.1; Next.js 15.0.5/15.1.9/15.2.6/15.3.6/15.4.8/15.5.7/16.0.7.
- **Safe, non-destructive detection (matches our confirm-primitive-not-harvest doctrine):** send a Flight payload of `["$1:a:a"]` against an empty object on the Server Function endpoint (`Next-Action` header). A **vulnerable** server crashes and returns `500` with a JSON body containing `"digest"`; a **patched** server rejects it cleanly with no crash. This distinguishes vuln/patched with zero code execution — usable in our n-day/version-reasoning lane before any exploit attempt.
- ⚠️ NVD reportedly **rejected** the companion Next.js-side CVE-2025-66478 assignment — cite CVE-2025-55182 as primary, verify -66478 status before referencing it in a report.
- Sources: [Sysdig — Detecting React2Shell](https://www.sysdig.com/blog/detecting-react2shell), [Datadog Security Labs](https://securitylabs.datadoghq.com/articles/cve-2025-55182-react2shell-remote-code-execution-react-server-components/), [SecureLayer7](https://blog.securelayer7.net/cve-2025-55182/), [Praetorian](https://www.praetorian.com/blog/critical-advisory-remote-code-execution-in-next-js-cve-2025-66478-with-working-exploit/)

## 2. Cloud-metadata SSRF filters bypassed via DNS-rebinding TOCTOU + a real IMDS-adjacent gap in AWS Bedrock (`class-ssrf`)
Two concrete, generalizable additions beyond the encoding-payload material we already recorded (2026-08-16 digest):

- **DNS-rebinding TOCTOU bypass (generalizable pattern, not just Craft CMS):** CVE-2026-27127 shows the anti-pattern — an SSRF guard resolves the target hostname to check it's not `169.254.169.254`/private, then a *separate* resolver does the actual fetch. Attacker registers a domain with a short TTL that resolves to a public IP at validation time, then to `169.254.169.254` at fetch time. Detection for our lane: any app-level "SSRF protection" that validates a hostname (not the IP actually connected to) is worth testing with a rebinding domain (e.g. via `rbndr.us`-style services) even when a metadata-IP blocklist appears present.
- **IMDSv2 is not automatically sufficient:** if the SSRF primitive gives the attacker control over HTTP method + arbitrary headers (not just a URL param), the full IMDSv2 `PUT`-token handshake can be replayed through the SSRF itself, defeating the "IMDSv2 blocks SSRF" assumption devs rely on.
- **AWS Bedrock AgentCore Runtime MMDS gap (Unit 42, 2025):** Bedrock's microVM Metadata Service did not enforce IMDSv2-style session tokens — basic unauth SSRF against the MMDS endpoint from inside an agent runtime leaked credentials. Relevant if we ever encounter Bedrock-agent-backed endpoints in scope; worth a specific fingerprint/check if we add Bedrock-hosted targets.
- Sources: [GitHub Advisory GHSA-gp2f-7wcm-5fhx (CVE-2026-27127)](https://github.com/advisories/GHSA-gp2f-7wcm-5fhx), [Appsecure — SSRF in Cloud Environments](https://www.appsecure.security/blog/ssrf-cloud-environments)

## 3. Salesforce Aura/Experience Cloud — live mass-exploitation campaign gives us a SAFE, read-only detection technique (`class-salesforce-aura`)
ShinyHunters ran a campaign (Sept 2025 → disclosed March 2026) against ~300–400 orgs by weaponizing **AuraInspector**, a tool Mandiant open-sourced in Jan 2026 specifically as a *defensive, read-only* misconfiguration checker — its detection method is exactly our style of unauth-safe primitive.

- **Target:** `/s/sfsites/aura` (also `/aura`, `/sfsites/aura`) on Salesforce Experience Cloud sites with an overly-permissive **guest user profile**.
- **Read-only detection flow (safe — no data extraction needed to confirm):** capture a legitimate `aura.context` blob from a normal page load (mode/framework UID/app reference/component hashes), then POST a `message` param invoking `serviceComponent://ui.force.components.controllers.hostConfig.HostConfigController/ACTION$getConfigData` — this enumerates accessible Objects/Components **without authentication**. A guest profile that returns sensitive objects (Account/Contact/Lead, internal user data, case/support records) confirms the misconfiguration; AuraInspector deliberately stops here (no record dump) to stay non-destructive — matches our doctrine exactly (confirm the primitive, never harvest).
- **Why this matters now:** the *malicious* variant of the same tool is what's actively breaching orgs, meaning any Salesforce Experience Cloud host we have in scope is presently under active mass-scanning — a fresh, high-signal, dup-resistant target class if we can fingerprint it (favicon/JS refs to `force.com`/`.lightning.force.com`, or `/s/sfsites/aura` responding) among in-scope hosts.
- **Confirmed real vulnerability class, not theoretical:** unauth full-name/email/phone disclosure via guest Aura context is separately documented (Intigriti); historically also unauthenticated file upload via guest support-ticket flows.
- Sources: [Wikipedia — Aura data breach](https://en.wikipedia.org/wiki/Aura_data_breach), [The Hacker News — Threat Actors Mass-Scan via Modified AuraInspector](https://thehackernews.com/2026/03/threat-actors-mass-scan-salesforce.html), [RH-ISAC](https://rhisac.org/threat-intelligence/shinyhunters-sf-aura/), [Intigriti — Hacking Salesforce Lightning](https://www.intigriti.com/researchers/blog/hacking-tools/hacking-salesforce-lightning-guide-for-bug-hunters), [GBHackers — AuraInspector](https://gbhackers.com/salesforce-aura/)
