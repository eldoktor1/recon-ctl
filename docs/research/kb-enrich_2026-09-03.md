Focused on two KB gaps found during review: `class-bucket-exposure.md` is S3Scanner/AWS-specific despite GCS being one of our top in-scope technologies, and `class-firebase.md`'s RTDB/Firestore test only tries raw-anonymous requests, missing the anonymous-signup-token bypass for `auth != null` rules. ## 1. GCS bucket enumeration is a real blind spot — our scanner is AWS/S3-only (`class-bucket-exposure`)

S3Scanner (our backend) has **no GCS provider support beyond `HeadBucket`-equivalent existence checks** — it can't test the anonymous-permission primitives GCS actually needs. Given "Google Cloud" and "Google Cloud CDN" are both in our top in-scope tech list, this is a genuine coverage gap on Lane A (target-reference mining already extracts `storage.googleapis.com` refs per the existing doc — they just aren't being tested with the right primitives).

**The unauthenticated permission-test primitive (safer than trying List directly):** GCS exposes a dedicated `testIamPermissions` endpoint that answers "what can an anonymous caller do" in one read-only call, without needing to actually list/read anything first:
```
GET https://www.googleapis.com/storage/v1/b/<bucket>/iam/testPermissions?permissions=storage.objects.list&permissions=storage.objects.get&permissions=storage.objects.create&permissions=storage.buckets.setIamPolicy
```
Returns only the subset of requested permissions actually granted to `allUsers`/anonymous — this is the GCS equivalent of our AWS `perm_*` fields and should drive the same LEAD/CONFIRMED split (list/get = read exposure LEAD, `objects.create` = write CONFIRMED, `setIamPolicy` = ACL-write CONFIRMED). — [Rhino Security Labs GCPBucketBrute](https://github.com/RhinoSecurityLabs/GCPBucketBrute)

**Direct read confirm (mirrors our AWS listing-XML evidence step):**
```
curl -I https://storage.googleapis.com/<bucket>/<object>       # 200 = object public
curl "https://storage.googleapis.com/<bucket>"                 # bucket listing attempt (JSON error names the exact missing perm when denied)
```
An anonymous denial names the specific permission it lacks (`"Anonymous caller does not have storage.objects.list access..."`) — useful for the FP table since it disambiguates "no perm" from "bucket doesn't exist" the way our S3 403-vs-404 table already does for AWS.

**UBLA nuance (the GCS-specific FP trap to add to our provenance/severity table):** Legacy per-object ACLs can grant `allUsers` read on individual objects even when the *bucket* IAM policy looks private — and these legacy ACLs **persist after switching to IAM** unless Uniform Bucket-Level Access (UBLA) is explicitly enabled. Check `iamConfiguration.uniformBucketLevelAccess.enabled` via `gcloud storage buckets describe`; a bucket with UBLA off may show secure bucket-level IAM but still leak individual public objects — don't call it secure off the bucket-level check alone. — [Haxoris GCS Public Buckets wiki](https://haxoris.com/haxoris-wiki/cloud-vulnerabilities/gcp/gcs-public-buckets), [Netskope](https://www.netskope.com/blog/google-storage-bucket-misconfiguration)

**Dangling/predictable-name pattern — same takeover lane, new source class:** Google's CVE-2026-2473 (Vertex AI SDK, patched, Unit 42-reported "Pickle in the Middle") is a generalizable pattern worth watching for on any GCP-SDK-backed target: SDKs that auto-derive a staging/temp bucket name from `{project-id}-{service}-{region}` and check *existence* but not *ownership* before uploading/trusting it. Attacker who can predict the pattern (project IDs are often public) registers the bucket first → cross-tenant model/data theft. This is our existing "NoSuchBucket referenced by live target → takeover lane" primitive applied to GCP client-SDK bucket derivation instead of only CNAME/JS references — worth grepping jsintel/source-map output for GCP SDK bucket-name-construction logic (`{project}-vertex-staging-{region}`-style string templates), not just literal bucket URLs. — [The Hacker News](https://thehackernews.com/2026/06/google-vertex-ai-sdk-flaw-let-attackers.html)

```
**FP trap — UBLA off ≠ what bucket-level IAM shows:** legacy per-object ACLs persist independently of
bucket IAM and are NOT disabled until Uniform Bucket-Level Access is explicitly turned on
(`gcloud storage buckets describe gs://<bucket> --format='value(iamConfiguration.uniformBucketLevelAccess.enabled)'`).
A bucket that looks IAM-secure at the bucket level can still leak individual objects via a stale object
ACL when UBLA is off — check UBLA status before declaring a GCS bucket "secure" off the bucket-level
IAM policy alone.
```

## 2. Firebase — Remote Config unauth fetch + anonymous-signup token bypasses `auth != null` rules (`class-firebase`)

Two concrete, unauth-appropriate gaps in our current methodology:

**(a) Remote Config is a distinct unauthenticated read surface we don't currently test.** The Android
API key (public by design, already excluded from `js_secret_hit`) plus an App ID (both extractable from
`google-services.json`/APK strings or the `__/firebase/init.js` config our lane already fetches) is
enough to pull the FULL Remote Config parameter set with no auth:
```
POST https://firebaseremoteconfig.googleapis.com/v1/projects/{PROJECT_ID}/namespaces/firebase:fetch?key={API_KEY}
Content-Type: application/json
{"appId":"{GOOGLE_APP_ID}","appInstanceId":"anyvalue"}
```
200 + JSON entries = exposed (feature flags, experiment config, and — the actual severity driver — any
secrets/internal endpoints operators mistakenly stashed in Remote Config, which happens per the source
writeup). This is read-only, no state change, same evidence-without-harvest discipline as our RTDB
`shallow=true` primitive: capture the parameter *names*, let the operator judge value sensitivity before
reporting. — [emergetools.com](https://docs.emergetools.com/docs/firebase-remote-config-api-exposed)

**(b) Anonymous-signup token bypasses `auth != null` rules our current RTDB/Firestore test can't see.**
Our current methodology only tries pure-anonymous GETs against RTDB/Firestore, which correctly identifies
`.read: true` rules but silently misses the much more common `.read: "auth != null"` rule — because
Firebase's own Identity Toolkit lets *anyone* mint a satisfying token with zero credentials, no signup
form, no CAPTCHA:
```
curl -X POST "https://identitytoolkit.googleapis.com/v1/accounts:signUp?key={API_KEY}" \
  -H "Content-Type: application/json" -d '{"returnSecureToken": true}'
```
Returns an `idToken` for a genuinely-created (but attacker-owned, empty) account — satisfies `auth != null`
everywhere. Re-run the RTDB/Firestore shallow-read tests WITH `Authorization: Bearer <idToken>` before
concluding a project is "secured" on the strength of an anonymous 401 alone:
```
curl -H "Authorization: Bearer <idToken>" "https://<rtdb>/.json?shallow=true"
curl -H "Authorization: Bearer <idToken>" "https://firestore.googleapis.com/v1/projects/<pid>/databases/(default)/documents/<collection>"
```
Fits our ACTIVE-PoC doctrine cleanly (own-account setup, minimal, non-malicious, prove-then-stop) — the
signUp call creates one throwaway anonymous account in the target's own Firebase project, not third-party
access. Severity discipline is unchanged: this only *upgrades what we can see*, it doesn't change the
read/write/keys-only rules already in the doc. A Dec-2025 writeup chains this with a CSP-wildcard bug for
a claimed CVSS 9.9 RCE — unverified aggregator claim, don't cite the score, but the underlying
signup-token-bypasses-auth-null-rules mechanism is independently corroborated and directly usable.
— [aw-junaid/bug-bounty Firebase Exploitation methodology](https://github.com/aw-junaid/bug-bounty/blob/main/methodologies/web%20technologies/Firebase%20Exploitation.md)


POST https://firebaseremoteconfig.googleapis.com/v1/projects/{PROJECT_ID}/namespaces/firebase:fetch?key={API_KEY}
Content-Type: application/json
{"appId":"{GOOGLE_APP_ID}","appInstanceId":"anyvalue"}
```
`API_KEY` and `PROJECT_ID`/`GOOGLE_APP_ID` come from the same `__/firebase/init.js` / JS-bundle mining
this doc already describes. 200 + JSON `entries` = exposed. Evidence-without-harvest: capture parameter
*names* only, flag to operator for value-sensitivity judgment (feature flags = low; anything
secret/endpoint-shaped in a value = escalate). Source: docs.emergetools.com/docs/firebase-remote-config-api-exposed

**Anonymous-signup token — re-test RTDB/Firestore before calling a project "secured" (critical addition):**
Our current pure-anonymous RTDB/Firestore test (§ RTDB open-read confirm above) only catches `.read: true`.
It MISSES the much more common `.read: "auth != null"` rule, because Identity Toolkit lets anyone mint a
satisfying token for free, no signup UI, no real user:
```
curl -X POST "https://identitytoolkit.googleapis.com/v1/accounts:signUp?key={API_KEY}" \
  -H "Content-Type: application/json" -d '{"returnSecureToken": true}'
```
→ `idToken` in the response. Re-run the shallow-keys-only RTDB test AND the Firestore collection test
WITH `Authorization: Bearer <idToken>` before recording a project as secured off an anonymous 401 alone:
```
curl -H "Authorization: Bearer <idToken>" "https://<rtdb>/.json?shallow=true"
curl -H "Authorization: Bearer <idToken>" "https://firestore.googleapis.com/v1/projects/<pid>/databases/(default)/documents/<collection>"
```
Gate: this creates one throwaway anonymous account inside the TARGET's own Firebase project — fits
ACTIVE-PoC doctrine (own-account setup, minimal, prove-then-stop), not third-party access. If the
bearer-token read now succeeds where anonymous failed, the finding is "any anonymous signup can read
[node]" — same MED-HIGH-if-PII severity ladder as the existing anonymous-read primitive, just reached via
a slightly higher (still unauth-equivalent) bar. Don't test write with the minted token (same hard line
as anonymous write testing above — operator-only).
```
