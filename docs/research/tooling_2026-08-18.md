## ADOPT-candidate — graphql-cop (dolevf/graphql-cop)
- **What it is:** Python GraphQL security auditor, 686★/102 forks/113 commits — actively maintained, well past our "single-author toy" bar. Runs 12 misconfig checks unauthenticated, non-destructive: **CSRF via GET-based queries / mutations-over-GET**, batch-query / alias-overloading / field-duplication / directive-overloading / circular-query **DoS-detection** (checks the primitive exists, doesn't launch a DoS), tracing/debug-mode leakage, field suggestions, GraphiQL exposure, introspection. Has `-f/--force` to probe common GraphQL paths even when introspection is off.
- **Why it beats what we have:** `recon_graphql.sh` today stops at introspection-schema→reasoning. graphql-cop's **mutation-over-GET / CSRF check is a real exploitable primitive** (a state-changing GraphQL mutation reachable via a plain `GET` request is CSRF-able cross-site) — not the Info-FP "introspection enabled" dup-trap our own KB warns against. That's a genuine chain-to-impact candidate, not a state.
- **Doctrine fit:** unauth-safe ✅ (GET/read-only probes, no exploitation), non-destructive ✅ (detects DoS-capability without firing it), dup-resistant ✅ (crowd mostly stops at introspection-only). Fits directly under `recon_graphql.sh`'s existing safe-probe posture.
- **Verdict: ADOPT** — wire as a supplemental pass inside `recon_graphql.sh` after schema harvest: run graphql-cop's misconfig checks, and treat a confirmed **mutation-reachable-via-GET** hit as CONFIRMED-primitive tier (matches our `ALWAYS_MINT`-style chain, since it's an executed unauth primitive, not a state observation) rather than a LEAD.

## Build-note (not a tool, sharpens an existing KB gate)
CVE-2026-40976 precise vulnerability preconditions (confirmed via GitHub Advisory GHSA-8v8j-3hxp-93wr + HeroDevs/ZeroPath writeups): a Spring Boot 4.0.0–4.0.5 app is vulnerable **only if** it (a) is servlet-based, (b) has **no own Spring Security config** (relies on Spring's default filter chain), (c) depends on `spring-boot-actuator-autoconfigure`, **and** (d) does **not** depend on `spring-boot-health`. Presence of `spring-boot-health` alone negates the bypass regardless of version. Sharpens the version-gate in our KB so `recon_actuator_chain.py` doesn't LEAD-flag every 4.0.0-4.0.5 host — only ones actually missing the health starter.
