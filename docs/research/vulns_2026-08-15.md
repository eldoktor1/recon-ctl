## 1. WordPress core "XSS2Shell" — CVE-2026-64638 — pre-auth reflected XSS on login, EVERY version since 4.7 ★ HIGH PRIORITY, DIRECTLY TESTABLE
- **What:** Reflected XSS on `wp-login.php`'s failed-login error page — a crafted **username** in the login POST reflects unencoded into the error output, executing attacker JS in the visitor's browser with zero interaction beyond the failed login. Nicknamed XSS2Shell because when a logged-in **Administrator** later interacts with the crafted page, the chain escalates to full PHP RCE on the server (deployment-condition-dependent for the RCE leg; the XSS leg alone is unauth and unconditional).
- **Affected:** WordPress core **4.7 through 7.0.2** — effectively every actively maintained install (bug shipped since 4.7, ~500M+ sites pre-patch). **Fixed 2026-08-06 in 7.0.3**, backported through the 4.7 branch.
- **Detect / in-range-verifiable:** version fingerprint via `readme.html`, `?ver=` query-string cache-busters on core `/wp-includes/js/*.js`, or `<meta name="generator">` (often stripped) — any WP host on core `< 7.0.3` is in-range. **The XSS leg itself is directly, safely testable** with our existing `recon_xss_confirm.sh` primitive against `wp-login.php` (crafted `log=` param, headless-Chromium execution check) — this is a real extension of our XSS lane onto a login endpoint we don't currently target. No PoC publicly weaponized yet, no ITW as of this writing.
- **Action:** treat version `<7.0.3` as in-range LEAD; run the XSS confirm primitive against `wp-login.php` on in-scope+paying WordPress hosts (top-tech for us) — a firing marker there is a genuine CONFIRMED unauth XSS, not just a version match. The admin-interaction RCE chain stays LEAD-only / report-the-XSS, don't chase full RCE.
- **Sources:** [The Hacker News](https://thehackernews.com/2026/08/new-wordpress-pre-auth-xss-could-lead.html), [WordPress GHSA-52p2-r8wf-jcrf](https://github.com/WordPress/wordpress-develop/security/advisories/GHSA-52p2-r8wf-jcrf), [cybersecuritynews.com](https://cybersecuritynews.com/wordpress-xss2shell-vulnerability/)

## 2. Ajax Search Lite plugin — CVE-2026-28139 / CVE-2026-16258 — unauth PHP Object Injection, CVSS 9.8
- **What:** Deserialization of untrusted input (CWE-502) in the Ajax Search Lite WP plugin lets an unauthenticated attacker perform PHP Object Injection; RCE is reachable **if** a usable POP gadget chain exists elsewhere in the site's loaded classes (not guaranteed, but common on plugin-heavy WP sites).
- **Affected:** Ajax Search Lite `≤ 4.14.4`. Fixed in `4.14.5` (patched ~Aug 4 2026).
- **Detect (unauth, in-range-verifiable):** plugin presence via `/wp-content/plugins/ajax-search-lite/readme.txt` → `Stable tag`, or `wp-json`/enqueued-script version strings (`ajax-search-lite` in jsintel asset paths). Version `<4.14.5` = in-range LEAD.
- **Action:** narrow-surface but worth a version sweep given WordPress's weight in our tech corpus — don't attempt the deserialization/gadget-chain exploitation without a confirmed gadget (PoC-OR-GTFO still needs a working, non-destructive primitive; PHPGGC gadget-chain probing on a live target is destructive-risk, treat as LEAD for report-the-version-exposure, escalate only with operator sign-off).
- **Sources:** [Patchstack DB](https://patchstack.com/database/vulnerability/ajax-search-lite), [OffSeq Threat Radar](https://radar.offseq.com/threat/cve-2026-16258-cwe-502-deserialization-of-untrusted-data-in-ajax-search-lite-1ae2ea1fc4b9d537)

## 4. Technique note — GraphQL global-ID decode/increment/re-encode is a repeat pattern across H1/GitLab/Shopify BOLA disclosures
An empirical taxonomy of 100+ disclosed BOLA/IDOR reports confirms GraphQL "global ID" (base64 `Type:123`) objects are routinely exploited by **base64-decoding the ID, incrementing the numeric component, re-encoding** — bypassing the false sense of security opaque IDs give. Also flags **batching attacks** (many queries in one request bypassing per-request rate limits) as a recurring GraphQL-specific issue. This is a concrete addition to our `recon_graphql.sh` schema-reasoning worklist: when a GraphQL schema exposes a `node(id: ID!)` resolver or Relay-style global IDs, flag it explicitly for the decode/increment/re-encode test (human 2-account confirm, not auto-probed — same hard line as existing IDOR doctrine).
- **Source:** [arXiv — BOLA in the Wild: Empirical Taxonomy from 100+ Bug Bounty Disclosures](https://arxiv.org/html/2605.25865)
