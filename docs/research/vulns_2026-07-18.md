## 1. NGINX version-table update — several 2026 CVEs land exactly on our fingerprinted `nginx/1.29.7` (HIGH PRIORITY)
Our in-scope tech list carries the literal fingerprint `Nginx:1.29.7`. Pulled the full 2026 advisory
table from nginx.org — **1.29.7 is NOT patched against 6 CVEs** (all fixed only in 1.30.1+/1.31.0+):

| CVE | Issue | Vulnerable range | Notes |
|---|---|---|---|
| **CVE-2026-42945** ("NGINX Rift") | Heap buffer overflow, `ngx_http_rewrite_module` | 0.6.27–1.30.0 | CVSS 9.2. **Actively exploited in the wild** (VulnCheck honeypots, since May 2026). RCE requires ASLR disabled; DoS (worker crash) is the reliable outcome. **Config-dependent**: needs a `rewrite`/`if`/`set` directive with an unnamed PCRE capture (`$1`) in a replacement string containing `?` — can't be config-confirmed from outside, and triggering it risks crashing the worker (DoS = out of bounds for our safe-probe doctrine). ## 2. WordPress core unauth RCE — "wp2shell" CVE-2026-63030 (HIGH PRIORITY, if any WP core in range)
Published 2026-07-17. Truly **unauthenticated**, no preconditions. Root cause: the `/wp-json/batch/v1`
REST batch endpoint runs sub-requests tracked in two parallel arrays; an error in one sub-request
desyncs the arrays by one, causing a request to execute under a *different* sub-request's handler —
which lets an attacker walk past the endpoint's allow-list. Chained with a separate unauth SQLi
(CVE-2026-60137, present since 6.8.0) it becomes full unauthenticated RCE.
- **Affected**: WordPress core 6.9.0–6.9.4 and 7.0.0–7.0.1. Fixed in 6.9.5 / 7.0.2.
- **Detect**: fingerprint WP version (meta generator tag / `readme.html` / `wp-json/` root response `"version"` sometimes exposed) in that range, confirm `/wp-json/batch/v1` route responds (route existence, not exploitation — GET/OPTIONS only, safe). A public checker exists at wp2shell.com if we want a reference implementation.
- **Do not** replay the chained exploit — this is RCE, out of bounds for our unauth-safe primitive; surface as a version+route-confirmed LEAD for the operator, not an auto-confirm.

Sources:
- [wp2shell — The Hacker News](https://thehackernews.com/2026/07/new-wp2shell-wordpress-core-flaw-lets.html)
- [Rapid7 ETR: CVE-2026-63030](https://www.rapid7.com/blog/post/etr-cve-2026-63030-wp2shell-a-critical-remote-code-execution-vulnerability-in-wordpress-core/)

## 3. Varnish Cache — new cache-poisoning/auth-bypass primitive, feeds our WCD lane directly
**CVE-2026-34475**: Varnish Cache OSS before 8.0.1 and Varnish Enterprise before 6.0.16r12 mishandle
HTTP/1.1 requests whose path is `/` in "certain unchecked `req.url` scenarios" — root-path URL
validation happens at the wrong pipeline stage (CWE-180), enabling **cache poisoning or auth bypass**.
CVSS 5.4 (medium) but directly on-topic for our web-cache-deception lane (`recon_wcd.sh`) since Varnish
is a named CDN/cache tech we may encounter. This is a genuinely new Varnish-specific poisoning primitive,
distinct from our generic path-confusion WCD detector — worth a dedicated probe variant (root-path `/`
request-smuggled variant) the next time `recon-wcd` runs against a Varnish-fingerprinted host
(`Via: varnish` / `X-Varnish` headers). Separately, CVE-2026-40396 (Varnish 9.0.0, workspace-overflow DoS
via HTTP/1 pipelining) is DoS-only — out of scope for us (destructive), noted for completeness only, do not test.

Sources:

## 4. WordPress plugin auth-bypass pattern (reusable technique, not just this one plugin)
CVE-2026-57807 — miniOrange OAuth SSO plugin (≤38.5.8), CVSS 9.8: attacker bypasses login entirely via
the **password-recovery flow**, an alternate auth pathway that doesn't enforce the same login controls
as the primary login form. Generalizable pattern worth remembering for any WP/auth-plugin target:
always test password-reset/recovery endpoints as a separate auth surface, not just the login form.
Low direct relevance unless a target runs this specific plugin (fingerprint: `wp-content/plugins/wp-oauth-server-premium|miniorange-oauth`).

Source: [gbhackers.com](https://gbhackers.com/critical-wordpress-oauth-sso-plugin-flaw/)
