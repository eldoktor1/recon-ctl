## 1. Salesforce Aura/Lightning guest-user BOLA — concrete unauth PoC + tooling (`class-salesforce-aura`)
Active exploitation in the wild (ShinyHunters, disclosed publicly March 2026) confirms this is a live, high-EV, dup-resistant class on any in-scope host running Salesforce Experience Cloud/Sites — it's a **customer misconfiguration** (guest-profile over-provisioning), not a Salesforce platform 0-day, so every misconfigured org is an independent finding, not a shared CVE.

**Fingerprint:** any in-scope host serving `/aura`, `/sfsites/aura`, or `/s/sfsites/aura` (check JS/network calls off any Experience Cloud / Lightning Community page — these are Aura framework internals, present whenever `force-community`/`sfsites` bundles load).

**Safe unauth confirm — exact request shape (read-only, single POST, no mutation):**
1. `GET` the site root/community page → regex out `"fwuid":"([^"]+)"` and `"app":"([^"]+)"` from the inline markup (these are public framework build IDs, not secrets).
2. Assemble `aura.context` = base64/JSON of `{mode:"PROD", fwuid, app, loaded:{...}}`.
3. `POST {endpoint}?r=1&aura.RecordUiController.getRecordUiById=1` (or a similar throwaway path suffix) with form params `message`, `aura.context`, `aura.token=undefined`.
4. `message` = `{"actions":[{"id":"1;a","descriptor":"serviceComponent://ui.force.components.controllers.hostConfig.HostConfigController/ACTION$getConfigData","callingDescriptor":"UNKNOWN","params":{}}]}` to confirm the endpoint answers unauthenticated.
5. **The actual BOLA/data-exposure probe** swaps the descriptor for a data-listing controller — the two documented in the wild:
   - `serviceComponent://ui.force.components.controllers.lists.selectableListDataProvider.SelectableListDataProviderController/ACTION$getItems` with `params:{entityNameOrId:"User", ...}` — lists arbitrary sObject records (User, Contact, Case, custom objects) if guest profile has read access.
   - `serviceComponent://ui.force.components.controllers.detail.DetailController/ACTION$getRecord` — fetches a specific record by ID once one is enumerated via the list call.
   A response containing real `Email`/`Name`/`Phone`/`Id` fields for a non-guest object = CONFIRMED broken access control (guest profile leaking PII) — this is the finding itself, no further exploitation needed (stop at first-record confirmation per PoC-OR-GTFO minimal-proof rule).
6. **Rate-limit bypass researchers found (context, not for us to exploit):** Salesforce's default 2,000-record cap on Aura list queries can be bypassed via the `sortBy` param — useful to know when scoping *severity* (unbounded vs capped exposure) but do NOT mass-harvest; one record proves the bug.

**Tooling to adopt (both purpose-built, low-FP):**
- **AuraInspector** (Mandiant, open-source) — the auditing tool ShinyHunters themselves weaponized; walks discovered Aura components and flags which return guest-accessible data.
- **SALSA** (`github.com/cosad3s/salsa`) — Aura endpoint scanner, enumerates vulnerabilities/misconfig at scale.
- **Misconfig Mapper** — bulk-discovers exposed `/aura` paths across a target's host list (good fit ahead of our jsintel pass — run it on any host serving Experience Cloud markup).

Add to our JS-intel lane: when jsluice/endpoint mining spots `/sfsites/aura` or Aura framework JS bundles, auto-flag the host for this probe (it's a distinct, high-value confirm primitive — same tier as our GraphQL introspection lane).

## 2. ServiceNow unauthenticated REST API exposure — the June 2026 incident, generalized to a detection pattern (`tech-servicenow`)
A real-world unauth data-exposure incident (June 2026, patched by ServiceNow on the hosted side June 5) generalizes to a checkable pattern on any customer-managed/on-prem ServiceNow instance still in scope: **scripted REST APIs with `requires_authentication=false`**.

- **Vulnerable pattern:** `/api/now/related_list_edit/create` (the specific endpoint that leaked ticket/HR/vendor data across multiple orgs) was a Scripted REST API resource where the "Requires authentication" checkbox on `sys_ws_operation` was left/set to false — a config error, not a platform bug, so the same root cause reproduces on any instance where the sysadmin exposed a custom scripted REST resource without auth.
- **Safe unauth detection for our lane:** `GET`/`OPTIONS` any discovered ServiceNow custom API path (from jsintel/JS mining or `/api/now/table/*` sweeps) with **no session cookie/token**. A response containing real record data (not a 401/302-to-login) = the endpoint is unauth-reachable — this is the primitive to confirm, same tier as our actuator/GraphQL lanes: fingerprint → unauth GET → if data comes back, that response IS the finding (redact before reporting).
- Complements our existing widget/ACL-misconfig angle (Aaron Costello/AppOmni's older Simple List widget research, ~70% of tested instances leaking PII via role-less ACLs + overprovisioned guest widgets) — that's the *client-side widget* variant; this incident is the *scripted REST API* variant. Both stem from the same customer-config root cause (ACL/auth left open) and both are unauth-GET-confirmable.
- **Indicator not useful to us** (defender-side): ServiceNow's own IOCs (source IP `51.159.98.241`, UA `Mozilla-BugBounty`) — irrelevant to our hunting, only useful if we ever see an org's incident writeup mention them.
