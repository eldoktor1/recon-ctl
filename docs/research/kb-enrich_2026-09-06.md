## 1. Next.js middleware authorization bypass (CVE-2025-29927, CVSS 9.1) — single-header, unauth, no-impact-needed detection (`tech-nextjs`)
Still directly exploitable on any unpatched Next.js host in our scope — one crafted header either returns a 200 where the app previously 3xx/4xx'd for auth, or it doesn't. This is a textbook unauth-safe primitive for our doctrine (detect via response-code delta, no data harvest needed to prove it).

**Mechanism:** Next.js's internal `x-middleware-subrequest` header exists to stop middleware from recursing on itself. The runtime trusts the header from the *client* request — spoofing it makes Next.js believe the request already passed through middleware, so it **skips middleware entirely**, including auth/authz checks implemented there (very common pattern for `/admin`, `/dashboard`, protected API routes gated by cookie/JWT checks in `middleware.ts`).

**Affected:** all Next.js < 12.3.5 (12.x), < 13.5.9 (13.x), < 14.2.25 (14.x), < 15.2.3 (15.x). Patched: 12.3.5+/13.5.9+/14.2.25+/15.2.3+.

**Detection/exploit steps (unauth, two GETs):**
1. Fingerprint Next.js: `_next/static` in body, or standard Next asset paths.
2. `GET` a protected route with no header — note status (redirect/401/403) and check for `x-middleware-rewrite`/`x-middleware-next`/`x-middleware-redirect` response headers (proves middleware is gating this route).
3. Re-send the same `GET` with the version-appropriate bypass header:
   - pre-12.2: `X-Middleware-Subrequest: pages/_middleware` (or `pages/<route>/_middleware`)
   - 12.2–13.1.x: `X-Middleware-Subrequest: middleware` (or `src/middleware`)
   - 13.2.0+: `X-Middleware-Subrequest: middleware:middleware:middleware:middleware:middleware` (5x chain; `src/middleware:...` variant too)
4. Status flips to 200 with the header, stays gated without it → **CONFIRMED** middleware auth bypass. This satisfies our confirm-primitive bar (observed behavioral change from a spoofed header, not a guess) and needs no credentials/third-party data.
5. Fits our nuclei/safe-probe pattern directly — worth adding as a `recon_safe_probe.sh`/nuclei check: two GETs, diff status.

— [ProjectDiscovery: technical analysis + exact header payloads by version](https://projectdiscovery.io/blog/nextjs-middleware-authorization-bypass), [Datadog Security Labs](https://securitylabs.datadoghq.com/articles/nextjs-middleware-auth-bypass/), [Offsec](https://www.offsec.com/blog/cve-2025-29927/), [PoC repo](https://github.com/aydinnyunus/CVE-2025-29927)



## 2. SSRF — provider-specific metadata endpoints most tooling misses (`class-ssrf`)
Our existing SSRF coverage has been AWS/GCP/Azure-centric; these three are commonly missed by generic SSRF scanners because they're not on the usual `169.254.169.254` IP or need a specific header:

- **Alibaba Cloud (ECS):** metadata lives at `100.100.100.200/latest/meta-data/` — a **different link-local IP than AWS** (not `169.254.169.254`), so cloud-agnostic SSRF payload lists that only try the AWS IP miss it entirely. No auth header needed for the legacy v1-style endpoint.
- **Oracle Cloud Infrastructure (OCI):** `192.0.0.192/latest/meta-data/` (not `169.254.169.254` either); the **v2 endpoint requires the literal header `Authorization: Bearer Oracle`** — absence gives a 401, which makes it a clean, low-noise unauth SSRF confirmation probe (a blind SSRF that reaches OCI metadata and gets 401 vs 200 with/without that header is unambiguous proof of reachability).
- **DigitalOcean:** `169.254.169.254/metadata/v1/` (same IP as AWS but different path prefix) returns droplet ID, region, **user-data, and SSH public keys over plain HTTP with no header gate at all** — high-value if reachable (SSH key exposure).

**General bypass pattern still evolving:** TOCTOU / DNS-rebinding against SSRF allowlist filters that validate a hostname's resolved IP, then make the actual HTTP request as a **separate** DNS lookup (attacker's DNS flips between check and use, e.g. Craft CMS's fix for CVE-2025-68437 was itself bypassed this way for CVE-2026-27127). Relevant to any of our targets doing homegrown SSRF allowlisting rather than a single-resolve-then-connect pattern.

⚠️ The Craft CMS CVE IDs (27127/27129) trace to a vendor GHSA (`GHSA-gp2f-7wcm-5fhx`) — verify against that advisory, not just the aggregator, before citing in a report (echoes our 2026-08-16 flag on the same cluster).

— [RingSafe: SSRF beyond AWS](https://ringsafe.in/ssrf-beyond-aws-gcp-azure-onprem/), [Craft CMS GHSA-gp2f-7wcm-5fhx](https://github.com/craftcms/cms/security/advisories/GHSA-gp2f-7wcm-5fhx), [vulnsy SSRF cheat sheet](https://www.vulnsy.com/cheat-sheets/ssrf)



## 3. Mass assignment — hidden-field discovery method (`class-idor`)
Smaller addition, but fills a gap: our IDOR doc covers object-reference enumeration but not the sibling class where the *object ID is right* and the bug is an over-writable *field*. Two concretely testable patterns worth adding to our authed-testing playbook (own-account only, matches ACTIVE-PoC doctrine):

- **Blind-action mass assignment:** endpoints whose response doesn't echo the object (password reset, invite, notification-settings) are the ones developers forget to strict-whitelist, because there's no obvious "extra field showed up in the response" tell during dev. Test by taking a normal request body and adding candidate privileged fields (`role`, `is_admin`, `is_verified`, `tier`, `credits`, `provider`, `type`, `id` targeting a different object) even when the response is empty/opaque — verify via a follow-up read on your OWN second account/object.
- **Field discovery sources (before guessing blind):** OpenAPI/Swagger spec if exposed, GraphQL introspection (mutation input types list every writable field including ones the UI hides), JS bundle jsintel mining (our existing jsluice/sourcemapper lane already surfaces these — cross-reference request bodies built from expanded object shapes with what the UI form actually submits), and error messages that leak accepted-field names on validation failure.
- No new framework-specific bypass beyond what's likely already documented (Rails strong_params misconfig, Spring `@RequestBody` binding raw DTOs, Mongoose schemas without `strict: true`, DRF serializers with `fields = '__all__'`) — worth a one-line mention but not deep new content this pass.
