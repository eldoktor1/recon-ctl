## Tooling Watch — 2026-07-28

### 1. GUIDtool (intruder-io/guidtool) — **ADOPT the technique** into the IDOR ranker
Small CLI (pip) that decodes/predicts **v1 UUIDs**: extracts timestamp + MAC/node-id from a sample GUID and generates candidate future/past v1 GUIDs for a target timeframe ("often possible to forge future v1 GUIDs... if you know the approximate time"). Modest project (240★, 5 commits, unmaintained-looking) — the binary itself isn't worth deploying, but the underlying fact is a real gap in our doctrine: `recon_idor_candidates.py` currently buckets all UUID-shaped IDs as one tier ("uuid=harvestable"). **v1 and v4 are NOT equally exploitable** — v1 embeds time+MAC and is *predictable without any leak*, v4 is cryptographically random and only exploitable if an ID is actually disclosed elsewhere. This is a precision upgrade, not a new dup-trap: distinguishing UUID version at intake lets us rank v1-bearing endpoints as higher-priority IDOR candidates (structurally guessable) versus v4 (harvest-only). Detection is a pure string/bit-math check on the version nibble (13th hex group char == `1`) — no target traffic, trivially reimplementable in our existing Python ranker, unauth-safe. Actual guessing/exploitation stays human-in-the-loop (2 owned accounts) per doctrine unchanged.
Source: https://github.com/intruder-io/guidtool



### 2. x8 (Sh1Yo/x8) — **EVALUATE** as an arjun complement (not replacement)
Rust hidden-parameter-discovery suite. The maintainer's own head-to-head (https://sh1yo.art/x8stats/) claims an edge over arjun/ParamMiner specifically on **non-reflection, value-changing parameters** (e.g. `admin=true`, `debug=1` — params that flip behavior/privilege rather than reflecting into the response body), plus higher throughput at scale (thousands of URLs/run). This is a different detection mechanism than arjun's reflection-diffing, so it's additive rather than a straight swap — worth an on-demand trial (`recon-params arjun`-style, same on-demand/GET-only/rate-limited posture) alongside arjun on a few hosts to see if it surfaces genuinely new hidden params (esp. auth/role-flip params relevant to BAC). Not urgent; arjun still covers the baseline.
Source: https://github.com/Sh1Yo/x8, https://sh1yo.art/x8stats/

### SKIP — no upgrade found
- **jwt_pwned** (Bytenull00) — kid/jku/none-alg/algorithm-confusion attack modes, but 4★/0 forks, no releases — too immature; if we ever staff a JWT lane, ticarpi/jwt_tool remains the established reference implementation, not a new find this cycle.
- **Web cache poisoning scanners** (wcpvs, autoPoisoner, toxicache) — all lower-signal than WCVS, which we already run for `recon-wcd`; none demonstrate a detection technique WCVS lacks.
- **Prototype-pollution scanners** (ppfuzz, ppmap, pphack, protoscan, plution) — same known set as prior cycles (pphack already logged EVALUATE 2026-07-03); nothing new released.
- **GCP bucket/IAM scanners** (GCP-Security-Scanner, GCPBucketBrute, gcp_scanner, gcpsight) — all require authenticated cloud-account access or are privesc-focused pentest tools against a project you control; doesn't fit external unauth bug-bounty recon (we never have the target's GCP IAM creds). Not applicable to our lane.
- Generic "all-in-one recon framework" hits (recon0, BUG Framework, reconFTW-style) — reinvent subfinder|httpx|nuclei pipelines we already run individually; adopting a monolith regresses our composable/unique-lane doctrine (the MOTTO).
