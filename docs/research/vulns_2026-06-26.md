### NEW TECHNIQUE — Re:CACHE: Next.js RSC reflection → zero-click stored XSS via cache poisoning

Fresh writeup (zhero-web-sec.github.io, June 2026). Not in nuclei community templates. Targets Next.js App Router.

**What it is:** When `Rsc: 1` header is sent, Next.js returns a React Server Component (RSC) payload. On certain routes, a URL parameter is reflected verbatim into the RSC output after a `__PAGE__` boundary marker. If a CDN caches that response under the poisoned key, all subsequent visitors receive the injected payload — zero-click stored XSS.

**Safe pipeline detection (no payload, unique buster):**
- Fingerprint Next.js App Router: `x-nextjs-cache` response header OR `__PAGE__` in RSC response body OR `__NEXT_DATA__` script tag
- With `Rsc: 1` header on a parameterized route, check whether a URL-param value appears verbatim in the RSC response body (safe canary string, no JS)
- Always send unique `?cb=<nonce>` cache-buster — never test under the shared cache key
- `CF-Cache-Status: HIT` on second request (without buster) = RSC variant gets cached = poisoning prerequisite confirmed

**Related CVE:** CVE-2025-57822 (Next.js < 14.2.32 / < 15.4.7) — version-specific confirmation of the reflection variant. Fingerprint via `/_next/static/<buildId>/_buildManifest.js` or error-page version leak.

**Edge vs crowd:** Requires understanding RSC internals (`Rsc: 1` header, `__PAGE__` boundary); crowd does not probe this. Not in community scanner templates.

Source: https://zhero-web-sec.github.io/research-and-things/re-cache-excessive-reflection-type-confusion-and-0-click-sxss-on-nextjs
